# 帳號與權限：七個現場故事

本頁依 #704、#705 核可目標撰寫。新導覽與新網址在相關工作合併後才生效；
本頁的路徑是預定網址，不代表目前版本已能實際操作。畫面尚未確認的地方
以註記保留，正式頁面完成後再依實際畫面補圖和按鈕名稱。

## 1. 新人報到：建立帳號並交付臨時密碼

**User story**

- 角色：系統管理者 `admin`
- 情境：新人加入示範廠擴建機電工程，尚未有系統帳號
- 目標：建立帳號、交付臨時密碼，並讓新人進入需要的專案工作

**現場故事**

新人第一天到職，管理者先依工作內容選「現場查核」，建立帳號並抄下
臨時密碼。職務是引導建立流程的選項，不會直接存成一組權限；完成後，
管理者再依實際工作設定權限和專案角色。

**操作步驟**

1. 開啟 [帳號](/accounts)，進入新增帳號精靈。
2. 依新人工作選「現場查核」。精靈提供系統管理、主管、內業規劃、
   現場查核、外部協作五種職務。
3. 依畫面完成帳號資料並建立帳號，抄下畫面提供的臨時密碼。
4. 開啟新人需要加入的專案成員頁（`/projects/:id/members`），加入帳號並
   指派合適的專案角色。

**為什麼這樣設計**

先用工作內容帶入建立流程，降低理解門檻；職務選項不會自動給權限，
避免新人因為選了職務就得到不需要的功能。權限和專案角色分開設定，
管理者可以只開通新人實際需要的範圍。

## 2. 主管看進度：只看工作狀態

**User story**

- 角色：主管 `demo-manager`
- 情境：主管要掌握示範廠擴建機電工程的任務進度
- 目標：找出待處理工作，不查看照片或查核結果

**現場故事**

主管登入後先看總覽，了解哪個專案有待開始或進行中的任務，再查看任務
狀態、地點和指派資訊。這個示範帳號沒有加入專案，所以不會看到「專案」；
若日後成為專案成員並取得相應權限，才會出現該導覽項目。

**操作步驟**

1. 開啟 [總覽](/overview)。
2. 從可查看的專案進度進入示範廠擴建機電工程。
3. 查看任務清單與任務明細中的狀態、地點和指派資訊。
4. 回到總覽比較各專案的進度；照片和查核結果不會顯示。

**為什麼這樣設計**

主管只需要用來安排工作的進度資訊。把照片、查核結果和管理入口留給有
相應權限的人，可以避免不必要的資料曝光，也不會讓主管遇到點進去才被
拒絕的入口。

## 3. 外部協作：唯讀查看加入的專案

**User story**

- 角色：外部協作 `demo-consultant`
- 情境：外部協作要查看示範廠擴建機電工程的查核項目
- 目標：唯讀查看已加入的專案，不瀏覽其他專案或範本庫

**現場故事**

外部協作登入後只看到自己已加入的專案，專案內容是唯讀。帳號雖有
`template.use`，但「專案查閱人員」角色不能編輯查核項目，因此看不到
套用範本的按鈕，也不能套用範本。「範本」導覽同樣不會出現。

**操作步驟**

1. 開啟 [專案](/projects)，確認清單只列出已加入的專案。
2. 開啟示範廠擴建機電工程的查核項目頁。
3. 在查核項目頁唯讀查看內容；看不到套用範本的按鈕，也不會看到其他專案。

<!-- 截圖：外部協作唯讀的專案查核項目頁，帳號 demo-consultant -->
<!-- 待確認畫面：查核項目頁的唯讀呈現，以及套用範本按鈕是否完全隱藏。 -->

**為什麼這樣設計**

套用範本會修改專案查核項目，因此除了 `template.use`，也需要該專案
具備編輯查核項目的角色。外部協作的「專案查閱人員」角色是唯讀，不能
套用範本。只有「管理範本庫」權限或系統管理者能看到「範本」導覽；此
規則待 #705 合併後生效。內業工程師具備適當專案角色時仍可在專案內套用。

## 4. 看不到任務：查原因並一鍵補上

**User story**

- 角色：系統管理者 `admin`
- 情境：內業同事回報看不到示範廠擴建機電工程的查核任務
- 目標：找出缺少的設定，只補上完成工作所需的一層

**現場故事**

管理者開啟同事的帳號詳情，使用「為什麼不能做」查看原因。結果指出
該帳號已有查核權限，但還缺少這個專案的角色。確認同事確實需要執行後，
管理者一鍵補上，其他權限不會跟著改變。

**操作步驟**

1. 開啟 [帳號清單](/accounts)，選取回報問題的帳號。
2. 在帳號詳情開啟「為什麼不能做」，查看查核任務受阻的原因。
3. 確認缺少的是該專案的角色後，選「一鍵補上」。
4. 重新查看原因說明，確認需要的設定已補上。

**為什麼這樣設計**

先說明哪一層不足，再讓管理者確認後補上，可以避免盲目重設權限。
一鍵補上只處理診斷指出的缺項，不會順便擴大其他專案或功能的權限。

## 5. 委派同事代管：只交出範本授權工作

**User story**

- 角色：系統管理者 `admin` 與委派者 `demo-template-delegate`
- 情境：管理者要把範本授權工作交給同事
- 目標：讓同事替他人開通或收回範本權限，不授予管理身分或範本編輯能力

**現場故事**

`demo-template-delegate` 已有範本授權委派。管理者確認範圍後，委派者
登入並直接進入「帳號」，替其他帳號處理範本權限；她不能替自己開通權限、
轉交委派，也不能編輯範本。

**操作步驟**

1. 管理者開啟 [帳號](/accounts)，確認 `demo-template-delegate` 的授權
   範圍只有範本。
2. `demo-template-delegate` 登入後開啟 [帳號](/accounts)，選取其他帳號，
   只處理範本權限。
3. 確認委派者不能替自己授權、不能轉委派，也沒有範本編輯能力。

**為什麼這樣設計**

委派只交出範本授權工作，不會附帶範本編輯能力，也不能自行擴大
委派範圍。委派者直接看到唯一可用的「帳號」入口，不會走進其他管理頁。

## 6. 離職停用：保留紀錄並停止登入

**User story**

- 角色：系統管理者 `admin`
- 情境：一名同仁離職，不再需要使用系統
- 目標：停用帳號，保留既有紀錄

**現場故事**

管理者在帳號清單找到離職同仁，停用他的帳號。停用後不再讓該帳號登入；
過去參與的專案與操作紀錄仍可追查。

**操作步驟**

1. 開啟 [帳號](/accounts)，找到離職同仁的帳號。
2. 開啟帳號詳情，確認選到正確的帳號。
3. 停用帳號，並確認狀態已更新。

停用可阻止離職帳號繼續使用系統，同時保留原有資料與紀錄，方便追溯。

## 7. 修改角色前先看持有人數

**User story**

- 角色：系統管理者 `admin`
- 情境：管理者要調整「現場工程師」角色的內容
- 目標：先了解有多少專案成員使用這個角色，再決定是否修改

**現場故事**

角色定義會影響使用它的專案成員。管理者先到「角色」頁查看「現場工程師」
的持有人數，再評估修改範圍；若人數或影響不清楚，就先確認受影響的專案，
不直接儲存變更。

**操作步驟**

1. 開啟 [角色](/roles)，找到「現場工程師」。
2. 修改前先讀取畫面顯示的持有人數。
3. 確認影響範圍後再調整角色，並確認畫面顯示的角色內容。

<!-- 截圖：專案角色與持有人數，帳號 admin -->
<!-- 待確認畫面：角色列表的持有人數欄位、編輯入口、修改前影響提示與儲存確認文字。 -->

**為什麼這樣設計**

角色定義會套用在多個專案。修改前先看持有人數，能讓管理者先評估影響，
避免把只針對一位成員的調整誤做成全系統角色變更。
