**代碼**：`STM`　**Phase**：P4、P6、P7、P9　**狀態**：草稿
**前置規格**：[domain-model](../domain-model/spec.md)、[api-conventions](../api-conventions/spec.md)

**被擋議題**：[OQ-09](../../intents/05-open-questions.md#oq-09)、[G-05](../../intents/05-open-questions.md#g-05)、[G-06](../../intents/05-open-questions.md#g-06)、[G-07](../../intents/05-open-questions.md#g-07)

## 目的

定義 `Inspection Plan`、`Inspection Task`、`Evidence` 與 `Report` 的狀態和轉換邊界，讓後端能一致地驗證業務動作並保留可追溯紀錄（依據：架構基準 §18、§20.6–20.8、§20.17；[PR-16](../../intents/02-principles.md#pr-16)）。本文件仍為草稿；未裁定的業務規則以待決題標示，不作為凍結規格。

## 範圍

**包含**：

- 四種實體的狀態、建議轉換、失敗／作廢／更正的表示方式。
- 狀態轉換由後端 Service 層控制的介面邊界。
- `Inspection Plan`、`Inspection Task`、`Evidence` 與 `Report` 狀態機之間已確定的關係。

**不包含**：

- 實體欄位、關聯與完整資料模型（由 [domain-model](../domain-model/spec.md) 負責）。
- API 的共通格式（由 [api-conventions](../api-conventions/spec.md) 負責）。
- 建立計畫與任務的完整流程、指派及產生規則（由 `inspection-planning` 規格負責）。
- 證據上傳、刪除 API、保留期限及實體刪除政策（受 [G-05](../../intents/05-open-questions.md#g-05) 阻擋；相關功能由 `field-evidence` 規格負責）。
- 報告欄位、版次治理與輸出內容（由 `report-delivery` 規格負責；其中狀態和快照邊界受 [G-06](../../intents/05-open-questions.md#g-06)、[G-07](../../intents/05-open-questions.md#g-07) 阻擋）。

## 使用情境

- 內業人員建立並啟動計畫，系統依任務狀態更新計畫進度。
- 現場人員開始、完成任務並提交查核資料；完成後若只需修正資料，任務仍維持完成。
- 內業人員修改專案查核項目時選擇是否重查；系統保留作廢任務與資料供查閱，並從報告使用的資料中排除作廢資料。
- 內業人員產製並核發報告；產製失敗時可辨認失敗並依裁定流程重試，已核發版次不被後續異動覆蓋。
- 使用者透過明確的業務動作要求狀態轉換，後端拒絕不合法的轉換。

## 資料

- `Inspection Plan`、`Inspection Task`、`Evidence`、`Report` 的屬性與關聯由 [domain-model](../domain-model/spec.md) 定義；本規格只定義其狀態行為。
- 建立 `Inspection Task` 時保存 `Task Requirement Snapshot`；不得為 `Inspection Template` 新增版本實體或狀態（[PR-04](../../intents/02-principles.md#pr-04)、[KD-03](../../intents/03-decisions-and-stack.md#kd-03)）。
- `Evidence` 的照片內容依 [PR-05](../../intents/02-principles.md#pr-05) 保存為現場版與內業版；證據刪除與保留政策尚受 G-05 阻擋。
- `Report` 作為持久化版本實體保存資料快照；具體快照時間點和草稿版次邊界待 G-07 裁定（[PR-06](../../intents/02-principles.md#pr-06)）。

## 狀態與轉換

以下為規格草案。來源確認的規則標為「已裁定」；英文狀態名或轉換細節若為本規格的技術提案，皆明示為「依業界做法提出、非負責人裁定」。原因：以清楚、可驗證的狀態表達建立、執行、完成及終止／失敗流程，同時保留後續依情境對答調整的空間。

### Inspection Plan

OQ-09 暫列 `DRAFT`、`READY`、`IN_PROGRESS`、`COMPLETED`、`ARCHIVED`。目前只有「所有任務完成即自動完成、不得手動改狀態」已裁定，其餘為暫定候選狀態，不代表已批准轉換（[OQ-09](../../intents/05-open-questions.md#oq-09)、[KD-42](../../intents/03-decisions-and-stack.md#kd-42)）。

| 目前狀態 | 動作與後續狀態 | 觸發者 | 裁定／提案及說明 |
|---|---|---|---|
| `DRAFT` | 設定完成 → `READY` | 內業人員（提案） | 技術提案，待 SM-Q01；是否需 READY 階段待確認。 |
| `READY` | 開始執行 → `IN_PROGRESS` | 內業人員（提案） | 技術提案，待 SM-Q01；代表計畫已可執行。 |
| `IN_PROGRESS` | 所有任務完成 → `COMPLETED` | 系統 | 已裁定：系統自動轉換，不提供人員手動改狀態（KD-42）。 |
| `COMPLETED` | 封存 → `ARCHIVED` | 內業人員（提案） | 技術提案，待 SM-Q02；是否需要封存及誰能操作待確認。 |

候選流程：`DRAFT → READY → IN_PROGRESS → COMPLETED → ARCHIVED`。最後一步及 `DRAFT`／`READY` 是否必要均未裁定。取消、暫停、重開及任務未完成時的計畫處理列為 SM-Q01、SM-Q02。

### Inspection Task

OQ-09 暫列 `PENDING`、`IN_PROGRESS`、`COMPLETED`，並將 `CANCELLED`、`REOPENED` 列為選配；只有已完成後可更正仍維持完成、以及 KD-55 標準變更作廢規則已裁定（[OQ-09](../../intents/05-open-questions.md#oq-09)、[KD-42](../../intents/03-decisions-and-stack.md#kd-42)、[KD-55](../../intents/03-decisions-and-stack.md#kd-55)）。

| 目前狀態 | 動作與後續狀態 | 觸發者 | 裁定／提案及說明 |
|---|---|---|---|
| `PENDING` | 開始作業 → `IN_PROGRESS` | 現場人員（提案） | 技術提案，操作者範圍待 SM-Q12；表示任務開始執行。 |
| `IN_PROGRESS` | 完成查核 → `COMPLETED` | 現場人員（提案） | 技術提案，操作者範圍待 SM-Q12；後端必須覆核完成條件（PR-01），並驗證每筆結果符合 KD-54 的必填規則（STM-R10）。是否有「不符合」就不能完成 Task 尚未裁定，待 SM-Q15；不得以標準值自動判定結果（KD-37、KD-54）。 |
| `COMPLETED` | 更正內容 → `COMPLETED` | 現場人員或內業人員 | 已裁定：更正不重新查核、不退回待確認；留下修正紀錄（KD-42）。 |
| 任一使用被修改項次的任務 | 內業選擇「要」重新查核 → 作廢舊任務 | 內業人員 | 已裁定；須先詢問並清楚警告舊查核作廢及任務改為「尚未查核」。舊任務整份保留、標示「標準變更作廢」，不納入報告；重查是原任務重來或另建任務未定（KD-55、OQ-09）。 |
| 任一使用被修改項次的任務 | 內業選擇「不要」重新查核 → 狀態不變 | 內業人員 | 已裁定：只更正文字，不動結果、照片；記錄更正（KD-55）。 |
| `PENDING`／`IN_PROGRESS`／`COMPLETED` | 取消、重開或其他原因作廢 | 角色待決 | 不推定這些轉換已允許；角色及規則待 SM-Q04、SM-Q05、SM-Q12。 |

將標準變更作廢視為終止舊任務的獨立結果，是本規格提出的建議；具體表示可為終止狀態或作廢標記，待 SM-Q03 決定。原因是 KD-55 要求舊任務保留且報告排除，必須能區分作廢紀錄與可供報告使用的任務。

### Evidence

Evidence 照片保存現場版與內業版，不保存原圖或編輯中間圖（[PR-05](../../intents/02-principles.md#pr-05)）。來源尚未裁定 Evidence 的狀態集合、刪除及保留期限（[OQ-09](../../intents/05-open-questions.md#oq-09)、[G-05](../../intents/05-open-questions.md#g-05)）。

| 階段／狀態 | 動作與後續階段 | 觸發者 | 裁定／提案及說明 |
|---|---|---|---|
| 尚未保存 | 開始上傳 → 上傳中 | 現場人員（提案） | 上傳中階段是技術提案；角色和上傳前檢查待 SM-Q13。 |
| 尚未保存 | 上傳非照片 Evidence → 已保存 | 現場人員（提案） | 通用 Evidence 狀態與角色沒有完整來源定義；此為狀態提案，待 SM-Q13；須維持可沿 Task Requirement Snapshot／Task／Plan／Project 回溯（PR-07）。 |
| 尚未保存 | 上傳照片並確認 → 現場版已保存 | 現場人員（照片；依 PR-05） | 現場人員得有限度編修並確認後保存現場版；階段名稱與上傳失敗補償方式為技術提案，待 SM-Q13。 |
| 上傳中 | 上傳失敗 → 上傳失敗待處理／重試 | 系統記錄；重試者待決 | 為追蹤失敗提出的技術狀態，非來源已裁定；重試與不完整檔案處理待 SM-Q13。 |
| 上傳失敗待處理 | 重試上傳 → 上傳中 | 操作者待決 | 技術提案；角色、錯誤資訊保留與重試限制待 SM-Q13。 |
| 現場版已保存 | 開始加入現場與查核資訊 → 內業版產製中 | 內業系統 | 系統取得現場版並準備內業版（PR-05）；中間階段名稱是技術提案，非已裁定狀態。 |
| 內業版產製中 | 產製完成 → 內業版已保存 | 內業系統 | 系統加入資訊後保存內業版（PR-05）；產製失敗狀態與重試方式是技術提案，待 SM-Q13。 |
| 內業版產製中 | 產製失敗 → 內業版產製失敗 | 內業系統 | 失敗狀態是為追蹤產製問題提出的技術提案，非 PR-05 裁定；記錄方式待 SM-Q13。 |
| 內業版產製失敗 | 重試產製 → 內業版產製中 | 操作者待決 | 技術提案；重試權限與不完整檔案清理方式待 SM-Q13。 |
| 現場版已保存 | 更正現場照片 → 更新唯一現場版 | 現場人員 | 得有限度編修並確認；仍只保存一張現場版，不保存原圖或中間版本（PR-05）。 |
| 內業版已保存 | 更正內業照片 → 更新同一張內業版 | 內業人員 | 得編修並直接更新內業版，不另增版本或中間檔（PR-05）；更正是否需原因及額外紀錄待 SM-Q13。 |
| 任一已保存證據 | 任務依 KD-55 作廢 → 保留但排除於新報告 | 系統依內業人員的重查選擇 | 已裁定適用於作廢任務中的證據；獨立 Evidence 狀態表示待 SM-Q07；舊任務照片、結果與標準不得刪除且內業可找回。 |
| 任一已保存證據 | 刪除、撤回、保留期限到期 | 觸發角色與政策待決 | 不提出可執行的刪除轉換；見 G-05、SM-Q07。 |
| 已保存的非照片 Evidence | 更正內容 → 原狀態或更正待確認 | 操作者待決 | 不預設原地更正或另建紀錄；規則待 SM-Q13。 |

「上傳中」「上傳失敗待處理」「已保存」「現場版已保存」「內業版產製中／失敗」是描述階段的技術提案，不是來源已裁定的 Evidence 狀態值。Evidence 照片更正須依 PR-05 保持每張照片僅有現場版及內業版；非照片 Evidence 的更正方式待 SM-Q13。是否以任務關聯判斷可用性、另設狀態或採刪除標記，待 SM-Q07；上傳／內業版產製失敗如何復原待 SM-Q13，不以此表繞過 G-05。

### Report

G-06 對 §20.6 和 §20.17 的狀態清單存在差異；G-07 對快照時點、Preview／草稿重產與版次界線存在缺漏。以下並列來源，不合併成單一既定狀態機。

| 來源 | 狀態／流程 | 來源所述 |
|---|---|---|
| 架構基準 §20.6（G-06 立場 A） | `DRAFT`、`GENERATED`、`UNDER_REVIEW`、`APPROVED`、`ISSUED`、`SUPERSEDED`、`VOID` | `Report Status` 列舉；表格未列 `issue_date` 或 `document_status` 欄位。 |
| 架構基準 §20.17（G-06 立場 B） | `DRAFT → GENERATING → GENERATED`；失敗為 `GENERATION_FAILED` | 以中間及失敗狀態表達產製交易邊界。 |
| 架構基準 §20.7／§20.13／§20.16–20.18（G-07） | 產製時取得快照、Preview 與草稿可重產的邊界未明 | 已核發版次不因現場資料異動而改變；後續應產生新版次。 |

下表是供決策討論的完整轉換草案。除產製中／失敗及核發版次不可覆蓋的來源規則外，轉換方式與人員角色均為提案，非負責人裁定；`VOID`／`SUPERSEDED` 是否適用於何種來源狀態也待 SM-Q14。各動作由後端 Service 驗證（PR-16），用戶端不能直接寫入狀態。

| 目前狀態 | 動作與後續狀態 | 觸發者 | 裁定／提案及說明 |
|---|---|---|---|
| `DRAFT` | 開始產製 → `GENERATING` | 有產製權限的內業人員（提案） | 技術提案；角色、Preview 與快照時點待 SM-Q09、SM-Q14。 |
| `GENERATING` | 產製成功 → `GENERATED` | 系統 | 技術流程提案；不得在產製完成前誤標為 `GENERATED`（PR-15）。 |
| `GENERATING` | 任一步驟失敗 → `GENERATION_FAILED` | 系統 | PR-15 要求表達失敗並保存錯誤資訊；跨檔案／資料庫復原及重試方式待 SM-Q10。 |
| `GENERATION_FAILED` | 重試 → `GENERATING` | 有產製權限的內業人員（提案） | 技術提案；同一 Report 或新產製嘗試待 SM-Q10、SM-Q14。 |
| `GENERATED` | 送審 → `UNDER_REVIEW` | 報告承辦人（提案） | 狀態取自 §20.6；提交條件與角色待 SM-Q14。 |
| `UNDER_REVIEW` | 核准 → `APPROVED` | 審查者（提案） | 狀態取自 §20.6；審查權限、退回及再次送審路徑待 SM-Q14。 |
| `UNDER_REVIEW` | 退回修正 → `GENERATED` | 審查者（提案） | 技術提案，非來源已定義轉換；退回原因、修改後再送審方式及快照是否更新待 G-07、SM-Q14。 |
| `APPROVED` | 核發 → `ISSUED` | 核發者（提案） | 狀態取自 §20.6；核發權限與文件編號／日期待 SM-Q14。 |
| `ISSUED` | 新版核發 → 舊版 `SUPERSEDED` | 系統依核發者的新版本動作 | 已核發版次不得覆蓋，應產生新版次（PR-06）；舊版狀態表示及建立新版的時點待 G-06／G-07、SM-Q14。 |
| `DRAFT`／`GENERATED`／`UNDER_REVIEW`／`APPROVED` | 作廢 → `VOID` | 有作廢權限的內業人員（提案） | 狀態取自 §20.6；適用條件、權限、原因及可否恢復待 G-06、SM-Q14。 |
| `ISSUED` | 撤銷／作廢 → `VOID` | 有核發撤銷權限者（角色提案） | 是否允許核發後作廢，以及如何保留交付紀錄，待 G-06、SM-Q14；不得藉狀態轉換覆蓋已核發檔案（PR-06）。 |
| `SUPERSEDED`／`VOID` | 無後續轉換（終止狀態提案） | 不適用 | 是否允許恢復或撤銷終止狀態待 G-06、SM-Q14。 |

**暫定建議（待 G-06／G-07 裁定，非負責人裁定）**：採用上表作為提案流程，並保留所有來源狀態概念；產製失敗須保留錯誤資訊，已核發版次不可覆蓋。此建議同時表達 §20.6 的審查／版次生命週期及 §20.17 的產製失敗路徑，避免漏記任一來源要求；狀態清單、轉換、角色及快照邊界均待裁定。來源差異詳列於上表和 SM-Q08、SM-Q09、SM-Q14。

## 待釐清

以下 SM-Q 題目是情境對答題，供負責人逐題確認；候選答案及影響均非本規格裁定。

### SM-Q01：計畫何時從草稿進入可執行狀態？

- **情境**：計畫已建立，但查核項目或任務尚未全部準備完成。
- **選項**：A. 建立後即可開始，省去 `READY`；B. 必須由內業明確確認後才可開始；C. 由第一個任務開始自動進入執行中。
- **影響**：決定是否保留 `READY`、誰能啟動，以及未準備完成的計畫能否產生任務。依據：[OQ-09](../../intents/05-open-questions.md#oq-09)。

### SM-Q02：計畫是否需要封存、取消或暫停？

- **情境**：計畫已完成或暫時不會繼續，內業要整理清單。
- **選項**：A. 僅完成，不另設封存／取消／暫停；B. 完成後可封存，保留查詢；C. 可取消或暫停，並定義其下未完成任務如何處理。
- **影響**：決定狀態數量、任務處置與畫面篩選；若允許取消／暫停，須指定角色與恢復方式。依據：[OQ-09](../../intents/05-open-questions.md#oq-09)。

### SM-Q03：KD-55 作廢後如何重新查核？

- **情境**：內業選擇標準變更後重新查核，原任務及其查核資料已作廢保留。
- **選項**：A. 同一 Task 回到待查核狀態；B. 保留舊 Task 並建立新 Task，兩筆以重查關聯；C. 其他流程。
- **影響**：A 需界定舊快照、結果及照片如何完整保留；B 需建立任務關聯並讓內業能同時找到新舊任務。OQ-09 與 KD-55 明確把此題留給 0.4.x 規格設計。推薦先採 B 作技術提案：以新任務承接新標準，舊任務保持不可改寫且可追溯；此建議依業界常見歷史保留做法提出，非負責人裁定。

### SM-Q04：現場是否能取消尚未完成的任務？

- **情境**：任務已建立，但現場確認該工作不需執行。
- **選項**：A. 不可取消，由內業調整計畫；B. 現場可提出取消、內業核准；C. 有指定權限者可直接取消並填原因。
- **影響**：決定誰能改變工作範圍、是否要記錄原因，以及計畫全部任務完成的判定方式。依據：[OQ-09](../../intents/05-open-questions.md#oq-09)。

### SM-Q05：已完成任務在何種情況可重新開啟？

- **情境**：發現資料錯誤或查核需要補做。
- **選項**：A. 完成後永不重開，資料更正維持完成；B. 只有內業可以重開並記錄原因；C. 依錯誤類型決定更正或重查。
- **影響**：A 最符合 KD-42 已裁定的更正路徑；其他選項需界定何者是更正、何者推翻查核，以及 Plan 完成後的狀態回復。KD-42 不允許一般更正造成重開；此題只問其他尚未裁定的重查情境。依據：[KD-42](../../intents/03-decisions-and-stack.md#kd-42)、[OQ-09](../../intents/05-open-questions.md#oq-09)。

### SM-Q06：任務完成失敗如何表示與重試？

- **情境**：完成動作部分寫入失敗，或後端覆核發現必要資料不足。
- **選項**：A. 維持原狀並讓使用者修正後重試；B. 顯示可修正的原因並保留未完成資料；C. 另記失敗狀態與人工處理流程。
- **影響**：決定使用者看到的結果、資料回復方式及是否需要失敗狀態；不得讓前端單方面顯示完成。依據：[PR-01](../../intents/02-principles.md#pr-01)、[PR-16](../../intents/02-principles.md#pr-16)、[OQ-09](../../intents/05-open-questions.md#oq-09)。

### SM-Q07：Evidence 如何表示撤回、刪除及作廢關聯？

- **情境**：使用者要求移除證據，或證據所屬任務因標準變更作廢。
- **選項**：刪除流程可選 A. 不提供獨立刪除，只在關聯任務作廢時排除；B. 使用者可提出刪除申請、內業核准後軟刪除；C. 內業可直接軟刪除，已被報告引用時改為封存。另須決定保留期限與核准角色。
- **影響**：決定誰能提出／執行刪除、證據能否取回、報告引用處理與儲存成本；必須先一併裁定 G-05 的刪除 API、報告引用限制與保留期限。此題不預設任何 Evidence 硬刪除行為。依據：[G-05](../../intents/05-open-questions.md#g-05)、[OQ-09](../../intents/05-open-questions.md#oq-09)、[KD-55](../../intents/03-decisions-and-stack.md#kd-55)。

### SM-Q08：Report 產製與審查狀態採哪一份清單？

- **情境**：Report 產製成功後要送審／核准／核發，或產製中發生錯誤。
- **選項**：A. 採 §20.6 列舉；B. 採 §20.17 的產製中與失敗狀態並補上審查狀態；C. 合併兩者並重新命名／精簡。
- **影響**：決定狀態欄位、重試行為、審查權限與版本治理；§20.6 和 §20.17 的差異如上表，須由團隊裁定，不以本規格的整併建議代替決議。依據：[G-06](../../intents/05-open-questions.md#g-06)。

### SM-Q09：Report 草稿、Preview 與正式版何時固定快照及版次？

- **情境**：同一份草稿再次預覽或產製，期間現場資料已更新；或已核發報告後又有資料異動。
- **選項**：A. 每次預覽可重用同一草稿並重產，核發時才建立固定版次；B. 每次產製就建立新 Report 與快照，Preview 只查看該快照；C. DOCX／PDF 共用固定快照，但另訂草稿更新規則。
- **影響**：決定草稿能否覆寫、Preview 是否形成版次，以及 DOCX／PDF 是否一致。已核發版次不可被覆蓋；其餘邊界未定。依據：[G-07](../../intents/05-open-questions.md#g-07)、[PR-06](../../intents/02-principles.md#pr-06)。

### SM-Q10：報告產製失敗由誰重試，何時停止？

- **情境**：產製因轉檔或儲存失敗，Report 留有失敗記錄。
- **選項**：A. 有權限的內業人員可重試同一草稿；B. 每次重試建立新產製嘗試但保留 Report；C. 超過次數後由管理者處理。
- **影響**：決定重試是否覆蓋產物、錯誤記錄保存方式、操作者與重試上限。應保留失敗追蹤；具體政策待 G-06／G-07 裁定後確認。依據：[PR-15](../../intents/02-principles.md#pr-15)、[G-06](../../intents/05-open-questions.md#g-06)、[G-07](../../intents/05-open-questions.md#g-07)。

### SM-Q11：誰能建立、啟動、封存或取消 Inspection Plan？

- **情境**：計畫已建立或完成，使用者要開始執行、暫停後恢復、封存或取消。
- **選項**：A. 由內業人員啟動／封存，取消另需主管核准；B. 由具專案管理權限者執行全部操作；C. 啟動由首個 Task 自動觸發，封存／取消由內業人員提出並由主管核准。
- **影響**：決定 Plan 各轉換的操作者、授權檢查及未完成 Task 的處理；「所有 Task 完成時系統自動完成且不得手動改 Plan 狀態」仍依 KD-42，不受此題改動。依據：[KD-42](../../intents/03-decisions-and-stack.md#kd-42)、[OQ-09](../../intents/05-open-questions.md#oq-09)。

### SM-Q12：誰能開始、完成、取消或重開 Inspection Task？

- **情境**：現場開始查核、提交完成，或有人要求取消／重開任務。
- **選項**：A. 指派的現場人員可開始及提交完成，取消／重開由內業核准；B. 專案內任何現場人員可執行，內業可取消／重開；C. 依角色權限設定，但完成後只有 KD-42 明定的更正可維持完成，不因此重開。
- **影響**：決定任務責任歸屬、未指派任務是否可作業，以及重開是否改變 Plan 完成狀態；完成與更正仍由後端覆核。依據：[PR-01](../../intents/02-principles.md#pr-01)、[PR-16](../../intents/02-principles.md#pr-16)、[KD-42](../../intents/03-decisions-and-stack.md#kd-42)、[OQ-09](../../intents/05-open-questions.md#oq-09)。

### SM-Q13：Evidence 上傳、照片更正與內業版產製失敗怎麼處理？

- **情境**：現場上傳或保存 Evidence 失敗、內業系統產製內業版失敗，或使用者要更正已保存 Evidence。
- **選項**：A. 上傳／產製失敗可由原操作者重試，系統保留錯誤與未完成階段；B. 失敗後由內業人員重新發起，系統清理不完整產物後重做；C. 失敗記錄保留供管理者處理，使用者不得自行重試。照片更正方面，現場人員確認後更新唯一現場版；內業人員更正則直接更新唯一內業版，均不保留原圖或編輯中間圖（此照片保存規則已由 PR-05 裁定）。非照片 Evidence 更正可選：A. 原地更正並留修改紀錄；B. 保留原值、另新增更正紀錄；C. 不允許更正，改作廢並建立新 Evidence。
- **影響**：決定失敗復原、重試權限、不完整檔案清理方式及非照片 Evidence 更正範圍；不得因重試另存照片原圖／中間圖，也不得把內業照片更正誤做成新增版本。非照片更正的選擇會影響歷史追溯與報告使用哪一筆資料。依據：[PR-02](../../intents/02-principles.md#pr-02)、[PR-05](../../intents/02-principles.md#pr-05)、[PR-07](../../intents/02-principles.md#pr-07)、[PR-08](../../intents/02-principles.md#pr-08)、[G-05](../../intents/05-open-questions.md#g-05)、[OQ-09](../../intents/05-open-questions.md#oq-09)。

### SM-Q14：誰能送審、核准、核發、作廢 Report？已核發報告能否作廢？

- **情境**：Report 產製完成後要送審、核准、核發；或使用者要作廢報告／建立新版。
- **選項**：A. 承辦人送審、不同的審查者核准、核發者簽發；已核發報告只可由新版取代，不允許作廢。B. 具報告管理權限的內業人員可處理送審至核發；已核發報告可由主管作廢，但保留原交付檔與原因。C. 由專案設定角色矩陣分別授權上述動作，並另外裁定核發後作廢及其留存方式。
- **影響**：決定各轉換操作者、是否需職務分離、核發後作廢與恢復權限；已核發版次不可覆蓋，但新版建立時點仍待 G-07。各角色配置均為情境選項，非本規格裁定。依據：[G-06](../../intents/05-open-questions.md#g-06)、[G-07](../../intents/05-open-questions.md#g-07)、[PR-06](../../intents/02-principles.md#pr-06)。

### SM-Q15：含「不符合」結果時，Task 何時可完成？

- **情境**：Task 的一個或多個查核項次已選「不符合」，並已填嚴重度、註解及所有適用的實測欄位；後端正覆核完成請求。
- **選項**：A. 三種結果皆可，在各自 KD-54 必填資料完整時允許完成；B. 含任何「不符合」即不得完成，須待改善或複查；C. 可完成，但依嚴重度門檻或指定角色覆核後完成。以上均為待裁定選項，非本規格規則。
- **影響**：決定 Plan 自動完成是否可包含有不符合項次的 Task、現場完成流程及是否需改善追蹤／額外核准。KD-54 已規定每筆結果的必填欄位，但明確未裁定嚴重度對 Task 完成判定的影響；亦不得推導「不符合」必然阻止完成。系統不得依標準值自動判定結果（KD-37、KD-54）。依據：[KD-54](../../intents/03-decisions-and-stack.md#kd-54)、[KD-37](../../intents/03-decisions-and-stack.md#kd-37)、[PR-01](../../intents/02-principles.md#pr-01)、[OQ-06](../../intents/05-open-questions.md#oq-06)。
