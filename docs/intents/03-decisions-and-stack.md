## 關鍵決策

<a id="kd-01"></a>
## KD-01：外部用戶端只透過後端 API 存取資料

- **決策**：Field Web、Admin Web 等外部用戶端**必須**經後端 API 讀寫資料；前端**不得**直接連資料庫或檔案儲存。後端 Report Service 可直接使用服務、資料存取與儲存介面，不必呼叫自己的 HTTP API。見 [PR-01](02-principles.md#pr-01)。
- **狀態**：已決定。
- **考慮過但沒選**：前端直接連資料庫或組出儲存路徑。
- **為什麼選這個**：權限、驗證與業務規則集中在後端；換資料庫時，前端契約可維持穩定。
- **代價**：外部存取要先定義 API；後端要維護 API 契約。
- **什麼情況要重新討論**：新增獨立外部服務，且現有 API 無法滿足資料交換需求時，檢查 API 契約與授權邊界；前端禁直連的要求仍有效。
- **依據**：架構基準 §2.2、§20.2、§37 ADR-002。

<a id="kd-02"></a>
## KD-02：照片檔案與關聯式資料分開存放

- **決策**：資料庫保存 Evidence metadata；檔案存入 Storage。後端產生 storage key，不以原始檔名當唯一識別。業務邏輯經 Storage 介面讀寫檔案。見 [PR-02](02-principles.md#pr-02)。
- **狀態**：已決定。
- **考慮過但沒選**：照片以 BLOB 放進 SQLite；原始檔名直接當 storage key。
- **為什麼選這個**：照片是容量主因；分開存放可控制資料庫大小，並保留物件儲存遷移路徑。
- **代價**：檔案與資料庫需要配對備份，也要處理兩邊寫入失敗。照片只保存現場版與內業版兩張，見 [KD-32](#kd-32)、[G-02](05-open-questions.md#g-02)（已裁定）。
- **什麼情況要重新討論**：本機檔案容量、備份或存取需求超出單機能力時，評估 MinIO、S3 或 NAS；Storage 介面仍維持。
- **依據**：架構基準 §2.3、§7.4、§13.1–13.2、§33、§37 ADR-004。

<a id="kd-03"></a>
## KD-03：範本版本化，任務建立時固定需求

- **決策**：`Inspection Template` **必須**版本化。建立 `Inspection Task` 時，**必須**把當時的需求固定為 `Task Requirement Snapshot`。後續範本異動不得改寫舊任務的需求。見 [PR-04](02-principles.md#pr-04)。
- **狀態**：已決定。
- **考慮過但沒選**：任務每次查詢都讀範本的目前版本。
- **為什麼選這個**：系統要能回答「任務建立當時要求什麼」。
- **代價**：任務需要自己的需求資料，且要保存來源需求的關聯。
- **什麼情況要重新討論**：若新需求要修改已建立任務，先定義更正或重新建立任務的流程；不能直接改寫歷史快照。
- **依據**：架構基準 §2.5、§12.9、§37 ADR-006。

## KD-04：照片編輯（已由 KD-32、KD-33 取代）

- **決策**：原決策要求照片編輯不得覆蓋原圖、每次編輯另存 `Evidence Variant` 系譜；此設計**已由** [KD-32](#kd-32)、[KD-33](#kd-33) 取代——照片只保存現場版與內業版兩張，不保存原圖，也不保存編輯中間版本。見 [PR-05](02-principles.md#pr-05)。
- **狀態**：已取代（依負責人決定，#90～#91，2026-09-28）。
- **考慮過但沒選**：直接改寫原圖；把物件移除、新增或生成式修圖列為標準功能——這兩項不選的理由仍然成立，延續至 [KD-32](#kd-32)。
- **為什麼選這個**：本卡片保留供追溯舊決策脈絡；現行規則見 [KD-32](#kd-32)、[KD-33](#kd-33)。
- **代價**：無（已由新決策取代，不再是有效規則）。
- **什麼情況要重新討論**：不適用，已被取代。
- **依據**：架構基準 §13A.2–13A.6、§37 ADR-010；已由負責人決定（#90～#91，2026-09-28）取代，見 [G-02](05-open-questions.md#g-02)、[G-03](05-open-questions.md#g-03)。

<a id="kd-05"></a>
## KD-05：DOCX 與 PDF 是 MVP 的正式交付物

- **決策**：MVP **必須**產出 DOCX 與 PDF。報告從後端 Report View Model 和版本化 DOCX 範本產生；HTML 可做預覽，不能取代正式文件。報告需保存範本版本、文件編號、版次、快照、檔案鍵、雜湊與產製資訊。見 [PR-06](02-principles.md#pr-06)。
- **狀態**：已決定；完整核准、簽名與核發流程仍待決議，見 [OQ-07](05-open-questions.md#oq-07)、[G-11](05-open-questions.md#g-11)。
- **考慮過但沒選**：只從 HTML 直接列印 PDF；只提供一次性下載檔。
- **為什麼選這個**：業主、監造與標案文件需要可提交、可歸檔、可追溯的正式產物。
- **代價**：需要管理 DOCX 範本、版面驗收及 PDF 轉換。轉換工具見 [OQ-15](05-open-questions.md#oq-15)。
- **什麼情況要重新討論**：正式收件規範改變，且 DOCX／PDF 不再滿足交付要求時，新增決策並評估舊報告的保存方式。
- **依據**：架構基準 §20.1–20.7、§20.22、§30 Phase 9、§37 ADR-009。

<a id="kd-06"></a>
## KD-06：資料庫存取用 SQLAlchemy，結構演進用 Alembic

- **決策**：資料庫存取**必須**經 SQLAlchemy。Schema 變更**必須**走 Alembic migration。正式環境**不得**靠 `Base.metadata.create_all()` 或未記錄的手動 ALTER 管理版本。見 [PR-03](02-principles.md#pr-03)。
- **狀態**：已決定。
- **考慮過但沒選**：正式環境直接建立表格或手動改 schema；大量使用 SQLite 專用 SQL。
- **為什麼選這個**：把 SQLite 換成 PostgreSQL 時，資料庫差異較容易收斂在資料存取與 migration 層。
- **代價**：每次 schema 變更都要寫、審查及驗證 migration。
- **什麼情況要重新討論**：導入 SQLAlchemy 無法支援的資料庫能力時，記錄相依性並以雙資料庫測試驗證；正式 schema 變更仍需可追蹤。
- **依據**：架構基準 §4.4–4.5、§22A.9、§32、§37 ADR-005。

<a id="kd-07"></a>
## KD-07：主要實體以 UUID 識別

- **決策**：Project、User、Plan、Task、Evidence 等主要實體使用 UUID。UUIDv7 **得**優先評估。人類可讀的業務編號與 UUID 分開保存。
- **狀態**：已決定；UUID 版本待實作選擇。
- **考慮過但沒選**：完全依賴 SQLite AUTOINCREMENT 作為跨系統身分。
- **為什麼選這個**：減少資料合併時撞號的風險，並保留離線用戶端自行產生 ID 的空間。
- **代價**：UUID 較長；畫面與文件還要另外使用可讀的業務編號。
- **什麼情況要重新討論**：離線建立、跨系統合併或排序效能提出具體需求時，選定 UUID 版本與產生位置；不改用自增值作為唯一對外識別。
- **依據**：架構基準 §11、§37 ADR-007。

<a id="kd-08"></a>
## KD-08：MVP 先用單機 SQLite

- **決策**：MVP 使用 SQLite。多台後端**不得**透過網路檔案系統共用同一個 SQLite 檔。連線初始化**應**確認 `foreign_keys = ON` 與 WAL；來源把兩項 PRAGMA 稱為「建議確認」，不是額外的 ADR 強制項。
- **狀態**：已決定；PRAGMA 屬建議設定。
- **考慮過但沒選**：MVP 一開始就維運 PostgreSQL；多台伺服器共用同一個 SQLite 檔。
- **為什麼選這個**：Pilot 規模小、schema 尚在變動，先降低資料庫維運成本。
- **代價**：寫入併發及資料庫維運能力有限；備份須處理 WAL 的一致性。
- **什麼情況要重新討論**：需要第二台後端、同時寫入明顯增加，或備份、鎖定、監控需求超出 SQLite 能力時，轉向 PostgreSQL。
- **依據**：架構基準 §9.1–9.2、§10、§23、§37 ADR-003。

<a id="kd-09"></a>
## KD-09：Pilot 與正式環境採 Linux 和 Docker Compose

- **決策**：Pilot／Production 使用 Linux Server、Docker Engine、Docker Compose 與持久化儲存。正式變更經 Git、審查、CI、版本化 image；migration 必須納入發布流程。見 [PR-13](02-principles.md#pr-13)。
- **狀態**：已決定；migration 與服務啟動的先後順序依 [G-09](05-open-questions.md#g-09) 的裁定，見 [PR-13](02-principles.md#pr-13)。
- **考慮過但沒選**：個人電腦、臨時 VM、沒有持久化磁碟的主機，或第一天就導入多節點編排。
- **為什麼選這個**：開發與正式環境較易重現，也能以固定流程備份、更新及回滾。
- **代價**：Compose 本身不提供多節點協調與自動容錯；部署仍需要維運程序。
- **什麼情況要重新討論**：需要多節點、高可用、自動容錯或大量後端副本時，評估編排平台。部署順序的來源歧義與裁定見 [G-09](05-open-questions.md#g-09)。
- **依據**：架構基準 §22.1–22.7、§22A.7、§22A.19、§37 ADR-011。

<a id="kd-10"></a>
## KD-10：第一版使用模組化單體

- **決策**：第一版只有一個 Backend Application。API、Service、Persistence 與 Storage 保持清楚邊界。見 [PR-11](02-principles.md#pr-11)。
- **狀態**：已決定。
- **考慮過但沒選**：為尚未出現的規模需求先導入微服務、訊息系統或多節點編排。
- **為什麼選這個**：縮短開發與部署路徑，同時保留日後拆分模組的空間。
- **代價**：模組共用部署單位，不能單獨擴充某個模組。
- **什麼情況要重新討論**：特定模組有可量測的獨立擴充、部署或隔離需求時，評估拆分；只因「未來可能變大」不足以拆分。
- **依據**：架構基準 §2.1、§7、§22A.19、§37 ADR-001。

<a id="kd-11"></a>
## KD-11：現場畫面只呈現完成任務所需資訊

- **決策**：Field UI 聚焦「今日任務 → 證據 → 完成」。範本版本、資料庫 ID、storage key 與後台設定不放在現場操作畫面。見 [PR-10](02-principles.md#pr-10)。
- **狀態**：已決定。
- **考慮過但沒選**：把管理及設定功能直接放進現場畫面。
- **為什麼選這個**：降低現場工程師的操作負擔與拍錯需求的機率。
- **代價**：進階設定與例外處理要由 Admin UI 或後端流程承接。
- **什麼情況要重新討論**：Pilot 顯示現場工程師因缺少必要資訊而無法完成任務時，調整呈現內容，但不暴露底層儲存與資料庫細節。
- **依據**：架構基準 §6.1–6.2、§31、§37 ADR-008。

<a id="kd-12"></a>
## KD-12：Admin／Field 共用單一前端程式庫

- **決策**：Admin UI 與 Field UI **必須**放在同一個 React application，以 `/admin/*`、`/field/*` 路由與權限區分；**必須**依路由拆分程式碼，Field 的程式包不得載入 Admin 的模組。
- **狀態**：已決定（團隊於 [#5](https://github.com/speko-tw/inspect-flow/issues/5) 裁定 [OQ-21](05-open-questions.md#oq-21)，採來源 §5.1 的建議）。
- **考慮過但沒選**：同一 repo 內分成兩個 app 加共用套件。
- **為什麼選這個**：一套 build、一條 CI、一次部署；API client、登入與元件共用；符合模組化單體方向（[KD-10](#kd-10)）。
- **代價**：沒有依路由拆分時，Field 會載入 Admin 的程式；日後要拆開需要搬遷。
- **什麼情況要重新討論**：Field PWA 需要獨立發布週期，或兩者差異大到共用成本高於分開維護時，評估拆分。
- **依據**：架構基準 §5.1；團隊裁定 [OQ-21](05-open-questions.md#oq-21)。

<a id="kd-13"></a>
## KD-13：清單端點採 cursor-based 分頁

- **決策**：`/api/v1` 清單端點的分頁**必須**採 cursor-based 分頁，不用 offset/limit。
- **狀態**：已決定。
- **考慮過但沒選**：offset/limit 分頁。
- **為什麼選這個**：現場查核的照片與任務清單偏向捲動瀏覽，cursor-based 分頁在資料持續新增時不會因位移量偏移而跳頁或重複。
- **代價**：不能直接跳到指定頁碼；cursor 的排序鍵必須穩定，見 [KD-14](#kd-14)（時間欄位精度到秒，需搭配 UUID 排序）。
- **什麼情況要重新討論**：後台管理畫面需要「跳到第 N 頁」這類操作時，評估是否額外提供 offset/limit 介面。
- **依據**：負責人決定（PR #30，2026-09-26）；架構基準無對應章節。

<a id="kd-14"></a>
## KD-14：時間欄位採 ISO 8601（RFC 3339）、UTC、精度到秒

- **決策**：API 回應中的時間欄位**必須**使用 ISO 8601（RFC 3339）字串，一律 UTC 並帶 `Z` 後綴，精度到秒（例如 `2026-09-26T08:30:00Z`）。
- **狀態**：已決定；輸入端的解析寬鬆度（是否接受小數秒、`+08:00` 偏移）不在本決策範圍，之後另議。
- **考慮過但沒選**：Unix epoch 數值、毫秒精度、本地時區字串。
- **為什麼選這個**：系統多為人類操作，秒級精度已足夠辨識操作先後，且字串格式比 epoch 對人類判讀與除錯更直接。
- **代價**：同一秒可能有多筆記錄，排序與 cursor 不得只靠時間欄位，必須以「時間＋UUID」為鍵（可評估搭配 [KD-07](#kd-07) 提及的 UUIDv7 提升同秒排序穩定性）。
- **什麼情況要重新討論**：出現需要秒級以下精度才能區分的業務情境（例如高頻自動化寫入）時，重新評估精度。
- **依據**：負責人決定（PR #30，2026-09-26）；架構基準無對應章節。

<a id="kd-15"></a>
## KD-15：`error.code` 採 dot-namespace 命名，對照表由程式列舉自動產生

- **決策**：`error.code` **必須**採 dot-namespace 命名（`<resource>.<reason>`，例如 `task.not_found`）；`error.code` 對照表**必須**由程式的列舉自動產生，不手寫維護獨立文件。不特定於單一資源的跨資源共用錯誤，依錯誤性質分類型 namespace：`request.*`（請求本身的問題，例如 `request.validation_failed`）、`resource.*`（不特定於某資源的通用資源錯誤，例如框架產生的 `resource.not_found`）、`server.*`（伺服器端錯誤，例如 `server.internal_error`）；資源專屬錯誤仍用 `<resource>.<reason>`。
- **狀態**：已決定。
- **考慮過但沒選**：SCREAMING_SNAKE_CASE 全域列舉、泛用少數碼、手寫維護對照表文件。
- **為什麼選這個**：dot-namespace 讓前端能依資源分類做程式化分支；對照表自動產生可避免列舉與文件長期不同步；跨資源共用錯誤依性質分為 `request`／`resource`／`server` 三類，讓歸屬判斷有固定規則可循，不必逐一個案討論。
- **代價**：每個資源都要維護自己的 reason 列舉；新增跨資源共用的錯誤原因時，須先判斷屬於 `request`／`resource`／`server` 三類中的哪一類，而非任意新增 namespace。
- **什麼情況要重新討論**：出現大量跨資源共用、難以歸入單一 `<resource>` 的錯誤原因時，重新評估命名法。
- **依據**：負責人決定（PR #30，2026-09-26）；架構基準無對應章節。

<a id="kd-16"></a>
## KD-16：人員（User）基本欄位，依帳號來源決定可否修改

- **決策**：`User` 的基本欄位為公司、部門、地點、工號、英文姓名、中文姓名、email、啟用狀態；除啟用狀態外皆為必填。本系統建立的帳號，這些欄位由 Admin 修改；外部來源匯入的帳號，任何人都不能修改這些欄位。
- **狀態**：已決定。
- **考慮過但沒選**：無，issue #63 未列出替代方案。
- **為什麼選這個**：這些欄位與可修改性是 `domain-model`、`database-foundation` T4 的前提（依負責人 #63 決定）。
- **代價**：本系統建立的帳號如果之後被外部來源匯入比對到同一個人，原本 Admin 可修改的欄位就會變成不能修改，見 [KD-20](#kd-20) 的比對規則。
- **什麼情況要重新討論**：需要讓特定欄位在外部帳號上也能人工覆寫時，重新評估。
- **依據**：負責人決定（#63，2026-09-26）；取代架構基準 §12.1 的最小欄位假設。

## KD-17：人員聯絡與補充欄位由本人與 Admin 維護，同步不覆蓋

## KD-25：權限模型＝資料 × 動作，系統存權限代碼

- **決策**：權限**必須**表示為「資料 × 動作」：讀取、新增、修改、刪除，再加上特殊動作（例如簽核、匯出列印）；系統存的是權限代碼，例如 `report.read`、`report.approve`。

- **為什麼選這個**：這是 [KD-26](#kd-26) 可自訂角色的資料基礎——角色本質是一組權限代碼的集合，而不是寫死的功能表（依負責人 #63 決定）。

## KD-30：登入採伺服器端 Session 搭配 HttpOnly Cookie

- **決策**：登入**必須**採 Server-managed Session + HttpOnly Cookie，Cookie **必須**加上 Secure、SameSite；**應**避免把長效 JWT 放在 browser localStorage（維持架構基準原本的建議）。
- **狀態**：已決定。
- **考慮過但沒選**：Short-lived Token in HttpOnly Cookie（架構基準 §17 列為「或經團隊評估採用」的選項）。
- **為什麼選這個**：部署是單一伺服器；停用人員時可以立刻讓現有的登入失效（依 [KD-21](#kd-21)），不需要另外做 token 撤銷機制。將來串接外部身分來源（LDAP、AD、Entra ID）時，登入成功後一樣建立伺服器端的 Session，兩者不衝突（依負責人 #82 決定）。

- **什麼情況要重新討論**：部署不再是單一伺服器（例如多台 API 伺服器分流）時，重新評估 Session 的存放位置。
- **依據**：架構基準 §17；在 §17 並列的兩個選項中，由負責人決定（#82，2026-09-26）。

<a id="kd-32"></a>
## KD-32：證據照片只保存現場版與內業版兩張，不保存原圖

- **決策**：現場人員拍照、編修並確認後**必須**存一張「現場版」；內業系統取得現場版、加入現場與查核相關資訊後**必須**存一張「內業版」；內業人員之後**得**再編修內業版，直接更新內業版本身。每筆照片**最終只保存現場版與內業版兩張圖片**，**不得**另外保存原始拍攝檔案，編輯過程中的中間圖片也**不得**保存。見 [PR-05](02-principles.md#pr-05)。
- **狀態**：已決定。
- **考慮過但沒選**：保留原始拍攝原圖，並以 `Evidence Variant`（`ORIGINAL`／`EDITED`）系譜記錄每次編輯（原 [KD-04](#kd-04) 的設計）；較早「保留原圖＋一張最終後製圖」的業務釐清已被本決策取代。
- **為什麼選這個**：現場版與內業版分別代表「現場確認」與「內業整理」兩個階段的最終結果，不需要保留每次編修留下的中間版本或原始拍攝檔案。
- **代價**：原圖一旦被現場版取代就無法回看；[KD-04](#kd-04)、[PR-05](02-principles.md#pr-05) 原有「原圖不可覆寫、每次編輯留系譜」的設計不再適用，已依本決策修訂。
- **什麼情況要重新討論**：若稽核或業主要求保留原始拍攝檔案時，重新評估。
- **依據**：負責人決定（#90，2026-09-28）；取代架構基準 §13A.2、§13A.4 與原 [KD-04](#kd-04) 的原圖保留設計，見 [G-02](05-open-questions.md#g-02)。

## KD-36：查驗項目由內業事先給定，MVP 不以 interval 為必填規則

- **決策**：查驗項目與查驗點**必須**由內業／後台人員依專案需求事先給定；MVP **不**以 `interval`（查核間距）作為每個工項的必填規則，也**不**以「輸入間距後自動切分任務」作為完成查驗的必要流程。見 [PR-09](02-principles.md#pr-09)。
- **狀態**：已決定（方向）。
- **考慮過但沒選**：系統強制所有工項依固定間距自動切分任務。
- **為什麼選這個**：不同工程要求查驗的密度差異很大，由內業依實際需求逐一給定查驗點，比系統強制固定間距更貼近實務。
- **代價**：`Template`／`Inspection Plan`／`Task Generator` 原本依 interval 自動切分任務的範例與資料快照語意需要在 intent／spec 對齊；未來若要做自動切分，須另定來源、覆寫與快照規則。
- **什麼情況要重新討論**：未來若需要自動切分工具時，另定 interval 的資料歸屬與快照規則。
- **依據**：負責人決定（#89，2026-09-28）；取代架構基準 §2.4、§16.2 的 interval 範例，見 [G-01](05-open-questions.md#g-01)。

<a id="kd-37"></a>
## KD-37：查核結果由現場對每個查核項次自行判定符合／不符合

- **決策**：每個查核項次**必須**各自有「符合」與「不符合」選項，由現場人員自行選擇，**不得**只替整個查核項目組選一個結果，也**不得**預設符合；系統**不得**依標準值自動判定結果。一個查核項次**得**有多個實測欄位（例如長、寬、高），欄位與標準值由內業事先設定，標準值**必須**依計畫書原文以文字輸入，系統不解析比較符號；不需量測的項次不強制填實際值。
- **狀態**：已決定（僅涵蓋以上範圍）；`N/A`、嚴重度、缺失管理與不符合後續流程未定，見 [OQ-06](05-open-questions.md#oq-06)。
- **考慮過但沒選**：以查核項目組為單位選一個結果；系統依標準值自動判定符合／不符合。
- **為什麼選這個**：不同項次的查核結果可能不同，統一判定會掩蓋個別項次的實際狀況；標準值來源是計畫書原文，格式不一致，系統解析風險高。
- **代價**：每個查核項次都要各自記錄結果與（若有）多筆實測值；欄位型別、單位與必填細節仍待裁定才能定案完整 schema。
- **什麼情況要重新討論**：`N/A`、嚴重度、缺失管理裁定後，一併檢視本決策是否需要調整。
- **依據**：負責人決定（#76，2026-09-28）；架構基準 §38 Result 的未定案項目部分裁定，見 [OQ-06](05-open-questions.md#oq-06)。

<a id="kd-38"></a>
## KD-38：查核項次由內業設定，照片依覆蓋規則佐證

- **決策**：查驗流程**必須**是一套共通流程，不因進料／施工／測試等報表樣板差異而分成不同流程；一個查核項目組下**得**有多個查核項次，項次內容由內業事先設定。現場人員自行選擇每張照片要佐證哪些查核項次，一張照片**得**覆蓋多個項次；每個查核項次**必須**至少被一張非總覽照片覆蓋。**得**額外提供「總覽照片」選項，由現場人員選擇是否拍攝；有拍就在該組報表中排第一張，且**不計入**最低覆蓋要求。
- **狀態**：已決定（僅涵蓋以上範圍）；每項次能否有多張照片、照片張數上限、總覽照片的具體拍攝方式未定，見 [OQ-05](05-open-questions.md#oq-05)。
- **考慮過但沒選**：依進料／施工／測試建立三套不同查驗流程；固定「每幾個項次配一張照片」的規則；把總覽照片列為必拍項目。
- **為什麼選這個**：報表樣板差異不代表查驗流程本身不同；由現場人員自行選擇佐證關係比系統預先固定配對更貼近實際拍攝情況。
- **代價**：完成度驗證需要依「每個項次至少一張非總覽照片」的規則檢查，而非簡單的照片數量比對；範本快照需要保存查核項次清單供現場端渲染。
- **什麼情況要重新討論**：每項次可否多張、照片張數上限、總覽照片拍攝方式裁定後，一併檢視本決策。
- **依據**：負責人決定（#75，2026-09-28）；架構基準 §38 Template 的未定案項目部分裁定，見 [OQ-05](05-open-questions.md#oq-05)。

<a id="kd-39"></a>
## KD-39：Project 必填欄位與專案編號可重複

- **決策**：一個工程案建立一筆 `Project`；必填欄位為專案編號／代號、工程名稱、業主／委託單位、整體工程地點。`project_code`（專案編號）**必須**允許重複，資料庫**不得**對此欄位加唯一約束；系統內部的 Project ID（UUID）才必須唯一。新建或修改 Project 時，若 `project_code` 與既有 Project 重複，系統**必須**跳出警告提示使用者，但**不得**阻擋建立或儲存。預計開工日、預計完工日為選填；其他參與單位不列為建立專案的必填欄位。`Project` 建立後**必須**直接可用，不要求額外啟用步驟。
- **狀態**：已決定。
- **考慮過但沒選**：以 `project_code` 作為唯一業務識別（原架構基準假設，`database-foundation` DBF-R13「必須唯一」的規則已被本決策取代）；建立時要求額外啟用流程；重複時直接阻擋建立。
- **為什麼選這個**：現場實務上專案編號可能重複使用或由不同單位各自編碼，不宜由系統強制唯一；建立後即可使用可以縮短內業建立查核工項的前置時間；重複時提示但不阻擋，兼顧提醒使用者與不影響作業。
- **代價**：既有 `backend/app/models/project.py`（`project_code` 目前 `unique=True`）與 `database-foundation` DBF-R13、`domain-model` 規格的唯一約束假設須另開 task 修改並新增 migration；規格修改見 [#246](https://github.com/speko-tw/inspect-flow/issues/246)，程式修改見 [#247](https://github.com/speko-tw/inspect-flow/issues/247)，不在本次變更範圍內。
- **什麼情況要重新討論**：若未來需要以 `project_code` 做唯一查詢鍵，另行評估是否新增複合唯一約束（例如搭配客戶或年度）。
- **依據**：負責人決定（#71，2026-09-28）；取代架構基準 §12.2 的最小佔位欄位假設，見 [OQ-01](05-open-questions.md#oq-01)；重複時的警告提示依負責人補充（[#71 留言](https://github.com/speko-tw/inspect-flow/issues/71#issuecomment-5872016815)，2026-09-28），取代 `database-foundation` DBF-R13。

<a id="kd-40"></a>
## KD-40：工項分類與分區皆依專案需求選用

- **決策**：每個專案的內業人員**必須**先依該專案需求，訂出要查核的分類與項目，**不得**套用公司共用的固定工項分類。工項分類（例如空調風管、給排水、電力設備）與分區（例如一樓 A 區、二樓 B 區）**皆為**依專案需求選用的設定，不強制每個專案都要建立。若專案正式建立分區，查核工項**必須**按分區分開建立與執行；若未建立分區，工區**得**只是同一查核工項的選項或資訊，合併為一個查核工項。
- **狀態**：已決定（僅涵蓋以上範圍）；分類與分區的固定階層、共用範本複製、名稱與代碼規則未定，分區**不**強制為分類的子層，見 [OQ-04](05-open-questions.md#oq-04)、[OQ-03](05-open-questions.md#oq-03)。
- **考慮過但沒選**：全公司共用一套固定工項分類；分區強制作為分類的子層。
- **為什麼選這個**：不同工程專案查核內容差異大，固定分類無法適用所有專案；分區是否需要視專案規模而定，不宜強制。
- **代價**：查核工項的資料模型需要支援「有分區」與「無分區」兩種情境；分類、分區的階層與命名規則要等後續裁定才能完整定案。
- **什麼情況要重新討論**：分類與分區的階層、共用範本複製、命名與代碼規則裁定後，一併檢視本決策。
- **依據**：負責人決定（#74、#73，2026-09-28）；架構基準 §38 Work Item、§12.8 的未定案項目部分裁定，見 [OQ-04](05-open-questions.md#oq-04)、[OQ-03](05-open-questions.md#oq-03)。

## KD-41：查驗是共通流程，報表樣板與匯入格式是獨立模組

- **決策**：查驗流程**必須**是一套共通機制：內業設定查核項次，現場填結果與實測值並拍佐證照片，內業再產出報表；建立查驗時**不得**選定或處理輸出報表樣板。報表**必須**是獨立的功能模組，**得**匯入不同樣板格式。
- **狀態**：已決定（僅涵蓋以上流程界線）；具體匯入格式、樣板欄位對應、選樣板時機、簽署欄位與 Revision 規則未定，見 [OQ-07](05-open-questions.md#oq-07)。

<a id="kd-42"></a>
## KD-42：任務完成後可修正資料，計畫在所有任務完成時自動完成

- **決策**：`Inspection Task` 標記完成後，若資料有錯字、文字或圖片需要修正，現場人員與內業人員**皆得**修改；此為已完成查核後的資料修正，**不要求**重新查核，也**不**因修正而改回待確認或要求再按一次完成，任務維持「已完成」。`Inspection Plan` 底下所有任務都完成時，系統**必須**自動將計畫設為「已完成」；**不開放**人員手動修改計畫狀態。
- **狀態**：已決定（僅涵蓋以上範圍）；Plan／Task／Template Version／Evidence／Report 的其他狀態、作廢、取消、失敗與更正路徑未定，見 [OQ-09](05-open-questions.md#oq-09)。
- **考慮過但沒選**：任務修正後改回待確認狀態，要求重新完成；開放人員手動修改計畫狀態（負責人已於本次討論中明確撤回）。
- **為什麼選這個**：已完成任務的資料修正屬於更正性質，不是推翻查核結果，不需要重新走一次完成流程；計畫狀態應反映任務進度的客觀結果，不需要人工介入。
- **代價**：需要記錄任務完成後的修改紀錄（誰、何時、改了什麼），具體欄位與機制待規格對齊；計畫的完成判定需要在每次任務狀態變化時重新檢查是否全部完成。
- **什麼情況要重新討論**：若未來確認需要開放人員手動修改計畫狀態，須先由負責人另行裁定，不得逕自實作。
- **依據**：負責人決定（#78，2026-09-28）；架構基準 §18、§20.6、§20.17 的未定案項目部分裁定，見 [OQ-09](05-open-questions.md#oq-09)。

### Web API

- **選用**：FastAPI；API 採 REST／JSON，照片上傳採 `multipart/form-data`。
- **負責什麼**：外部 API、驗證入口、上傳、授權入口與 OpenAPI 文件。
- **狀態**：建議（FastAPI）；API 邊界已決定，見 [KD-01](#kd-01)。
- **為什麼**：型別整合與文件產生方便內部系統開發。
- **不要用**：把大量業務邏輯寫在 route，或讓前端直接連資料庫。
- **未來升級路線**：維持 `/api/v1` 契約；框架版本由測試後的 lockfile 固定。
- **依據**：架構基準 §4.2、§7.1、§14。

<a id="stack-asgi-server"></a>
### ASGI 伺服器

- **選用**：uvicorn。
- **負責什麼**：本機開發時啟動 FastAPI（`make run-backend`）。
- **狀態**：建議；正式部署用什麼伺服器不在此決定，留給 pilot-deployment（[#109](https://github.com/speko-tw/inspect-flow/issues/109)）。
- **為什麼**：FastAPI 需要 ASGI 伺服器才能執行；uvicorn 是它文件的預設選擇，支援開發用的自動重載。
- **不要用**：把本機開發的啟動方式直接當成正式部署設定。
- **未來升級路線**：部署方式定案後再補正式環境的伺服器設定；依賴版本由 lockfile 固定。
- **依據**：負責人裁定（[PR #212 留言](https://github.com/speko-tw/inspect-flow/pull/212#issuecomment-5851963155)，2026-09-27）；架構基準無對應章節。

<a id="stack-api-schema"></a>
### API Schema

- **選用**：Pydantic v2 系列。
- **負責什麼**：Request／Response 型別與輸入驗證。
- **狀態**：建議。
- **為什麼**：在資料進入 Service 前建立清楚的 API 契約。
- **不要用**：只在前端驗證，或把未驗證的 JSON 直接交給業務規則。
- **未來升級路線**：隨 API 契約演進調整 schema；精確依賴版本由 lockfile 固定。
- **依據**：架構基準 §4.3、§16.1。

<a id="stack-orm"></a>
### ORM 與資料存取

- **選用**：SQLAlchemy 2.x，見 [KD-06](#kd-06)。
- **負責什麼**：讓 Service 存取 SQLite／PostgreSQL。
- **狀態**：已決定。
- **為什麼**：降低資料庫切換時的程式改動。
- **不要用**：到處散落 SQLite 專用 raw SQL；需要 raw SQL 時要標明資料庫相依性。
- **未來升級路線**：先以 PostgreSQL 整合測試確認相容性，再搬移資料。
- **依據**：架構基準 §4.4、§7.3、§32、§37 ADR-005。

<a id="stack-migration"></a>
### Database Migration

- **選用**：Alembic，見 [KD-06](#kd-06)。
- **負責什麼**：建立、升級與追蹤正式 schema。
- **狀態**：已決定。
- **為什麼**：每次 schema 變更都要可審查、可重現。
- **不要用**：正式環境靠 `create_all()` 或未記錄的手動 ALTER。
- **未來升級路線**：SQLite 與 PostgreSQL 都要跑 migration 驗證。
- **依據**：架構基準 §4.5、§22A.9、§27.3。

<a id="stack-frontend"></a>
### Frontend

- **選用**：React、TypeScript、Vite；Admin／Field 共用單一程式庫，見 [KD-12](#kd-12)。
- **負責什麼**：現場與後台操作畫面、API Client、前端建置。
- **狀態**：建議（工具）；已決定（單一程式庫，見 [KD-12](#kd-12)）。
- **為什麼**：支援手機介面與 Dashboard，TypeScript 可減少欄位錯誤。
- **不要用**：把資料庫或 storage key 當作前端存取契約。
- **未來升級路線**：如差異擴大，評估拆分；實際套件版由 lockfile 固定。
- **依據**：架構基準 §5.1–5.2、§37 ADR-008。

<a id="stack-pwa"></a>
### PWA

- **選用**：現場 Web 朝 PWA 相容設計；MVP 先採 Online-first。
- **負責什麼**：手機與平板使用路徑，保留日後安裝與離線草稿能力。
- **狀態**：建議；完整離線同步是延後能力。
- **為什麼**：工程師可用 iPhone、iPad 或 Android 開啟 Web App。
- **不要用**：把 PWA 相容等同已完成離線同步。
- **未來升級路線**：依 Pilot 網路資料，再加入 cache、draft、待上傳佇列與同步。
- **依據**：架構基準 §5.3、§13A.14、§34–35。

<a id="stack-database"></a>
### 資料庫

- **選用**：MVP 用 SQLite；`foreign_keys = ON`、WAL **應**在連線初始化時確認。見 [KD-08](#kd-08)。
- **負責什麼**：人員、專案、範本、任務、證據 metadata 與報告資料。
- **狀態**：已決定（SQLite）；建議（兩項 PRAGMA）。
- **為什麼**：Pilot 規模可先降低維運負擔。
- **不要用**：多台後端經 NAS 共用同一個 SQLite 檔。
- **未來升級路線**：併發、鎖定或維運需求增加時轉 PostgreSQL。
- **依據**：架構基準 §9–10、§32、§37 ADR-003。

<a id="stack-photo-storage"></a>
### 照片儲存

- **選用**：本機持久化儲存與 Storage 介面；檔案和 DB metadata 分離。見 [KD-02](#kd-02)。
- **負責什麼**：現場版、內業版兩張照片的檔案存取（見 [KD-32](#kd-32)）。
- **狀態**：已決定（分離與介面）；建議（第一版本機儲存）。
- **為什麼**：避免照片 BLOB 撐大 SQLite，也保留遷移彈性。
- **不要用**：原檔名當唯一 key；業務邏輯直接寫死檔案路徑。
- **未來升級路線**：以 MinIO、S3 或 NAS 實作相同 Storage 介面；照片版本模型見 [KD-32](#kd-32)、[G-02](05-open-questions.md#g-02)（已裁定）。
- **依據**：架構基準 §2.3、§7.4、§13.1–13.2、§33。

<a id="stack-image-processing"></a>
### 現場影像處理

- **選用**：前端即時預覽；後端可用 Pillow 依編輯參數產生內業版。見 [KD-32](#kd-32)、[KD-33](#kd-33)、[OQ-14](05-open-questions.md#oq-14)。
- **負責什麼**：現場端裁切、旋轉、亮度等編修，以及內業端加工產生內業版。
- **狀態**：待定（Frontend Render 或 Backend Render）；照片只保存現場版、內業版兩張已決定（見 [KD-32](#kd-32)）。
- **為什麼**：前端預覽反應快；後端處理有利結果一致與重現。
- **不要用**：另外保存原始拍攝檔案或編輯中間版本；提供會增刪現場內容的標準修圖功能。
- **未來升級路線**：離線時先存現場版與編輯參數，連線後再上傳及產生內業版；見 [G-03](05-open-questions.md#g-03)。
- **依據**：架構基準 §13A.2、§13A.5–13A.8、§13A.14；照片版本模型依負責人決定（#90～#92，2026-09-28）。

<a id="stack-docx"></a>
### DOCX 產製

- **選用**：版本化 DOCX 範本；Python 端**應**先評估 `python-docx`，複雜樣板可評估 `docxtpl`。見 [KD-05](#kd-05)。
- **負責什麼**：用 Report View Model 產生可編輯的正式 Word 文件。
- **狀態**：已決定（DOCX 輸出與範本版本）；建議（函式庫）。
- **為什麼**：業主與標案常沿用 Word 表單；版次要能對應範本。
- **不要用**：從瀏覽器 UI state 拼正式報告，或把 DOCX 當暫存下載。
- **未來升級路線**：增加不同業主樣板與 View Model Builder，不改歷史文件。
- **依據**：架構基準 §20.2–20.5、§20.19、§37 ADR-009。

<a id="stack-pdf"></a>
### PDF 轉換

- **選用**：以 DOCX 為來源產出 PDF；轉換器待 Pilot 驗證，見 [KD-05](#kd-05)、[OQ-15](05-open-questions.md#oq-15)。
- **負責什麼**：產生提交與歸檔用 PDF。
- **狀態**：已決定（PDF 輸出）；待定（LibreOffice Headless 或受控轉換服務）。
- **為什麼**：兩種格式要共享報告資料與正式版面。
- **不要用**：只以 HTML 列印 PDF 當正式報告；未實測就指定 Production 轉換器。
- **未來升級路線**：依字型、表格、圖片、頁碼、分頁及簽名欄實測結果選轉換服務。
- **依據**：架構基準 §20.3–20.4、§20.20–20.22。

<a id="stack-auth"></a>
### 認證與授權

- **選用**：內部帳號搭配 Server-managed Session 與 HttpOnly Cookie（Secure、SameSite），見 [KD-30](#kd-30)；密碼以 Argon2id 雜湊，見 [KD-31](#kd-31)。兩者由負責人裁定，見 [OQ-13](05-open-questions.md#oq-13)。
- **負責什麼**：登入、目前使用者與 API 權限檢查。
- **狀態**：建議（內部帳號）；已決定（Session 與 HttpOnly Cookie、Argon2id，見 [KD-30](#kd-30)、[KD-31](#kd-31)）；已決定（權限機制，見 [KD-24](#kd-24)～[KD-29](#kd-29)）。
- **為什麼**：先滿足內部系統需求，不必在 MVP 建完整 OAuth 基礎設施。
- **不要用**：把長效 JWT 直接放在 browser localStorage。
- **未來升級路線**：`User` 已預留外部身分來源欄位與同步比對規則，見 [KD-20](#kd-20)；實際串接方式（含 Corporate SSO）另開「外部身分同步」規格，見 [docs/specs/README.md](../specs/README.md#index)，本卡不預先寫串接方式。角色矩陣已裁定，見 [OQ-08](05-open-questions.md#oq-08)。
- **依據**：架構基準 §17、§35、§36；Session 與密碼雜湊為負責人決定（#82，2026-09-26）。

### 部署

- **選用**：Linux Server、Docker Engine、Docker Compose 與版本化 image，見 [KD-09](#kd-09)。
- **負責什麼**：啟動 Web、API、Reverse Proxy；掛載持久化資料。

<a id="stack-reverse-proxy"></a>
### Reverse Proxy 與 HTTPS

- **選用**：正式環境提供 HTTPS；Caddy、Nginx 或企業現有 Proxy 可選。見 [KD-09](#kd-09)。
- **負責什麼**：將 `/api/*` 導向後端，其餘請求導向前端。
- **狀態**：已決定（HTTPS）；建議（Caddy）；待定（正式 Proxy 選型）。
- **為什麼**：使用者不需要直接連 API 容器埠。
- **不要用**：把 API 或未受控資料庫埠直接暴露給一般使用者。
- **未來升級路線**：可改接企業 Proxy 或 Load Balancer，保留外部 HTTPS 入口。
- **依據**：架構基準 §22.5、§22.10–22.11。

<a id="stack-tests"></a>
### 測試工具

- **選用**：Backend 以 pytest；Frontend component 可用 Vitest；關鍵流程可用 Playwright。
- **負責什麼**：驗證 task generation、快照、Evidence、權限、完整使用者流程與 PostgreSQL 相容性。
- **狀態**：建議（工具）；關鍵流程與跨資料庫驗證為來源要求。
- **為什麼**：任務與正式報告的資料正確性要能重複驗證。
- **不要用**：只測 UI 顯示而略過後端完成驗證或報告內容。
- **未來升級路線**：隨正式報告樣板增加 DOCX/PDF 資料與版面測試。
- **依據**：架構基準 §13A.15、§20.20、§27.1–27.4。

<a id="stack-ci"></a>
### CI

- **選用**：GitHub Actions；每次 PR 執行 lint、後端測試、前端測試、build 與 PostgreSQL 相容性測試。見 [KD-09](#kd-09)。
- **負責什麼**：在版本化 image 進入正式發布前擋下失敗變更。
- **狀態**：已決定（CI 閘門）；已決定（CI 平台採 GitHub Actions，團隊於 [#5](https://github.com/speko-tw/inspect-flow/issues/5) 選定，非架構基準來源）。理由：repo 在 GitHub，檢查結果可直接接上分支保護與 PR 審查。
- **為什麼**：正式環境只部署已審查、已建置、已驗證的產物。
- **不要用**：CI 失敗仍發布，或在 Production 現場編譯臨時版本。
- **未來升級路線**：部署自動化可稍後加入；先維持可重現的手動發布流程。
- **依據**：架構基準 §22A.4–22A.7、§28、§37 ADR-011。

<a id="stack-code-quality"></a>
### 程式品質工具

- **選用**：Python 用 ruff（format 與 lint）；Frontend 用 Prettier（格式）、ESLint（lint）、TypeScript（型別）；Python 型別檢查用 pyright。
- **負責什麼**：基本 lint、格式與型別檢查。formatter 管排版、linter 管寫法、型別檢查器管型別，三者不重疊。
- **狀態**：
  - 已決定：ruff、ESLint、TypeScript、Prettier（團隊於 [#5](https://github.com/speko-tw/inspect-flow/issues/5) 選定，非架構基準來源）；起始設定見 `skeleton` 規格。
  - 已決定：pyright，先 `basic`、再逐個模組改 `strict`（團隊於 [#5](https://github.com/speko-tw/inspect-flow/issues/5) 裁定 [OQ-16](05-open-questions.md#oq-16)）。
  - 已決定：程式碼行寬上限 79 字元，依 PEP 8，全專案程式碼一律適用（專案負責人指定，非架構基準來源；Markdown 文件不受此限）；formatter 與 linter 設定**必須**與之一致。
  - Python 風格以 PEP 8 為基準。起始規則集與新增規則的方式由 `skeleton` 規格與設定檔維護。
- **為什麼**：維持基本一致性，同時避免 MVP 一開始導入過多規則。pyright 與 VS Code 的 Pylance 同一引擎，編輯器與 CI 的結果一致。
- **不要用**：未經團隊評估就把多套重疊的 lint 或架構框架加入發布閘門。
- **未來升級路線**：依程式量與缺陷資料調整檢查；pyright 逐個模組改為 `strict`。
- **依據**：架構基準 §29。
