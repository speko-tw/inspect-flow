# 關鍵決策與技術棧

**這份文件回答**：InspectFlow 選了哪些架構方向？各項工具負責什麼？
**什麼時候讀**：選技術、調整模組邊界、規劃資料遷移、製作報告或部署服務時。

本文件保留 KD-01 到 KD-57 的編號。技術棧卡片另標「已決定／建議／待定」。卡片狀態依架構基準正文判定，不以 §36 的表格直接推定。規則強度見本目錄 README；尚未定案的細節見 [待決議](05-open-questions.md)。

## 關鍵決策

<a id="kd-01"></a>
## KD-01：外部用戶端只透過後端 API 存取資料

- **決策**：Field Web、Admin Web 等外部用戶端**必須**經後端 API 讀寫資料；前端**不得**直接連資料庫或檔案儲存。後端 Report Service 可直接使用服務、資料存取與儲存介面，不必呼叫自己的 HTTP API。見 [PR-01](02-principles.md#pr-01)。
- **狀態**：已決定。
- **考慮過但沒選**：前端直接連資料庫或組出儲存路徑。
- **為什麼選這個**：權限、驗證與業務規則集中在後端；換資料庫時，前端契約可維持穩定。
- **代價**：外部存取要先定義 API；後端要維護 API 契約。
- **什麼情況要重新討論**：新增獨立外部服務，且現有 API 無法滿足資料交換需求時，檢查 API 契約與授權邊界；前端禁直連的要求仍有效。
- **依據**：架構基準 §2.2、§20.2、§37 ADR-002。

<a id="kd-02"></a>
## KD-02：照片檔案與關聯式資料分開存放

- **決策**：資料庫保存 Evidence metadata；檔案存入 Storage。後端產生 storage key，不以原始檔名當唯一識別。業務邏輯經 Storage 介面讀寫檔案。見 [PR-02](02-principles.md#pr-02)。
- **狀態**：已決定。
- **考慮過但沒選**：照片以 BLOB 放進 SQLite；原始檔名直接當 storage key。
- **為什麼選這個**：照片是容量主因；分開存放可控制資料庫大小，並保留物件儲存遷移路徑。
- **代價**：檔案與資料庫需要配對備份，也要處理兩邊寫入失敗。照片只保存現場版與內業版兩張，見 [KD-32](#kd-32)、[G-02](05-open-questions.md#g-02)（已裁定）。
- **什麼情況要重新討論**：本機檔案容量、備份或存取需求超出單機能力時，評估 MinIO、S3 或 NAS；Storage 介面仍維持。
- **依據**：架構基準 §2.3、§7.4、§13.1–13.2、§33、§37 ADR-004。

<a id="kd-03"></a>
## KD-03：查核範本不版本化，套用到專案時複製成專案自己的一份

- **決策**：範本庫裡的 `Inspection Template` 修改時**直接覆蓋**，只保留最新內容，**不做**版本化（不設 `Template Version`）。查核範本套用到專案時**必須**複製一份，成為專案自己的查核項目（見 [KD-47](#kd-47)）；「快照」由這份複製負責，之後修改或刪除查核範本，都不影響已套用的專案。專案**必須**記錄來源查核範本名稱與套用時間，供追查；查核範本被覆蓋後，不保證能回看套用當時的查核範本內容。
- **狀態**：已決定（改寫原決策「查核範本版本化，任務建立時固定需求」，保留編號）。任務需求快照維持必須：建立任務時**必須**產生 `Task Requirement Snapshot`（見 [PR-04](02-principles.md#pr-04)，不變）。專案副本與任務快照的分工已由 [KD-55](#kd-55) 裁定（內業修改專案查核項目時，選擇是否讓現場重新查核；選「要」則用到該項次的任務作廢）；其餘細節見 [OQ-09](05-open-questions.md#oq-09) 的未定項目。
- **考慮過但沒選**：查核範本版本化（v1、v2、v3……），任務建立時鎖定某一版並把需求複製成 `Task Requirement Snapshot`（原決策）。
- **為什麼選這個**：專案套用時已經持有獨立的一份，歷史可追溯由專案那份負責，範本庫不必再維護版本，只保留最新內容即可。以上理由是依裁定內容整理，負責人只說明「修改時直接覆蓋、快照由套用複製負責」。
- **代價**：查核範本被覆蓋後，無法回看專案當時依據的查核範本內容，只能靠專案複本本身與「來源查核範本名稱、套用時間」追查；`Template Version` 實體取消，依版本鎖定的設計一併取消，[06-versioning-and-milestone-governance.md](06-versioning-and-milestone-governance.md) 中 0.3.x 與 0.4.x 的範圍已對應調整。
- **什麼情況要重新討論**：稽核或業主要求回看查核範本歷史內容時，評估保留查核範本修改歷程；若要修改已建立任務的需求，仍須先定義更正流程，不能直接改寫歷史快照。
- **依據**：負責人裁定（[#78 留言](https://github.com/speko-tw/inspect-flow/issues/78#issuecomment-5956039701)，2026-10-02）；取代原決策依據的架構基準 §2.5、§12.4、§12.9、§37 ADR-006 中「查核範本版本化」的部分；本決策只管查核範本，報告範本（報告版面）及其版本不受影響，見 [KD-05](#kd-05)，依[負責人確認（#313，2026-10-02）](https://github.com/speko-tw/inspect-flow/issues/313)。

- **為什麼選這個**：本卡片保留供追溯舊決策脈絡；現行規則見 [KD-32](#kd-32)、[KD-33](#kd-33)。
- **代價**：無（已由新決策取代，不再是有效規則）。
- **什麼情況要重新討論**：不適用，已被取代。
- **依據**：架構基準 §13A.2–13A.6、§37 ADR-010；已由負責人決定（#90～#91，2026-09-28）取代，見 [G-02](05-open-questions.md#g-02)、[G-03](05-open-questions.md#g-03)。

## KD-05：DOCX 與 PDF 是 MVP 的正式交付物

- **決策**：MVP **必須**產出 DOCX 與 PDF。報告從後端 Report View Model 和版本化的報告範本（DOCX 報告版面）產生；HTML 可做預覽，不能取代正式文件。報告需保存報告範本版本、文件編號、版次、快照、檔案鍵、雜湊與產製資訊。見 [PR-06](02-principles.md#pr-06)。
- **狀態**：已決定；完整核准、簽名與核發流程仍待決議，見 [OQ-07](05-open-questions.md#oq-07)、[G-11](05-open-questions.md#g-11)。
- **考慮過但沒選**：只從 HTML 直接列印 PDF；只提供一次性下載檔。
- **為什麼選這個**：業主、監造與標案文件需要可提交、可歸檔、可追溯的正式產物。
- **代價**：需要管理報告範本（DOCX 版面）、版面驗收及 PDF 轉換。轉換工具見 [OQ-15](05-open-questions.md#oq-15)。
- **什麼情況要重新討論**：正式收件規範改變，且 DOCX／PDF 不再滿足交付要求時，新增決策並評估舊報告的保存方式。
- **依據**：架構基準 §20.1–20.7、§20.22、§30 Phase 9、§37 ADR-009。本卡的「範本」指報告範本（報告版面），與查核範本（[KD-03](#kd-03)）是兩種不同的東西，版本與快照規則維持原文（[負責人確認（#313，2026-10-02）](https://github.com/speko-tw/inspect-flow/issues/313)）。

<a id="kd-06"></a>
## KD-06：資料庫存取用 SQLAlchemy，結構演進用 Alembic

- **決策**：資料庫存取**必須**經 SQLAlchemy。Schema 變更**必須**走 Alembic migration。正式環境**不得**靠 `Base.metadata.create_all()` 或未記錄的手動 ALTER 管理版本。見 [PR-03](02-principles.md#pr-03)。
- **狀態**：已決定。
- **考慮過但沒選**：正式環境直接建立表格或手動改 schema；大量使用 SQLite 專用 SQL。
- **為什麼選這個**：把 SQLite 換成 PostgreSQL 時，資料庫差異較容易收斂在資料存取與 migration 層。
- **代價**：每次 schema 變更都要寫、審查及驗證 migration。
- **什麼情況要重新討論**：導入 SQLAlchemy 無法支援的資料庫能力時，記錄相依性並以雙資料庫測試驗證；正式 schema 變更仍需可追蹤。
- **依據**：架構基準 §4.4–4.5、§22A.9、§32、§37 ADR-005。

<a id="kd-07"></a>
## KD-07：主要實體以 UUID 識別

- **決策**：Project、User、Plan、Task、Evidence 等主要實體使用 UUID。UUIDv7 **得**優先評估。人類可讀的業務編號與 UUID 分開保存。
- **狀態**：已決定；UUID 版本待實作選擇。
- **考慮過但沒選**：完全依賴 SQLite AUTOINCREMENT 作為跨系統身分。
- **為什麼選這個**：減少資料合併時撞號的風險，並保留離線用戶端自行產生 ID 的空間。
- **代價**：UUID 較長；畫面與文件還要另外使用可讀的業務編號。
- **什麼情況要重新討論**：離線建立、跨系統合併或排序效能提出具體需求時，選定 UUID 版本與產生位置；不改用自增值作為唯一對外識別。
- **依據**：架構基準 §11、§37 ADR-007。

<a id="kd-08"></a>
## KD-08：MVP 先用單機 SQLite

- **決策**：MVP 使用 SQLite。多台後端**不得**透過網路檔案系統共用同一個 SQLite 檔。連線初始化**應**確認 `foreign_keys = ON` 與 WAL；來源把兩項 PRAGMA 稱為「建議確認」，不是額外的 ADR 強制項。
- **狀態**：已決定；PRAGMA 屬建議設定。
- **考慮過但沒選**：MVP 一開始就維運 PostgreSQL；多台伺服器共用同一個 SQLite 檔。
- **為什麼選這個**：Pilot 規模小、schema 尚在變動，先降低資料庫維運成本。
- **代價**：寫入併發及資料庫維運能力有限；備份須處理 WAL 的一致性。
- **什麼情況要重新討論**：需要第二台後端、同時寫入明顯增加，或備份、鎖定、監控需求超出 SQLite 能力時，轉向 PostgreSQL。
- **依據**：架構基準 §9.1–9.2、§10、§23、§37 ADR-003。

<a id="kd-09"></a>
## KD-09：Pilot 與正式環境採 Linux 和 Docker Compose

- **決策**：Pilot／Production 使用 Linux Server、Docker Engine、Docker Compose 與持久化儲存。正式變更經 Git、審查、CI、版本化 image；migration 必須納入發布流程。見 [PR-13](02-principles.md#pr-13)。
- **狀態**：已決定；migration 與服務啟動的先後順序依 [G-09](05-open-questions.md#g-09) 的裁定，見 [PR-13](02-principles.md#pr-13)。
- **考慮過但沒選**：個人電腦、臨時 VM、沒有持久化磁碟的主機，或第一天就導入多節點編排。
- **為什麼選這個**：開發與正式環境較易重現，也能以固定流程備份、更新及回滾。
- **代價**：Compose 本身不提供多節點協調與自動容錯；部署仍需要維運程序。
- **什麼情況要重新討論**：需要多節點、高可用、自動容錯或大量後端副本時，評估編排平台。部署順序的來源歧義與裁定見 [G-09](05-open-questions.md#g-09)。
- **依據**：架構基準 §22.1–22.7、§22A.7、§22A.19、§37 ADR-011。

<a id="kd-10"></a>
## KD-10：第一版使用模組化單體

- **決策**：第一版只有一個 Backend Application。API、Service、Persistence 與 Storage 保持清楚邊界。見 [PR-11](02-principles.md#pr-11)。
- **狀態**：已決定。
- **考慮過但沒選**：為尚未出現的規模需求先導入微服務、訊息系統或多節點編排。
- **為什麼選這個**：縮短開發與部署路徑，同時保留日後拆分模組的空間。
- **代價**：模組共用部署單位，不能單獨擴充某個模組。
- **什麼情況要重新討論**：特定模組有可量測的獨立擴充、部署或隔離需求時，評估拆分；只因「未來可能變大」不足以拆分。
- **依據**：架構基準 §2.1、§7、§22A.19、§37 ADR-001。

<a id="kd-11"></a>
## KD-11：現場畫面只呈現完成任務所需資訊

- **決策**：Field UI 聚焦「今日任務 → 證據 → 完成」。查核範本庫與範本設定、資料庫 ID、storage key 與後台設定不放在現場操作畫面。見 [PR-10](02-principles.md#pr-10)。
- **狀態**：已決定。
- **考慮過但沒選**：把管理及設定功能直接放進現場畫面。
- **為什麼選這個**：降低現場工程師的操作負擔與拍錯需求的機率。
- **代價**：進階設定與例外處理要由 Admin UI 或後端流程承接。
- **什麼情況要重新討論**：Pilot 顯示現場工程師因缺少必要資訊而無法完成任務時，調整呈現內容，但不暴露底層儲存與資料庫細節。
- **依據**：架構基準 §6.1–6.2、§31、§37 ADR-008。

<a id="kd-12"></a>
## KD-12：Admin／Field 共用單一前端程式庫

- **決策**：Admin UI 與 Field UI **必須**放在同一個 React application，以 `/admin/*`、`/field/*` 路由與權限區分；**必須**依路由拆分程式碼，Field 的程式包不得載入 Admin 的模組。
- **狀態**：已決定（團隊於 [#5](https://github.com/speko-tw/inspect-flow/issues/5) 裁定 [OQ-21](05-open-questions.md#oq-21)，採來源 §5.1 的建議）。
- **考慮過但沒選**：同一 repo 內分成兩個 app 加共用套件。
- **為什麼選這個**：一套 build、一條 CI、一次部署；API client、登入與元件共用；符合模組化單體方向（[KD-10](#kd-10)）。
- **代價**：沒有依路由拆分時，Field 會載入 Admin 的程式；日後要拆開需要搬遷。
- **什麼情況要重新討論**：Field PWA 需要獨立發布週期，或兩者差異大到共用成本高於分開維護時，評估拆分。
- **依據**：架構基準 §5.1；團隊裁定 [OQ-21](05-open-questions.md#oq-21)。

<a id="kd-13"></a>
## KD-13：清單端點採 cursor-based 分頁

- **決策**：`/api/v1` 清單端點的分頁**必須**採 cursor-based 分頁，不用 offset/limit。
- **狀態**：已決定。
- **考慮過但沒選**：offset/limit 分頁。
- **為什麼選這個**：現場查核的照片與任務清單偏向捲動瀏覽，cursor-based 分頁在資料持續新增時不會因位移量偏移而跳頁或重複。
- **代價**：不能直接跳到指定頁碼；cursor 的排序鍵必須穩定，見 [KD-14](#kd-14)（時間欄位精度到秒，需搭配 UUID 排序）。
- **什麼情況要重新討論**：後台管理畫面需要「跳到第 N 頁」這類操作時，評估是否額外提供 offset/limit 介面。
- **依據**：負責人決定（PR #30，2026-09-26）；架構基準無對應章節。

<a id="kd-14"></a>
## KD-14：時間欄位採 ISO 8601（RFC 3339）、UTC、精度到秒

- **決策**：API 回應中的時間欄位**必須**使用 ISO 8601（RFC 3339）字串，一律 UTC 並帶 `Z` 後綴，精度到秒（例如 `2026-09-26T08:30:00Z`）。
- **狀態**：已決定；輸入端的解析寬鬆度（是否接受小數秒、`+08:00` 偏移）不在本決策範圍，之後另議。
- **考慮過但沒選**：Unix epoch 數值、毫秒精度、本地時區字串。
- **為什麼選這個**：系統多為人類操作，秒級精度已足夠辨識操作先後，且字串格式比 epoch 對人類判讀與除錯更直接。
- **代價**：同一秒可能有多筆記錄，排序與 cursor 不得只靠時間欄位，必須以「時間＋UUID」為鍵（可評估搭配 [KD-07](#kd-07) 提及的 UUIDv7 提升同秒排序穩定性）。
- **什麼情況要重新討論**：出現需要秒級以下精度才能區分的業務情境（例如高頻自動化寫入）時，重新評估精度。
- **依據**：負責人決定（PR #30，2026-09-26）；架構基準無對應章節。

<a id="kd-15"></a>
## KD-15：`error.code` 採 dot-namespace 命名，對照表由程式列舉自動產生

- **決策**：`error.code` **必須**採 dot-namespace 命名（`<resource>.<reason>`，例如 `task.not_found`）；`error.code` 對照表**必須**由程式的列舉自動產生，不手寫維護獨立文件。不特定於單一資源的跨資源共用錯誤，依錯誤性質分類型 namespace：`request.*`（請求本身的問題，例如 `request.validation_failed`）、`resource.*`（不特定於某資源的通用資源錯誤，例如框架產生的 `resource.not_found`）、`server.*`（伺服器端錯誤，例如 `server.internal_error`）；資源專屬錯誤仍用 `<resource>.<reason>`。
- **狀態**：已決定。
- **考慮過但沒選**：SCREAMING_SNAKE_CASE 全域列舉、泛用少數碼、手寫維護對照表文件。
- **為什麼選這個**：dot-namespace 讓前端能依資源分類做程式化分支；對照表自動產生可避免列舉與文件長期不同步；跨資源共用錯誤依性質分為 `request`／`resource`／`server` 三類，讓歸屬判斷有固定規則可循，不必逐一個案討論。
- **代價**：每個資源都要維護自己的 reason 列舉；新增跨資源共用的錯誤原因時，須先判斷屬於 `request`／`resource`／`server` 三類中的哪一類，而非任意新增 namespace。
- **什麼情況要重新討論**：出現大量跨資源共用、難以歸入單一 `<resource>` 的錯誤原因時，重新評估命名法。
- **依據**：負責人決定（PR #30，2026-09-26）；架構基準無對應章節。

## KD-37：查核結果由現場對每個查核項次自行判定符合／不符合

- **決策**：每個查核項次**必須**各自有「符合」與「不符合」選項，由現場人員自行選擇，**不得**只替整個查核項目組選一個結果，也**不得**預設符合；系統**不得**依標準值自動判定結果。一個查核項次**得**有多個實測欄位（例如長、寬、高），欄位與標準值由內業事先設定，標準值通常取自計畫書，按原文以文字輸入，系統不解析 `±`、`≥` 等條件；不需量測的項次不強制填實際值。結果另有「不適用」，各結果的必填內容與實測欄位的型別見 [KD-54](#kd-54)。數值標準另有結構化欄位（見 [KD-52](#kd-52)），實測欄位的型別與必填規則已由 [KD-54](#kd-54) 裁定，現場填值的實作屬 0.7.x；是否自動判定尚未裁定，裁定前系統仍**不得**自動判定。
- **狀態**：已決定；`N/A`（不適用）、嚴重度與實測欄位的型別、必填已由 [KD-54](#kd-54) 補完（[OQ-06](05-open-questions.md#oq-06) 已裁定）；缺失管理與不符合後的改善追蹤、限期複查、自動判定屬 0.7.x，尚未裁定。
- **考慮過但沒選**：以查核項目組為單位選一個結果；系統依標準值自動判定符合／不符合。
- **為什麼選這個**：不同項次的查核結果可能不同，統一判定會掩蓋個別項次的實際狀況；標準值通常取自計畫書，格式不一致，系統解析風險高。
- **代價**：每個查核項次都要各自記錄結果與（若有）多筆實測值；欄位型別、單位與必填規則見 [KD-54](#kd-54)，完整 schema 由規格制定。
- **什麼情況要重新討論**：0.7.x 裁定不符合後的改善追蹤、限期複查或自動判定時，一併檢視本決策是否需要調整。
- **依據**：負責人決定（#76，2026-09-28）；架構基準 §38 Result 的未定案項目，見 [OQ-06](05-open-questions.md#oq-06)（已裁定）；其餘部分由 [KD-54](#kd-54) 補完（負責人裁定（[#76 留言](https://github.com/speko-tw/inspect-flow/issues/76#issuecomment-5965076758)，2026-10-03））。

<a id="kd-38"></a>
## KD-38：查核項次由內業設定，照片依覆蓋規則佐證

- **決策**：查驗流程**必須**是一套共通流程，不因進料／施工／測試等報表樣板差異而分成不同流程；一個查核項目組下**得**有多個查核項次，項次內容由內業事先設定。現場人員自行選擇每張照片要佐證哪些查核項次，一張照片**得**覆蓋多個項次；每個查核項次**必須**至少被一張非總覽照片覆蓋。**得**額外提供「總覽照片」選項，由現場人員選擇是否拍攝；有拍就在該組報表中排第一張，且**不計入**最低覆蓋要求。
- **狀態**：已決定；每項次可多張照片、不設張數上限、總覽照片可多張與照片註記，由 [KD-50](#kd-50) 補充，見 [OQ-05](05-open-questions.md#oq-05)（已裁定）。
- **考慮過但沒選**：依進料／施工／測試建立三套不同查驗流程；固定「每幾個項次配一張照片」的規則；把總覽照片列為必拍項目。
- **為什麼選這個**：報表樣板差異不代表查驗流程本身不同；由現場人員自行選擇佐證關係比系統預先固定配對更貼近實際拍攝情況。
- **代價**：完成度驗證需要依「每個項次至少一張非總覽照片」的規則檢查，而非簡單的照片數量比對；範本快照需要保存查核項次清單供現場端渲染。
- **什麼情況要重新討論**：照片張數規則或總覽照片的排列規則調整時，連同 [KD-50](#kd-50) 一併檢視。
- **依據**：負責人決定（#75，2026-09-28）；架構基準 §38 Template 的未定案項目裁定，見 [OQ-05](05-open-questions.md#oq-05)。2026-10-02 的補充裁定見 [KD-50](#kd-50)。

## KD-39：Project 必填欄位與專案編號可重複

- **決策**：一個工程案建立一筆 `Project`；必填欄位為專案編號／代號、工程名稱、業主／委託單位、整體工程地點。`project_code`（專案編號）**必須**允許重複，資料庫**不得**對此欄位加唯一約束；系統內部的 Project ID（UUID）才必須唯一。新建或修改 Project 時，若 `project_code` 與既有 Project 重複，系統**必須**跳出警告提示使用者，但**不得**阻擋建立或儲存。預計開工日、預計完工日為選填；其他參與單位不列為建立專案的必填欄位。`Project` 建立後**必須**直接可用，不要求額外啟用步驟。
- **狀態**：已決定。
- **考慮過但沒選**：以 `project_code` 作為唯一業務識別（原架構基準假設，`database-foundation` DBF-R13「必須唯一」的規則已被本決策取代）；建立時要求額外啟用流程；重複時直接阻擋建立。
- **為什麼選這個**：現場實務上專案編號可能重複使用或由不同單位各自編碼，不宜由系統強制唯一；建立後即可使用可以縮短內業建立查核工項的前置時間；重複時提示但不阻擋，兼顧提醒使用者與不影響作業。
- **代價**：既有 `backend/app/models/project.py`（`project_code` 目前 `unique=True`）與 `database-foundation` DBF-R13、`domain-model` 規格的唯一約束假設須另開 task 修改並新增 migration；規格修改見 [#246](https://github.com/speko-tw/inspect-flow/issues/246)，程式修改見 [#247](https://github.com/speko-tw/inspect-flow/issues/247)，不在本次變更範圍內。
- **什麼情況要重新討論**：若未來需要以 `project_code` 做唯一查詢鍵，另行評估是否新增複合唯一約束（例如搭配客戶或年度）。

## KD-40：工項分類與分區皆依專案需求選用

- **決策**：每個專案的內業人員**必須**依該專案需求設定要查核的工項（查核項目本身是必要設定，不得省略），**不得**套用公司共用的固定工項分類。工項分類（例如空調風管、給排水、電力設備）與分區（例如一樓 A 區、二樓 B 區）是否使用，**皆**依專案需求選用，不強制每個專案都要建立這兩層組織方式。若專案正式建立分區，查核工項**必須**按分區分開建立與執行；若未建立分區，工區**得**只是同一查核工項的選項或資訊，合併為一個查核工項。
- **狀態**：已決定；分類固定兩層、範本庫複製與名稱規則已由 [KD-47](#kd-47)、[KD-48](#kd-48) 裁定，分區**不**強制為分類的子層，見 [OQ-04](05-open-questions.md#oq-04)（已裁定）；分區代碼等結構化規則仍未定，見 [OQ-03](05-open-questions.md#oq-03)。
- **考慮過但沒選**：全公司共用一套固定工項分類；分區強制作為分類的子層。
- **為什麼選這個**：不同工程專案查核內容差異大，固定分類無法適用所有專案；分區是否需要視專案規模而定，不宜強制。
- **代價**：查核工項的資料模型需要支援「有分區」與「無分區」兩種情境；分類階層與命名規則已由 [KD-48](#kd-48) 裁定（固定兩層、同層名稱不得重複、不設代號），不再待定；仍待後續裁定的只有分區的結構化規則（例如分區代碼，見 [OQ-03](05-open-questions.md#oq-03)）。
- **什麼情況要重新討論**：分區代碼或分區與分類關係的規則裁定後，一併檢視本決策。
- **依據**：負責人決定（#74、#73，2026-09-28）；架構基準 §38 Work Item、§12.8 的未定案項目裁定，見 [OQ-04](05-open-questions.md#oq-04)、[OQ-03](05-open-questions.md#oq-03)。2026-10-02 的補充裁定見 [KD-47](#kd-47)、[KD-48](#kd-48)。

## KD-41：查驗是共通流程，報表樣板與匯入格式是獨立模組

- **決策**：查驗流程**必須**是一套共通機制：內業設定查核項次，現場填結果與實測值並拍佐證照片，內業再產出報表；建立查驗時**不得**選定或處理輸出報表樣板。報表**必須**是獨立的功能模組，**得**匯入不同樣板格式。
- **狀態**：已決定（僅涵蓋以上流程界線）；具體匯入格式、樣板欄位對應、選樣板時機、簽署欄位與 Revision 規則未定，見 [OQ-07](05-open-questions.md#oq-07)。
- **考慮過但沒選**：依範例文件的進料／施工／測試名稱建立多套查驗流程。
- **為什麼選這個**：範例文件的表單差異只是輸出報表的樣板格式，查驗本身的資料蒐集方式不應因此分裂成多套流程。
- **代價**：報表模組需要自行處理樣板匯入與欄位對應，不能假設查驗流程已內建特定樣板結構。
- **什麼情況要重新討論**：報表匯入格式、選樣板時機、簽署與 Revision 規則裁定後，一併檢視本決策。
- **依據**：負責人決定（#77，2026-09-28）；架構基準 §20.5、§20.9 的未定案項目部分裁定，見 [OQ-07](05-open-questions.md#oq-07)。

## KD-42：任務完成後可修正資料，計畫在所有任務完成時自動完成

- **決策**：`Inspection Task` 標記完成後，若資料有錯字、文字或圖片需要修正，現場人員與內業人員**皆得**修改；此為已完成查核後的資料修正，**不要求**重新查核，也**不**因修正而改回待確認或要求再按一次完成，任務維持「已完成」。`Inspection Plan` 底下所有任務都完成時，系統**必須**自動將計畫設為「已完成」；**不開放**人員手動修改計畫狀態。**加註**：依 2026-10-03 對答（[#78 留言](https://github.com/speko-tw/inspect-flow/issues/78#issuecomment-5967467998)），此限制指「不得手動將計畫改為已完成」；「封存」與取消封存為手動，草稿、就緒等其他轉換未定，見 [KD-56](#kd-56)。
- **狀態**：已決定（僅涵蓋以上範圍）；Plan／Task 的自動進行中、任務取消、已完成不重開與封存已由 [KD-56](#kd-56) 補完，報告核發與新版取代見 [KD-57](#kd-57)；Evidence／Report 的其他狀態、其他原因的作廢、失敗與更正路徑未定，見 [OQ-09](05-open-questions.md#oq-09)。專案查核項目被修改時，選「不要重新查核」同樣只更正內容、不重查，選「要」則任務作廢，見 [KD-55](#kd-55)；兩者層級不同：本決策修的是已完成任務自己的資料，KD-55 處理的是專案查核項目（標準）的修改。
- **考慮過但沒選**：任務修正後改回待確認狀態，要求重新完成；開放人員手動修改計畫狀態（負責人已於本次討論中明確撤回）。
- **為什麼選這個**：已完成任務的資料修正屬於更正性質，不是推翻查核結果，不需要重新走一次完成流程；計畫狀態應反映任務進度的客觀結果，不需要人工介入。
- **代價**：需要記錄任務完成後的修改紀錄（誰、何時、改了什麼），具體欄位與機制待規格對齊；計畫的完成判定需要在每次任務狀態變化時重新檢查是否全部完成。
- **什麼情況要重新討論**：若未來確認需要開放人員手動修改計畫狀態，須先由負責人另行裁定，不得逕自實作。
- **依據**：負責人決定（#78，2026-09-28）；架構基準 §18、§20.6、§20.17 的未定案項目部分裁定，見 [OQ-09](05-open-questions.md#oq-09)。

## KD-43：初始化只建系統資料，首次設定用一次性首次登入碼

- **決策**：初始化指令（`make init`）**必須**只建立資料庫、內建 `admin`，並在終端機印出一次**首次登入碼**；**不得**建立範本角色、詢問公司或任何個人資料，**不得**設定 `admin` 的密碼。首次登入碼 24 小時有效，資料庫只存雜湊；輸錯 10 次（15 分鐘內）鎖 15 分鐘，計數與密碼登入失敗分開，被鎖只寫應用程式日誌、不寫稽核紀錄。`admin` 還沒有密碼時重跑初始化指令，作廢舊碼並印出新碼；已設定密碼則拒絕。首次開網頁的流程固定為：輸入首次登入碼、設定 `admin` 密碼（碼隨即作廢）、新增第一個使用者；這段流程的稽核紀錄視為系統事件，操作者記為 `admin`。第一個使用者由系統產生臨時密碼，只在畫面顯示一次，首次登入必須變更；畫面提供「給予 admin 權限」勾選框，預設不勾。`admin` 忘記密碼時，只能在伺服器端用重設指令（互動輸入兩次密碼、寫稽核紀錄）重設；一般使用者的設定密碼指令移除。負責人裁定（#261，2026-09-29）：角色一律由 Admin 之後在系統內自行新增，初始化不建立三個範本角色。
- **狀態**：已決定。
- **考慮過但沒選**：初始化指令詢問並建立兩個帳號、email 與姓名與密碼在指令中輸入（原 [KD-22](#kd-22)）。
- **為什麼選這個**：初始化指令不再經手個人資料與密碼，個人資料與密碼都在網頁上設定；首次登入碼有時效、只存雜湊、有鎖定，被看到也有限度。以上理由是依裁定內容整理，負責人未逐項說明。
- **代價**：使用者多一步輸入首次登入碼；`admin` 已設定密碼後忘記，必須有伺服器端存取才能重設；首次登入碼的鎖定與稽核規則要另外實作與驗收。
- **什麼情況要重新討論**：部署改成多台伺服器、或需要在沒有伺服器端存取的情況下重設 `admin` 密碼時。
- **依據**：負責人裁定（[#259](https://github.com/speko-tw/inspect-flow/issues/259)，2026-09-29）；取代 [KD-22](#kd-22)。

## KD-44：內建 admin 代表系統本身

- **決策**：內建 `admin`（`is_system`）代表系統本身：**不屬於**任何公司，沒有部門、地點、工號、姓名；帳號名稱固定為 `admin`；email 選填。它**不得**被停用，任何人都**不得**收回它的 Admin 權限；它的 `created_by` 指向自己。系統自動觸發的事件，操作者記為 `admin`。
- **狀態**：已決定。
- **考慮過但沒選**：內建 `admin` 也要有公司與姓名（原 [KD-22](#kd-22) 與 [KD-16](#kd-16) 的必填欄位）。
- **為什麼選這個**：`admin` 是安裝時就存在的系統帳號，不是某一個人；初始化又不再詢問個人資料（[KD-43](#kd-43)），沒有資料可填。
- **代價**：`User` 的公司、姓名、email 等欄位對內建 `admin` 要允許空值，資料庫約束與 Service 層要能區分內建帳號與一般帳號。
- **什麼情況要重新討論**：需要讓真人直接使用內建 `admin` 並記錄其個人資料時。
- **依據**：負責人裁定（[#259](https://github.com/speko-tw/inspect-flow/issues/259)，2026-09-29）；內建 `admin` 不能停用、不能被拿掉 Admin、`created_by` 指向自己三點沿用 [KD-22](#kd-22)、[KD-19](#kd-19)。

## KD-45：使用者有帳號名稱，可用帳號名稱或 email 登入

- **決策**：每個 `User` 有內部 UUID，另有**必填**的帳號名稱與 email（內建 `admin` 的 email 例外，見 [KD-44](#kd-44)）；兩者都能登入，輸入含 `@` 視為 email，否則視為帳號名稱。帳號名稱 3～32 字元，英文字母開頭，只能用英文字母、數字與 `.`、`_`、`-`（不可中文、不可 `@`）；不分大小寫，一律存成小寫；保留字為 `admin`、`system`、`root`；只有具 Admin 權限的人能修改，修改要寫稽核紀錄；外部（AD）帳號以外部來源為準，不能手動修改。
- **狀態**：已決定。
- **考慮過但沒選**：只用 email 登入、不設帳號名稱（原 [KD-18](#kd-18)）。
- **為什麼選這個**：沒有 email 或不想用 email 的人也要有登入識別；用有無 `@` 判斷輸入的是哪一種，登入畫面只需要一個輸入欄。以上理由是依裁定內容整理，負責人未逐項說明。
- **代價**：兩個識別都要維持唯一（帳號名稱不分大小寫、email 不分大小寫），改名時要處理既有登入與稽核紀錄的對應；既有資料要回填帳號名稱（內建 `admin` 填 `admin`，其他人取 email `@` 前段轉小寫，重複時加數字）。
- **什麼情況要重新討論**：外部身分來源串接後，帳號名稱的格式或唯一性與外部來源衝突時。
- **依據**：負責人裁定（[#259](https://github.com/speko-tw/inspect-flow/issues/259)，2026-09-29）；取代 [KD-18](#kd-18)。

<a id="kd-46"></a>
## KD-46：使用者的公司是可選的，工號、部門、地點跟著公司

- **決策**：`User` 的中文姓名**必填**、英文姓名選填（內建 `admin` 例外，見 [KD-44](#kd-44)）。人員**不一定**屬於公司，最多連結一家（[KD-23](#kd-23)）。工號、部門、地點在連結公司之前不能填；換公司或解除連結時，這三個欄位清空並寫稽核紀錄；工號在**同一家公司內**不得重複。沒有公司的人（獨立或外部人員）也可以加入專案、被指派角色：專案角色跟著人，不跟著公司。本系統建立的帳號，這些欄位由 Admin 修改；外部來源匯入的帳號，任何人都不能修改這些基本欄位（沿用原 [KD-16](#kd-16)）。
- **狀態**：已決定。
- **考慮過但沒選**：每個人都必須屬於一家公司、工號全系統唯一（原 [KD-16](#kd-16)、[KD-23](#kd-23)）。
- **為什麼選這個**：獨立或外部人員本來就不隸屬於任何一家公司；工號是公司內部編號，不同公司之間可能撞號。以上理由是依裁定內容整理，負責人未逐項說明。
- **代價**：換公司會清掉工號、部門、地點，操作前要提示；工號唯一約束要改成「同公司內唯一」，沒有公司的人不受工號約束。
- **什麼情況要重新討論**：需要一個人同時屬於多家公司時。
- **依據**：負責人裁定（[#259](https://github.com/speko-tw/inspect-flow/issues/259)，2026-09-29）；取代 [KD-16](#kd-16) 的必填欄位規則。

<a id="kd-47"></a>
## KD-47：範本庫是獨立於專案的系統，套用即複製、選用

- **決策**：**必須**有一個獨立於專案的範本庫；所有專案都**得**從範本庫挑項目，**套用（複製）**成自己的查核項目。範本庫為選用，專案**得**不使用查核範本、從零建立查核項目。套用時複製一份，之後修改查核範本只影響之後才套用的專案，**不得**回頭改動已套用的專案；專案**必須**記錄來源查核範本名稱與套用時間（見 [KD-03](#kd-03)）。查核範本的單位有兩種：可以只存單一查核項目，也可以存整個系統（含其下所有查核項目）；套用時也一樣，可套用單一查核項目或整個系統。
- **狀態**：已決定。
- **考慮過但沒選**：專案直接引用範本庫的目前內容，查核範本一改全部連動；要求每個專案都必須從範本庫建立。
- **為什麼選這個**：每個專案要查核的內容不盡相同（[KD-40](#kd-40)），專案需要能自由調整；複製後各自獨立，已進行中的專案不會被查核範本修改影響。以上理由是依裁定內容整理，負責人未逐項說明。
- **代價**：查核範本修改不會同步到已套用的專案，專案要自行更新；套用時必須複製整個結構（分類、查核項目、查核項次、檢查標準、照片要求）並寫入來源與時間。
- **什麼情況要重新討論**：出現「查核範本更新後要通知或同步已套用專案」的需求時。
- **依據**：負責人裁定（[#74 留言](https://github.com/speko-tw/inspect-flow/issues/74#issuecomment-5956038822)，2026-10-02）；[#78 留言](https://github.com/speko-tw/inspect-flow/issues/78#issuecomment-5956039701)（2026-10-02）；查核範本的單位依[負責人裁定（#313，2026-10-02）](https://github.com/speko-tw/inspect-flow/issues/313)；查核範本與報告範本是兩種不同的東西，依[負責人確認（#313，2026-10-02）](https://github.com/speko-tw/inspect-flow/issues/313)，報告範本不受本決策影響，見 [KD-05](#kd-05)。

<a id="kd-48"></a>
## KD-48：查核範本只存結構，分類固定兩層，同一層名稱不得重複

- **決策**：查核範本內容**只存結構**：分類、查核項目、查核項次、檢查標準、照片要求；**不存**現場結果與照片。分類先固定兩層「工程類別 → 系統」，其下為查核項目（試做，日後調整另開 issue）。名稱規則：同一層之下**不得**重名，不同層**得**重名；目前只用名稱、不設代號，需要時另提。專案內是否使用分類與分區，仍依 [KD-40](#kd-40) 選用；分區不是分類的子層。
- **狀態**：已決定（分類層數為試做）；名稱比對的細節（空白、大小寫）未說明，由規格定。
- **考慮過但沒選**：全公司共用一套固定工項分類（[KD-40](#kd-40) 已排除）；查核範本連同現場結果或照片一起存；先不限制分類階層；同時設代號。
- **為什麼選這個**：查核範本是「要查什麼」的結構，現場結果與照片屬於個別專案的執行紀錄；先固定兩層可以先落地、日後依使用情況調整。以上理由是依裁定內容整理，負責人未逐項說明。
- **代價**：固定兩層可能不符合部分工程的分類習慣，要調整時需另開 issue 與規格變更；沒有代號就沒有穩定的短識別，匯入匯出或報表引用時只能靠名稱與內部 UUID（[KD-07](#kd-07)）。
- **什麼情況要重新討論**：試做後發現兩層不夠或太多；需要代號供報表或外部系統引用時。
- **依據**：負責人裁定（[#74 留言](https://github.com/speko-tw/inspect-flow/issues/74#issuecomment-5956038822)，2026-10-02）。

<a id="kd-49"></a>
## KD-49：新增「全系統角色」機制，第一個是範本管理員

- **決策**：系統**必須**新增「全系統角色」機制：這類角色的權限不屬於任何專案，由 Admin 直接指派給人員；它與「專案角色」（掛在 `ProjectMember` 上，見 [KD-27](#kd-27)）、Admin 開關（[KD-24](#kd-24)）是並存、各自獨立的機制，不互相混用。第一個全系統角色是**範本管理員**：**得**新增、修改、刪除查核範本；**得**查看所有專案，並把任何專案的查核項目存成查核範本。把查核範本套用到專案，由「有權限編輯該專案查核項目的人」進行（專案角色的權限），不需要範本管理員身分。查核範本建議加入與審核流程留待之後版本，目前不設。
- **狀態**：已決定；全系統角色清單是否可由 Admin 自訂、除範本管理員之外有哪些角色，裁定沒有說明，由規格確認。
- **考慮過但沒選**：無，#313 未列出替代方案。
- **為什麼選這個**：範本庫獨立於專案（[KD-47](#kd-47)），管理查核範本的權限無法掛在某個專案的成員上，需要跨專案、不屬於任何專案的角色。以上理由是依裁定內容整理，負責人未逐項說明。
- **代價**：授權檢查多一層：先判斷 `is_admin`，再判斷全系統角色，再判斷專案角色，三者不能合併成單一查詢；範本管理員可查看所有專案，指派時須視為敏感權限，並寫稽核紀錄（[KD-29](#kd-29)）。
- **什麼情況要重新討論**：需要更多全系統角色，或要加入查核範本建議與審核流程時。
- **依據**：負責人裁定（[#313](https://github.com/speko-tw/inspect-flow/issues/313) 內文，2026-10-02）；與 [KD-24](#kd-24)、[KD-26](#kd-26)、[KD-27](#kd-27) 並存。

## KD-50：每個項次可有多張照片，每張照片可加現場註記

- **決策**：每個查核項次的佐證照片**得**有多張，最少 1 張（沿用 [KD-38](#kd-38) 的最低覆蓋），**不設**張數上限。總覽照片**得**有多張，全部排在該查核項目組的最前面；仍為選拍，不計入各項次的最低覆蓋。每一張照片（總覽與佐證項次的照片）都**得**加上現場工程師的文字註記（照片註記）：有填寫就**必須**呈現在報告中，留白則不顯示；註記一律保留。照片註記是文字說明，與 [OQ-12](05-open-questions.md#oq-12)（#81）討論的「在照片上畫標註」不同。
- **狀態**：已決定；「註記一律保留」在現場版與內業版之間如何沿用，裁定沒有細說，由規格確認。
- **考慮過但沒選**：每個項次固定一張照片（[KD-38](#kd-38) 已排除）；訂張數上限；總覽照片只能一張。
- **為什麼選這個**：現場實際需要多角度、多張照片佐證同一個項次，註記讓現場工程師能說明照片內容（也用於文件拍照的說明，見 [KD-53](#kd-53)）。以上理由是依裁定內容整理，負責人未逐項說明。
- **代價**：沒有張數上限，儲存容量與報告版面都要預留彈性（[PR-02](02-principles.md#pr-02)）；註記欄位要隨現場版、內業版與報表資料一路帶下去；`Evidence Requirement` 的 `max_count` 對照片不適用。
- **什麼情況要重新討論**：照片量造成容量或報告長度問題時，評估上限；需要在照片上畫標註時，另見 [OQ-12](05-open-questions.md#oq-12)。
- **依據**：負責人裁定（[#75 留言](https://github.com/speko-tw/inspect-flow/issues/75#issuecomment-5956039268)，2026-10-02）；補充 [KD-38](#kd-38)。

## KD-51：本系統定位為工程查核系統，長期涵蓋一級自主檢查與二級監造抽查

- **決策**：InspectFlow 是「工程查核系統」，涵蓋公共與私人工程的施工查驗、材料設備（進料）查驗等。長期使用對象包含廠商自主檢查（一級）與監造抽查（二級），**必須**在同一系統串起來；現階段甲方以監造／PCM 抽查為主，MVP 以抽查紀錄表為核心。資料結構**必須**預留「自主檢查／抽查」的區分與「由誰檢查」。檢查時機與停留點，MVP **不做**，之後再加。缺失改善追蹤屬 [#76](https://github.com/speko-tw/inspect-flow/issues/76)（0.7.x）、簽認屬 [#77](https://github.com/speko-tw/inspect-flow/issues/77)（0.9.x），不在此決定。
- **狀態**：已決定。
- **考慮過但沒選**：只做抽查、不考慮自主檢查（資料結構不預留區分）。
- **為什麼選這個**：一級自主檢查與二級抽查是同一條品管鏈，分成兩套系統會讓資料無法串接；MVP 先聚焦目前甲方的實際用法。以上理由是依裁定內容整理，負責人未逐項說明。
- **代價**：資料模型要多預留「檢查層級」與「檢查者」欄位，即使 MVP 只用到抽查；一級自主檢查的流程與畫面不在 MVP 範圍，日後要另行規格。
- **什麼情況要重新討論**：要開始支援廠商自主檢查，或要加入檢查時機與停留點時。
- **依據**：負責人裁定（[#313](https://github.com/speko-tw/inspect-flow/issues/313) 追加裁定第 15～18 題，2026-10-02）。

## KD-52：每個查核項次的檢查標準分文字與數值兩種

- **決策**：每個查核項次**得**選用「文字標準」或「數值標準」。文字標準沿用 [KD-37](#kd-37)：按計畫書原文以文字記錄，系統不解析。數值標準的欄位為：標準值、條件（`≤`、`≥`、`＝`、範圍）、單位、容許誤差。0.3.x 的查核範本**只定義**這兩種標準欄位；實測值輸入與自動判定屬 [#76](https://github.com/speko-tw/inspect-flow/issues/76)（0.7.x）。
- **狀態**：已決定（僅涵蓋以上範圍）；實測值如何輸入、是否自動判定、範圍條件的資料表示，待 0.7.x 與規格處理。
- **考慮過但沒選**：數值標準也只存文字原文（[KD-37](#kd-37) 目前做法）。
- **為什麼選這個**：標準值、條件、單位與容許誤差結構化後，日後才能做實測值判定；0.3.x 先定義欄位，避免到 0.7.x 才回頭改查核範本結構。以上理由是依裁定內容整理，負責人未逐項說明。
- **代價**：查核範本與專案複本要多存一組數值標準欄位；[KD-37](#kd-37)「系統不解析、不自動判定」的範圍縮為文字標準與 #76 裁定前的暫行規則，兩者需在規格對齊。
- **什麼情況要重新討論**：#76 裁定實測值輸入與自動判定規則時。
- **依據**：負責人裁定（[#313](https://github.com/speko-tw/inspect-flow/issues/313) 追加裁定第 15～18 題，2026-10-02）。

## KD-53：MVP 佐證只收照片，佐證類型未來可擴充

- **決策**：MVP 的佐證**只收照片**。額外文件（例如出廠證明、試驗報告）拍成照片，並以照片註記說明（[KD-50](#kd-50)）；報告功能（0.9.x）提供「補充文件」區，可附文件或連結；串接文件管理系統屬未來。佐證類型未來可能擴充（例如文件、量測數值、簽名、影片）。**不設**固定的檢討時點：有需要時開 issue，由負責人裁定後寫入規格再實作。原 `TEXT` 是否仍保留為獨立的 Evidence 類型，裁定沒有說明，待規格確認。
- **狀態**：已決定。
- **考慮過但沒選**：MVP 同時支援 `NUMBER`、`BOOLEAN`、`SIGNATURE`、`DOCUMENT`（[OQ-20](05-open-questions.md#oq-20) 列出的另一選項）。
- **為什麼選這個**：MVP 先聚焦照片佐證，額外文件以照片加註記處理已能滿足現場需求，其餘類型有需要再加。以上理由是依裁定內容整理，負責人未逐項說明。
- **代價**：文件類佐證在 MVP 只有照片畫質，沒有原始檔案；補充文件要等 0.9.x 的報告功能才能附上。
- **什麼情況要重新討論**：實際出現要附原始文件或檔案、量測值、簽名、影片的需求時，由負責人開 issue 裁定。
- **依據**：負責人裁定（[#88 留言](https://github.com/speko-tw/inspect-flow/issues/88#issuecomment-5956040233)，2026-10-02）；補充見 [#88 補充留言](https://github.com/speko-tw/inspect-flow/issues/88#issuecomment-5956189277)（2026-10-02）。

## KD-54：查核項次結果分符合／不符合／不適用，並規定各結果的必填內容

- **決策**：每個查核項次的結果有三種：「符合」「不符合」「不適用」（N/A）。
  - 選「不符合」時，**必須**選嚴重度（輕微、一般、嚴重），並**必須**填註解說明問題。
  - 選「不適用」時，**必須**填原因；照片選填。
  - 項次設有實測欄位時，**必須**全部填寫才能選「符合」或「不符合」；量不到時改選「不適用」並寫原因。
  - 實測欄位的型別由內業設定：「數字」（**必須**設單位，只接受數字）或「文字」（自由填寫）。項次設有數值標準時，對應實測欄位的單位**必須**與該數值標準單位相同，由系統自動帶入、不得另設；現場自行換算，單位換算不在本次範圍。
  - 版本劃分（依 [KD-52](#kd-52) 的範圍劃分整理，不是負責人裁定）：實測欄位的定義（型別、單位）屬範本結構，由 0.3.x 範本規格定義；現場填值屬 0.7.x（依 KD-52 與 [06](06-versioning-and-milestone-governance.md)）。
  - 不在本次裁定：不符合後的改善追蹤與限期複查、系統自動判定，維持在 0.7.x；系統**不得**依標準值自動判定的規定仍依 [KD-37](#kd-37)。
- **狀態**：已決定（僅涵蓋以上範圍）；嚴重度對任務完成判定與報告呈現的影響，裁定沒有說明，待規格或 0.7.x 處理。
- **考慮過但沒選**：維持只有符合與不符合、不擴充欄位（[OQ-06](05-open-questions.md#oq-06) 列出的另一選項）。
- **為什麼選這個**：現場有些項次量不到或不適用，只有符合與不符合會逼人選錯；不符合要有嚴重度與說明、不適用要有原因，之後才分得出差別；實測欄位全部填完才能判定，避免漏量。以上理由是依裁定內容整理，負責人未逐項說明。
- **代價**：每個查核項次要多記錄嚴重度、註解與不適用原因；內業要為每個實測欄位設定型別，數字欄位還要設單位。[KD-37](#kd-37)「標準值按原文以文字輸入、系統不解析」與「數字欄位必須設單位、只接受數字」的適用範圍，裁定沒有說明，需在規格對齊。數值標準與對應實測欄位使用相同單位，現場需自行換算。
- **什麼情況要重新討論**：0.7.x 裁定不符合後的改善追蹤、限期複查或自動判定時；現場試用發現三種結果或必填規則不敷使用時。
- **依據**：負責人裁定（[#76 留言](https://github.com/speko-tw/inspect-flow/issues/76#issuecomment-5965076758)，2026-10-03）；補完 [OQ-06](05-open-questions.md#oq-06) 原本未定的部分，與 [KD-37](#kd-37)、[KD-52](#kd-52) 並用；單位相同、不得另設，依負責人裁定（[#76 留言](https://github.com/speko-tw/inspect-flow/issues/76#issuecomment-5965931420)，2026-10-03）。實測欄位定義與填值的版本劃分是依 KD-52 的範圍劃分整理，裁定本身沒有說明。

<a id="kd-55"></a>
## KD-55：修改專案查核項目時詢問是否重新查核，選「要」則用到該項次的任務全部作廢

- **決策**：
  - 內業修改專案查核項目並存檔時，系統**必須**跳出選單詢問「這次修改要讓現場重新查核嗎？」，並清楚警告：選「要」時，過去的查核會作廢、任務改為「尚未查核」。
  - 選「要」：同一專案內用到被修改項次的任務，不論未開始、進行中或已完成，**全部作廢**，以新標準重新查核。
  - 選「不要」：只更正內容（例如錯字），不重查；同一專案內用到該項次的已建立任務（未開始、進行中、已完成）**一併更正**為修改後的內容，只更正文字，不動結果與照片，任務狀態不變；已發出的報告不受影響。這是 [PR-04](02-principles.md#pr-04)「任務需求快照不改寫」的明確例外，僅限內業選擇「不要」重新查核的更正；系統記錄誰、何時、改了什麼；精神與 [KD-42](#kd-42)（已完成任務可修正錯字、不重查）一致。
  - 系統**必須**記錄是誰、何時、選了什麼。
  - 作廢的照片、結果與當時標準**不刪除**，標示「標準變更作廢」存檔，內業人員**必須**找得到；報告不使用作廢資料。舊任務紀錄整份保留、只標示作廢，不改寫，符合 [PR-04](02-principles.md#pr-04)。
  - 系統資料與報告分開：已發出的報告存在報告系統，不受影響；之後產生報告一律從系統資料即時撈取。
  - 只影響用到被修改項次的任務。
- **狀態**：已決定（僅涵蓋以上範圍）。**未定**：作廢後重新查核是讓同一任務重來，還是另開新任務，屬 0.4.x 規格設計；「尚未查核」對應哪個任務狀態，裁定沒有說明，待 0.4.x 規格確認；其他原因的作廢、失敗路徑，見 [OQ-09](05-open-questions.md#oq-09)。完成的計畫遇作廢退回進行中、任務取消與已完成任務不重開，見 [KD-56](#kd-56)。
- **與其他議題的關係**：作廢資料不刪除與 [G-05](05-open-questions.md#g-05)（證據刪除與保留）有關，但 G-05 仍未裁定，本決策不代為決定證據刪除 API 與保留期限；已發出報告不受影響、之後從系統資料即時撈取，與 [G-06](05-open-questions.md#g-06)／[G-07](05-open-questions.md#g-07)（報告狀態與快照邊界）有關，這兩題仍未裁定，報告狀態機與快照邊界不因本決策而定。
- **考慮過但沒選**（出自裁定前的情境對答，紀錄見 [#78 留言](https://github.com/speko-tw/inspect-flow/issues/78#issuecomment-5966398101)）：
  - 已建立的任務一律維持舊標準，要用新標準就刪除重建。
  - 只有未開始的任務自動換新標準，已開始或已完成的不動。
  - 內業改標準時，系統詢問是否套用到未開始的任務（負責人先選此項，接著補充「標準改了就要重查」，被整體做法取代）。
  - 怎樣算「已開始」（打開就算、存下資料才算、只有完成才不動）：被「不論進度一律重查」取代。
  - 已完成但未出報告的任務：不動，或交給內業逐一勾選是否重查；負責人選一律重查。
  - 作廢的照片與結果真的刪除；負責人選作廢存檔，內業要找得到。
  - 判斷是否觸發重查：任何修改都觸發（含錯字），或由系統自動判斷「改到要查什麼、怎樣算合格」才觸發；最後採用的是每次修改都由內業自己選，系統記錄並清楚警告作廢後果，即本決策。
- **為什麼選這個**：標準改了，舊查核不一定還成立，所以由內業決定要不要重查；只改錯字不該逼現場重做；作廢資料不刪除，之後才能追查當時依據什麼標準、誰決定重查。以上理由是依裁定內容整理，負責人未逐項說明。
- **代價**：選「要」會讓已完成的任務退回重查，現場要重做；作廢資料要額外保留並讓內業查得到；報告從系統資料即時撈取，已發出的報告與之後重新產生的報告內容可能不同（依裁定內容整理，與 G-06／G-07 相關）；記錄「誰、何時、選了什麼」的具體欄位待規格制定。
- **什麼情況要重新討論**：0.4.x 規格設計「作廢後重來或另開任務」時；G-05、G-06、G-07 裁定後，一併檢視本決策是否相容；現場試用發現詢問流程不敷使用時。
- **依據**：議題背景為架構基準 §2.5、§12.9（需求快照與套用複製）、§18（狀態機）；裁定為負責人裁定（[#78 留言](https://github.com/speko-tw/inspect-flow/issues/78#issuecomment-5966290670)，2026-10-03；選「不要」時一併更正已建立任務見[補充裁定](https://github.com/speko-tw/inspect-flow/issues/78#issuecomment-5966446983)，同日），補完 [OQ-09](05-open-questions.md#oq-09) 的「專案副本與任務快照分工」；與 [KD-03](#kd-03)、[KD-42](#kd-42)、[PR-04](02-principles.md#pr-04) 並用。

<a id="kd-56"></a>
## KD-56：計畫狀態自動進行，任務可取消但已完成不重開，有不符合仍可完成並標示「有缺失」

- **決策**：
  - 計畫的「進行中」「已完成」由系統自動變更：計畫有任務派出後，系統**必須**自動將計畫改為「進行中」；底下任務全部完成時，系統**必須**自動改為「已完成」，人員**不得**手動將計畫改為已完成（[KD-42](#kd-42)）；「封存」與取消封存由內業**手動**操作；草稿、就緒等其他轉換未定，待規格。
  - 任務取消：內業**得**取消任務，**必須**填原因；已取消的任務保留、顯示「已取消」，**不計入**計畫完成判斷。
  - 已完成的任務**不開放**重新打開。要重新查核，走 [KD-55](#kd-55)（修改專案查核項目並選「要」重新查核，任務作廢）；錯字與照片修正依 [KD-42](#kd-42)，任務維持已完成。
  - 計畫已完成後，若有任務因 [KD-55](#kd-55) 作廢，系統**必須**自動將計畫退回「進行中」，重查完成後再自動改回「已完成」。已封存的計畫**必須**先取消封存，才能修改標準。
  - 任務有「不符合」的項次（[KD-54](#kd-54)）時，資料齊全即可完成任務，計畫照常自動完成；任務清單與報告**必須**明顯標示「有缺失」。不符合後的改善追蹤與限期複查屬 0.7.x，不在本決策範圍（見 [KD-54](#kd-54)）。
- **狀態**：已決定（僅涵蓋以上範圍）。**未定**：計畫「草稿」「已就緒」等其他狀態與轉換規則，仍依 [OQ-09](05-open-questions.md#oq-09) 目前暫定；怎樣算任務「派出」；取消任務的細節（已完成或進行中的任務能否取消、取消後能否恢復、計畫底下任務全部取消時計畫算什麼狀態）；取消封存的操作與權限；「有缺失」是獨立的狀態值還是依不符合結果顯示的標示；以上裁定沒有說明，待 0.4.x 規格（`state-machines`）處理。
- **權限**：取消任務、封存與取消封存**得**由哪些人執行，依 [OQ-08](05-open-questions.md#oq-08)、[KD-24](#kd-24)～[KD-29](#kd-29)（Admin 自訂角色與權限代碼）設定，具體代碼由規格制定；裁定只說「內業」，這裡不寫死職稱。
- **考慮過但沒選**（出自裁定前的情境對答，紀錄見 [#78 留言](https://github.com/speko-tw/inspect-flow/issues/78#issuecomment-5967478534)）：
  - 計畫狀態全自動、不設封存；開始與封存都由內業手動。
  - 任務只能刪除、不留紀錄；改由現場提出、內業確認才取消。
  - 計畫已完成後遇標準變更作廢：計畫維持「已完成」不退回。
  - 有不符合的任務：不標示就可完成；或要改善完才算完成。
- **為什麼選這個**：以下理由是依裁定內容整理，負責人未逐項說明。計畫狀態反映任務進度的客觀結果，由系統自動變更才不會與任務脫節（延續 [KD-42](#kd-42)）；封存是內業整理案件的管理動作，系統無從判斷，所以留給人。取消的任務保留並要求原因，事後才查得到為什麼不做；不計入完成判斷，計畫才不會被取消的任務卡住。已完成不重開、重查一律走標準變更，讓「改了標準才重查」只有一條路，歷史（[PR-04](02-principles.md#pr-04)）才不亂。完成的計畫遇作廢退回進行中，狀態才不會與實際進度矛盾。有不符合不擋完成，是因為查核的工作是如實記錄現場，不是要求全部合格；改善屬 0.7.x。
- **代價**：計畫狀態會在任務變化時自動來回（完成、退回、再完成），每次任務狀態變化都要重新判斷；封存的計畫要改標準得先取消封存，多一步；「有缺失」要在清單與報告上額外呈現。
- **什麼情況要重新討論**：現場試用發現計畫自動狀態不敷使用（例如需要手動結案）；0.7.x 決定不符合後的改善追蹤時，一併檢視「有缺失」與任務完成的關係；`state-machines` 規格整理出裁定沒有說明的狀態與轉換時。
- **依據**：議題背景為架構基準 §18（狀態機）；裁定為負責人裁定（[#78 留言](https://github.com/speko-tw/inspect-flow/issues/78#issuecomment-5967467998)，2026-10-03，第 1、2、3、5 題與第 2 題補充）；補完 [OQ-09](05-open-questions.md#oq-09) 的計畫與任務部分；與 [KD-42](#kd-42)、[KD-54](#kd-54)、[KD-55](#kd-55) 並用。

<a id="kd-57"></a>
## KD-57：報告由有權限者直接核發、不需送審，有錯時出新版取代舊版

- **決策**：
  - 報告產生後，有權限者**得**直接核發，**不需**送審；審核流程之後再加，本次不做。
  - 已核發的報告有錯時，**必須**出新版取代；舊版**必須**保留，並標示「已被新版取代」，**不得**覆蓋或刪除（與 [PR-06](02-principles.md#pr-06)「已核發版次不可覆蓋」一致）。
  - 「有權限者」依 [OQ-08](05-open-questions.md#oq-08)、[KD-24](#kd-24)～[KD-29](#kd-29)（Admin 自訂角色與權限代碼），不寫固定職稱；核發對應哪一個權限代碼，由規格制定。
- **狀態**：已決定（僅涵蓋以上範圍）。**未定**：`Report` 的其他狀態（產製中、產製失敗等）、完整狀態機與版次快照邊界，仍依 [G-06](05-open-questions.md#g-06)、[G-07](05-open-questions.md#g-07) 待規格整合；[PR-15](02-principles.md#pr-15) 的「產製失敗不得誤標為已完成」不因本決策改變。審核流程加入前，送審與核准類狀態（原 §20.6 列舉的 `UNDER_REVIEW`、`APPROVED`）是否保留，裁定沒有說明，待規格確認。「新版」與版次序號（REV.n）的對應、舊版是否仍可下載，裁定沒有說明，待規格確認。
- **與其他議題的關係**：[KD-55](#kd-55) 規定已發出的報告不受標準變更影響、之後產生的報告從系統資料即時撈取；本決策規定發出的報告有錯時如何更正（出新版、舊版標示被取代），兩者都不允許悄悄改變已核發的內容。
- **考慮過但沒選**（出自裁定前的情境對答，紀錄見 [#78 留言](https://github.com/speko-tw/inspect-flow/issues/78#issuecomment-5967478534)）：
  - 報告一定要審，且「送審」與「核准」分成兩個動作。
  - 是否送審改成每個專案可開關。
  - 已核發報告有錯時，舊版直接作廢。
- **為什麼選這個**：以下理由是依裁定內容整理，負責人未逐項說明。第一階段先把產出與核發做通，審核流程等實際需要再加，避免一開始就綁死流程；舊版保留並標示被取代，之後才查得到當時交付的內容，也符合已核發版次不可覆蓋的原則。
- **代價**：核發前沒有第二個人把關，錯誤要靠事後出新版更正；舊版要長期保存並在介面上標示，報告列表要能分辨現行版與被取代的版本。
- **什麼情況要重新討論**：加入審核流程時（須另行裁定送審與核准的規則，不得逕自實作）；G-06、G-07 裁定後，一併檢視本決策是否相容。
- **依據**：議題背景為架構基準 §20.6–20.8（Report 狀態與版次）、§18（狀態機）；裁定為負責人裁定（[#78 留言](https://github.com/speko-tw/inspect-flow/issues/78#issuecomment-5967467998)，[#94 留言](https://github.com/speko-tw/inspect-flow/issues/94#issuecomment-5967468330)，2026-10-03，第 4 題）；部分裁定 [G-06](05-open-questions.md#g-06)；與 [KD-55](#kd-55)、[PR-06](02-principles.md#pr-06)、[PR-15](02-principles.md#pr-15) 並用。

## 技術棧卡片

卡片的「不要用」指出與本階段目標不合的做法。標為「建議」或「待定」時，卡片不替團隊拍板。

<a id="stack-backend-language"></a>
### Backend 語言

- **選用**：Python 3.12 作為基準版本。
- **負責什麼**：Backend API、業務規則、報告與影像處理。
- **狀態**：建議。
- **為什麼**：生態與團隊維護成本適合現階段；依賴的精確版本由 lockfile 固定。
- **不要用**：未經驗證就追最新 Python major。
- **未來升級路線**：新版 Python 經依賴、測試及 image 驗證後再升級。
- **依據**：架構基準 §4.1。

<a id="stack-web-api"></a>
### Web API

- **選用**：FastAPI；API 採 REST／JSON，照片上傳採 `multipart/form-data`。
- **負責什麼**：外部 API、驗證入口、上傳、授權入口與 OpenAPI 文件。
- **狀態**：建議（FastAPI）；API 邊界已決定，見 [KD-01](#kd-01)。
- **為什麼**：型別整合與文件產生方便內部系統開發。
- **不要用**：把大量業務邏輯寫在 route，或讓前端直接連資料庫。
- **未來升級路線**：維持 `/api/v1` 契約；框架版本由測試後的 lockfile 固定。
- **依據**：架構基準 §4.2、§7.1、§14。

<a id="stack-asgi-server"></a>
### ASGI 伺服器

- **選用**：uvicorn。
- **負責什麼**：本機開發時啟動 FastAPI（`make run-backend`）。
- **狀態**：建議；正式部署用什麼伺服器不在此決定，留給 pilot-deployment（[#109](https://github.com/speko-tw/inspect-flow/issues/109)）。
- **為什麼**：FastAPI 需要 ASGI 伺服器才能執行；uvicorn 是它文件的預設選擇，支援開發用的自動重載。
- **不要用**：把本機開發的啟動方式直接當成正式部署設定。
- **未來升級路線**：部署方式定案後再補正式環境的伺服器設定；依賴版本由 lockfile 固定。
- **依據**：負責人裁定（[PR #212 留言](https://github.com/speko-tw/inspect-flow/pull/212#issuecomment-5851963155)，2026-09-27）；架構基準無對應章節。

<a id="stack-api-schema"></a>
### API Schema

- **選用**：Pydantic v2 系列。
- **負責什麼**：Request／Response 型別與輸入驗證。
- **狀態**：建議。
- **為什麼**：在資料進入 Service 前建立清楚的 API 契約。
- **不要用**：只在前端驗證，或把未驗證的 JSON 直接交給業務規則。
- **未來升級路線**：隨 API 契約演進調整 schema；精確依賴版本由 lockfile 固定。
- **依據**：架構基準 §4.3、§16.1。

<a id="stack-orm"></a>
### ORM 與資料存取

- **選用**：SQLAlchemy 2.x，見 [KD-06](#kd-06)。
- **負責什麼**：讓 Service 存取 SQLite／PostgreSQL。
- **狀態**：已決定。
- **為什麼**：降低資料庫切換時的程式改動。
- **不要用**：到處散落 SQLite 專用 raw SQL；需要 raw SQL 時要標明資料庫相依性。
- **未來升級路線**：先以 PostgreSQL 整合測試確認相容性，再搬移資料。
- **依據**：架構基準 §4.4、§7.3、§32、§37 ADR-005。

<a id="stack-migration"></a>
### Database Migration

- **選用**：Alembic，見 [KD-06](#kd-06)。
- **負責什麼**：建立、升級與追蹤正式 schema。
- **狀態**：已決定。
- **為什麼**：每次 schema 變更都要可審查、可重現。
- **不要用**：正式環境靠 `create_all()` 或未記錄的手動 ALTER。
- **未來升級路線**：SQLite 與 PostgreSQL 都要跑 migration 驗證。
- **依據**：架構基準 §4.5、§22A.9、§27.3。

<a id="stack-frontend"></a>
### Frontend

- **選用**：React、TypeScript、Vite；Admin／Field 共用單一程式庫，見 [KD-12](#kd-12)。
- **負責什麼**：現場與後台操作畫面、API Client、前端建置。
- **狀態**：建議（工具）；已決定（單一程式庫，見 [KD-12](#kd-12)）。
- **為什麼**：支援手機介面與 Dashboard，TypeScript 可減少欄位錯誤。
- **不要用**：把資料庫或 storage key 當作前端存取契約。
- **未來升級路線**：如差異擴大，評估拆分；實際套件版由 lockfile 固定。
- **依據**：架構基準 §5.1–5.2、§37 ADR-008。

<a id="stack-pwa"></a>
### PWA

- **選用**：現場 Web 朝 PWA 相容設計；MVP 先採 Online-first。
- **負責什麼**：手機與平板使用路徑，保留日後安裝與離線草稿能力。
- **狀態**：建議；完整離線同步是延後能力。
- **為什麼**：工程師可用 iPhone、iPad 或 Android 開啟 Web App。
- **不要用**：把 PWA 相容等同已完成離線同步。
- **未來升級路線**：依 Pilot 網路資料，再加入 cache、draft、待上傳佇列與同步。
- **依據**：架構基準 §5.3、§13A.14、§34–35。

<a id="stack-database"></a>
### 資料庫

- **選用**：MVP 用 SQLite；`foreign_keys = ON`、WAL **應**在連線初始化時確認。見 [KD-08](#kd-08)。
- **負責什麼**：人員、專案、範本、任務、證據 metadata 與報告資料。
- **狀態**：已決定（SQLite）；建議（兩項 PRAGMA）。
- **為什麼**：Pilot 規模可先降低維運負擔。
- **不要用**：多台後端經 NAS 共用同一個 SQLite 檔。
- **未來升級路線**：併發、鎖定或維運需求增加時轉 PostgreSQL。
- **依據**：架構基準 §9–10、§32、§37 ADR-003。

<a id="stack-photo-storage"></a>
### 照片儲存

- **選用**：本機持久化儲存與 Storage 介面；檔案和 DB metadata 分離。見 [KD-02](#kd-02)。
- **負責什麼**：現場版、內業版兩張照片的檔案存取（見 [KD-32](#kd-32)）。
- **狀態**：已決定（分離與介面）；建議（第一版本機儲存）。
- **為什麼**：避免照片 BLOB 撐大 SQLite，也保留遷移彈性。
- **不要用**：原檔名當唯一 key；業務邏輯直接寫死檔案路徑。
- **未來升級路線**：以 MinIO、S3 或 NAS 實作相同 Storage 介面；照片版本模型見 [KD-32](#kd-32)、[G-02](05-open-questions.md#g-02)（已裁定）。
- **依據**：架構基準 §2.3、§7.4、§13.1–13.2、§33。

<a id="stack-image-processing"></a>
### 現場影像處理

- **選用**：前端即時預覽；後端可用 Pillow 依編輯參數產生內業版。見 [KD-32](#kd-32)、[KD-33](#kd-33)、[OQ-14](05-open-questions.md#oq-14)。
- **負責什麼**：現場端裁切、旋轉、亮度等編修，以及內業端加工產生內業版。
- **狀態**：待定（Frontend Render 或 Backend Render）；照片只保存現場版、內業版兩張已決定（見 [KD-32](#kd-32)）。
- **為什麼**：前端預覽反應快；後端處理有利結果一致與重現。
- **不要用**：另外保存原始拍攝檔案或編輯中間版本；提供會增刪現場內容的標準修圖功能。
- **未來升級路線**：離線時先存現場版與編輯參數，連線後再上傳及產生內業版；見 [G-03](05-open-questions.md#g-03)。
- **依據**：架構基準 §13A.2、§13A.5–13A.8、§13A.14；照片版本模型依負責人決定（#90～#92，2026-09-28）。

<a id="stack-docx"></a>
### DOCX 產製

- **選用**：版本化的報告範本（DOCX 報告版面）；Python 端**應**先評估 `python-docx`，複雜樣板可評估 `docxtpl`。見 [KD-05](#kd-05)。
- **負責什麼**：用 Report View Model 產生可編輯的正式 Word 文件。
- **狀態**：已決定（DOCX 輸出與報告範本版本）；建議（函式庫）。
- **為什麼**：業主與標案常沿用 Word 表單；版次要能對應報告範本的版本。
- **不要用**：從瀏覽器 UI state 拼正式報告，或把 DOCX 當暫存下載。
- **未來升級路線**：增加不同業主樣板與 View Model Builder，不改歷史文件。
- **依據**：架構基準 §20.2–20.5、§20.19、§37 ADR-009。

<a id="stack-pdf"></a>
### PDF 轉換

- **選用**：以 DOCX 為來源產出 PDF；轉換器待 Pilot 驗證，見 [KD-05](#kd-05)、[OQ-15](05-open-questions.md#oq-15)。
- **負責什麼**：產生提交與歸檔用 PDF。
- **狀態**：已決定（PDF 輸出）；待定（LibreOffice Headless 或受控轉換服務）。
- **為什麼**：兩種格式要共享報告資料與正式版面。
- **不要用**：只以 HTML 列印 PDF 當正式報告；未實測就指定 Production 轉換器。
- **未來升級路線**：依字型、表格、圖片、頁碼、分頁及簽名欄實測結果選轉換服務。
- **依據**：架構基準 §20.3–20.4、§20.20–20.22。

<a id="stack-auth"></a>
### 認證與授權

- **選用**：內部帳號搭配 Server-managed Session 與 HttpOnly Cookie（Secure、SameSite），見 [KD-30](#kd-30)；密碼以 Argon2id 雜湊，見 [KD-31](#kd-31)。兩者由負責人裁定，見 [OQ-13](05-open-questions.md#oq-13)。
- **負責什麼**：登入、目前使用者與 API 權限檢查。
- **狀態**：建議（內部帳號）；已決定（Session 與 HttpOnly Cookie、Argon2id，見 [KD-30](#kd-30)、[KD-31](#kd-31)）；已決定（權限機制，見 [KD-24](#kd-24)～[KD-29](#kd-29)）。
- **為什麼**：先滿足內部系統需求，不必在 MVP 建完整 OAuth 基礎設施。
- **不要用**：把長效 JWT 直接放在 browser localStorage。
- **未來升級路線**：`User` 已預留外部身分來源欄位與同步比對規則，見 [KD-20](#kd-20)；實際串接方式（含 Corporate SSO）另開「外部身分同步」規格，見 [docs/specs/README.md](../specs/README.md#index)，本卡不預先寫串接方式。角色矩陣已裁定，見 [OQ-08](05-open-questions.md#oq-08)。
- **依據**：架構基準 §17、§35、§36；Session 與密碼雜湊為負責人決定（#82，2026-09-26）。

<a id="stack-deployment"></a>
### 部署

- **選用**：Linux Server、Docker Engine、Docker Compose 與版本化 image，見 [KD-09](#kd-09)。
- **負責什麼**：啟動 Web、API、Reverse Proxy；掛載持久化資料。
- **狀態**：已決定。
- **為什麼**：單機 Pilot 可重現部署與更新，不先引入多節點編排。
- **不要用**：正式環境臨時改 container 程式或把資料放在暫存層。
- **未來升級路線**：第二階段可在 Compose 接 PostgreSQL；多節點需求再評估編排。
- **依據**：架構基準 §22.1、§22.5–22.8、§22A.12、§37 ADR-011。

<a id="stack-reverse-proxy"></a>
### Reverse Proxy 與 HTTPS

- **選用**：正式環境提供 HTTPS；Caddy、Nginx 或企業現有 Proxy 可選。見 [KD-09](#kd-09)。
- **負責什麼**：將 `/api/*` 導向後端，其餘請求導向前端。
- **狀態**：已決定（HTTPS）；建議（Caddy）；待定（正式 Proxy 選型）。
- **為什麼**：使用者不需要直接連 API 容器埠。
- **不要用**：把 API 或未受控資料庫埠直接暴露給一般使用者。
- **未來升級路線**：可改接企業 Proxy 或 Load Balancer，保留外部 HTTPS 入口。
- **依據**：架構基準 §22.5、§22.10–22.11。

<a id="stack-tests"></a>
### 測試工具

- **選用**：Backend 以 pytest；Frontend component 可用 Vitest；關鍵流程可用 Playwright。
- **負責什麼**：驗證 task generation、快照、Evidence、權限、完整使用者流程與 PostgreSQL 相容性。
- **狀態**：建議（工具）；關鍵流程與跨資料庫驗證為來源要求。
- **為什麼**：任務與正式報告的資料正確性要能重複驗證。
- **不要用**：只測 UI 顯示而略過後端完成驗證或報告內容。
- **未來升級路線**：隨正式報告樣板增加 DOCX/PDF 資料與版面測試。
- **依據**：架構基準 §13A.15、§20.20、§27.1–27.4。

<a id="stack-ci"></a>
### CI

- **選用**：GitHub Actions；每次 PR 執行 lint、後端測試、前端測試、build 與 PostgreSQL 相容性測試。見 [KD-09](#kd-09)。
- **負責什麼**：在版本化 image 進入正式發布前擋下失敗變更。
- **狀態**：已決定（CI 閘門）；已決定（CI 平台採 GitHub Actions，團隊於 [#5](https://github.com/speko-tw/inspect-flow/issues/5) 選定，非架構基準來源）。理由：repo 在 GitHub，檢查結果可直接接上分支保護與 PR 審查。
- **為什麼**：正式環境只部署已審查、已建置、已驗證的產物。
- **不要用**：CI 失敗仍發布，或在 Production 現場編譯臨時版本。
- **未來升級路線**：部署自動化可稍後加入；先維持可重現的手動發布流程。
- **依據**：架構基準 §22A.4–22A.7、§28、§37 ADR-011。

<a id="stack-code-quality"></a>
### 程式品質工具

- **選用**：Python 用 ruff（format 與 lint）；Frontend 用 Prettier（格式）、ESLint（lint）、TypeScript（型別）；Python 型別檢查用 pyright。
- **負責什麼**：基本 lint、格式與型別檢查。formatter 管排版、linter 管寫法、型別檢查器管型別，三者不重疊。
- **狀態**：
  - 已決定：ruff、ESLint、TypeScript、Prettier（團隊於 [#5](https://github.com/speko-tw/inspect-flow/issues/5) 選定，非架構基準來源）；起始設定見 `skeleton` 規格。
  - 已決定：pyright，先 `basic`、再逐個模組改 `strict`（團隊於 [#5](https://github.com/speko-tw/inspect-flow/issues/5) 裁定 [OQ-16](05-open-questions.md#oq-16)）。
  - 已決定：程式碼行寬上限 79 字元，依 PEP 8，全專案程式碼一律適用（專案負責人指定，非架構基準來源；Markdown 文件不受此限）；formatter 與 linter 設定**必須**與之一致。
  - Python 風格以 PEP 8 為基準。起始規則集與新增規則的方式由 `skeleton` 規格與設定檔維護。
- **為什麼**：維持基本一致性，同時避免 MVP 一開始導入過多規則。pyright 與 VS Code 的 Pylance 同一引擎，編輯器與 CI 的結果一致。
- **不要用**：未經團隊評估就把多套重疊的 lint 或架構框架加入發布閘門。
- **未來升級路線**：依程式量與缺陷資料調整檢查；pyright 逐個模組改為 `strict`。
- **依據**：架構基準 §29。
