**這份文件回答**：InspectFlow 選了哪些架構方向？各項工具負責什麼？
**什麼時候讀**：選技術、調整模組邊界、規劃資料遷移、製作報告或部署服務時。

本文件保留 KD-01 到 KD-69 的編號（KD-60、KD-67 已整併進 KD-69，編號不重用）。技術棧卡片另標「已決定／建議／待定」。卡片狀態依架構基準正文判定，不以 §36 的表格直接推定。規則強度見本目錄 README；尚未定案的細節見 [待決議](05-open-questions.md)。

## 關鍵決策

<a id="kd-01"></a>
## KD-01：外部用戶端只透過後端 API 存取資料

- **決策**：Field Web、Admin Web 等外部用戶端**必須**經後端 API 讀寫資料；前端**不得**直接連資料庫或檔案儲存。後端 Report Service 可直接使用服務、資料存取與儲存介面，不必呼叫自己的 HTTP API。見 [PR-01](02-principles.md#pr-01)。
- **狀態**：已決定。
- **考慮過但沒選**：前端直接連資料庫或組出儲存路徑。
- **為什麼選這個**：權限、驗證與業務規則集中在後端；換資料庫時，前端契約可維持穩定。
- **代價**：外部存取要先定義 API；後端要維護 API 契約。
- **什麼情況要重新討論**：新增獨立外部服務，且現有 API 無法滿足資料交換需求時，檢查 API 契約與授權邊界；前端禁直連的要求仍有效。
- **依據**：架構基準 §2.2、§20.2、§37 ADR-002。

<a id="kd-02"></a>
## KD-02：照片檔案與關聯式資料分開存放

- **決策**：資料庫保存 Evidence metadata；檔案存入 Storage。後端產生 storage key，不以原始檔名當唯一識別。業務邏輯經 Storage 介面讀寫檔案。見 [PR-02](02-principles.md#pr-02)。
- **狀態**：已決定。
- **考慮過但沒選**：照片以 BLOB 放進 SQLite；原始檔名直接當 storage key。
- **為什麼選這個**：照片是容量主因；分開存放可控制資料庫大小，並保留物件儲存遷移路徑。
- **代價**：檔案與資料庫需要配對備份，也要處理兩邊寫入失敗。照片只保存現場版與內業版兩張，見 [KD-32](#kd-32)、[G-02](05-open-questions.md#g-02)（已裁定）。
- **什麼情況要重新討論**：本機檔案容量、備份或存取需求超出單機能力時，評估 MinIO、S3 或 NAS；Storage 介面仍維持。
- **依據**：架構基準 §2.3、§7.4、§13.1–13.2、§33、§37 ADR-004。

<a id="kd-03"></a>
## KD-03：查核範本不版本化，套用到專案時複製成專案自己的一份

- **決策**：範本庫裡的 `Inspection Template` 修改時**直接覆蓋**，只保留最新內容，**不做**版本化（不設 `Template Version`）。查核範本套用到專案時**必須**複製一份，成為專案自己的查核項目（見 [KD-47](#kd-47)）；「快照」由這份複製負責，之後修改或刪除查核範本，都不影響已套用的專案。專案**必須**記錄來源查核範本名稱與套用時間，供追查；查核範本被覆蓋後，不保證能回看套用當時的查核範本內容。
- **狀態**：已決定（改寫原決策「查核範本版本化，任務建立時固定需求」，保留編號）。任務需求快照維持必須：建立任務時**必須**產生 `Task Requirement Snapshot`（見 [PR-04](02-principles.md#pr-04)，不變）。專案副本與任務快照的分工已由 [KD-55](#kd-55) 裁定（內業修改專案查核項目時，選擇是否讓現場重新查核；選「要」則只作廢被修改的查核項目）；其餘細節已由 [`state-machines` 規格](../specs/state-machines/spec.md)與 [OQ-09](05-open-questions.md#oq-09) 處理。
- **考慮過但沒選**：查核範本版本化（v1、v2、v3……），任務建立時鎖定某一版並把需求複製成 `Task Requirement Snapshot`（原決策）。
- **為什麼選這個**：專案套用時已經持有獨立的一份，歷史可追溯由專案那份負責，範本庫不必再維護版本，只保留最新內容即可。以上理由是依裁定內容整理，負責人只說明「修改時直接覆蓋、快照由套用複製負責」。
- **代價**：查核範本被覆蓋後，無法回看專案當時依據的查核範本內容，只能靠專案複本本身與「來源查核範本名稱、套用時間」追查；`Template Version` 實體取消，依版本鎖定的設計一併取消，[06-versioning-and-milestone-governance.md](06-versioning-and-milestone-governance.md) 中 0.3.x 與 0.4.x 的範圍已對應調整。
- **什麼情況要重新討論**：稽核或業主要求回看查核範本歷史內容時，評估保留查核範本修改歷程；若要修改已建立任務的需求，仍須先定義更正流程，不能直接改寫歷史快照。
- **依據**：負責人裁定（[#78 留言](https://github.com/speko-tw/inspect-flow/issues/78#issuecomment-5956039701)，2026-10-02）；取代原決策依據的架構基準 §2.5、§12.4、§12.9、§37 ADR-006 中「查核範本版本化」的部分；本決策只管查核範本，報告範本（報告版面）及其版本不受影響，見 [KD-05](#kd-05)，依[負責人確認（#313，2026-10-02）](https://github.com/speko-tw/inspect-flow/issues/313)。

- **代價**：無（已由新決策取代，不再是有效規則）。
- **什麼情況要重新討論**：不適用，已被取代。
- **依據**：架構基準 §13A.2–13A.6、§37 ADR-010；已由負責人決定（#90～#91，2026-09-28）取代，見 [G-02](05-open-questions.md#g-02)、[G-03](05-open-questions.md#g-03)。

## KD-05：DOCX 與 PDF 是 MVP 的正式交付物

- **決策**：MVP **必須**產出 DOCX 與 PDF。報告從後端 Report View Model 和版本化的報告範本（DOCX 報告版面）產生；HTML 可做預覽，不能取代正式文件。報告需保存報告範本版本、文件編號、版次、快照、檔案鍵、雜湊與產製資訊。見 [PR-06](02-principles.md#pr-06)。
- **狀態**：已決定；完整核准、簽名與核發流程仍待決議，見 [OQ-07](05-open-questions.md#oq-07)、[G-11](05-open-questions.md#g-11)。
- **考慮過但沒選**：只從 HTML 直接列印 PDF；只提供一次性下載檔。
- **為什麼選這個**：業主、監造與標案文件需要可提交、可歸檔、可追溯的正式產物。
- **代價**：需要管理報告範本（DOCX 版面）、版面驗收及 PDF 轉換。轉換工具見 [OQ-15](05-open-questions.md#oq-15)。
- **什麼情況要重新討論**：正式收件規範改變，且 DOCX／PDF 不再滿足交付要求時，新增決策並評估舊報告的保存方式。
- **依據**：架構基準 §20.1–20.7、§20.22、§30 Phase 9（架構基準原 Phase 9、現行路線圖 Phase 8）、§37 ADR-009。本卡的「範本」指報告範本（報告版面），與查核範本（[KD-03](#kd-03)）是兩種不同的東西，版本與快照規則維持原文（[負責人確認（#313，2026-10-02）](https://github.com/speko-tw/inspect-flow/issues/313)）。

<a id="kd-06"></a>
## KD-06：資料庫存取用 SQLAlchemy，結構演進用 Alembic

- **決策**：資料庫存取**必須**經 SQLAlchemy。Schema 變更**必須**走 Alembic migration。正式環境**不得**靠 `Base.metadata.create_all()` 或未記錄的手動 ALTER 管理版本。見 [PR-03](02-principles.md#pr-03)。
- **狀態**：已決定。
- **考慮過但沒選**：正式環境直接建立表格或手動改 schema；大量使用 SQLite 專用 SQL。
- **為什麼選這個**：把 SQLite 換成 PostgreSQL 時，資料庫差異較容易收斂在資料存取與 migration 層。
- **代價**：每次 schema 變更都要寫、審查及驗證 migration。
- **什麼情況要重新討論**：導入 SQLAlchemy 無法支援的資料庫能力時，記錄相依性並以雙資料庫測試驗證；正式 schema 變更仍需可追蹤。
- **依據**：架構基準 §4.4–4.5、§22A.9、§32、§37 ADR-005。

<a id="kd-07"></a>
## KD-07：主要實體以 UUID 識別

- **決策**：Project、User、Plan、Task、Evidence 等主要實體使用 UUID。UUIDv7 **得**優先評估。人類可讀的業務編號與 UUID 分開保存。
- **狀態**：已決定；UUID 版本待實作選擇。
- **考慮過但沒選**：完全依賴 SQLite AUTOINCREMENT 作為跨系統身分。
- **為什麼選這個**：減少資料合併時撞號的風險，並保留離線用戶端自行產生 ID 的空間。
- **代價**：UUID 較長；畫面與文件還要另外使用可讀的業務編號。
- **什麼情況要重新討論**：離線建立、跨系統合併或排序效能提出具體需求時，選定 UUID 版本與產生位置；不改用自增值作為唯一對外識別。
- **依據**：架構基準 §11、§37 ADR-007。

<a id="kd-08"></a>
## KD-08：MVP 先用單機 SQLite

- **決策**：MVP 使用 SQLite。多台後端**不得**透過網路檔案系統共用同一個 SQLite 檔。連線初始化**應**確認 `foreign_keys = ON` 與 WAL；來源把兩項 PRAGMA 稱為「建議確認」，不是額外的 ADR 強制項。
- **狀態**：已決定；PRAGMA 屬建議設定。
- **考慮過但沒選**：MVP 一開始就維運 PostgreSQL；多台伺服器共用同一個 SQLite 檔。
- **為什麼選這個**：Pilot 規模小、schema 尚在變動，先降低資料庫維運成本。
- **代價**：寫入併發及資料庫維運能力有限；備份須處理 WAL 的一致性。
- **什麼情況要重新討論**：需要第二台後端、同時寫入明顯增加，或備份、鎖定、監控需求超出 SQLite 能力時，轉向 PostgreSQL。
- **依據**：架構基準 §9.1–9.2、§10、§23、§37 ADR-003。

<a id="kd-09"></a>
## KD-09：Pilot 與正式環境採 Linux 和 Docker Compose

- **決策**：Pilot／Production 使用 Linux Server、Docker Engine、Docker Compose 與持久化儲存。正式變更經 Git、審查、CI、版本化 image；migration 必須納入發布流程。見 [PR-13](02-principles.md#pr-13)。
- **狀態**：已決定；migration 與服務啟動的先後順序依 [G-09](05-open-questions.md#g-09) 的裁定，見 [PR-13](02-principles.md#pr-13)。
- **考慮過但沒選**：個人電腦、臨時 VM、沒有持久化磁碟的主機，或第一天就導入多節點編排。
- **為什麼選這個**：開發與正式環境較易重現，也能以固定流程備份、更新及回滾。
- **代價**：Compose 本身不提供多節點協調與自動容錯；部署仍需要維運程序。
- **什麼情況要重新討論**：需要多節點、高可用、自動容錯或大量後端副本時，評估編排平台。部署順序的來源歧義與裁定見 [G-09](05-open-questions.md#g-09)。
- **依據**：架構基準 §22.1–22.7、§22A.7、§22A.19、§37 ADR-011。

<a id="kd-10"></a>
## KD-10：第一版使用模組化單體

- **決策**：第一版只有一個 Backend Application。API、Service、Persistence 與 Storage 保持清楚邊界。見 [PR-11](02-principles.md#pr-11)。
- **狀態**：已決定。
- **考慮過但沒選**：為尚未出現的規模需求先導入微服務、訊息系統或多節點編排。
- **為什麼選這個**：縮短開發與部署路徑，同時保留日後拆分模組的空間。
- **代價**：模組共用部署單位，不能單獨擴充某個模組。
- **什麼情況要重新討論**：特定模組有可量測的獨立擴充、部署或隔離需求時，評估拆分；只因「未來可能變大」不足以拆分。
- **依據**：架構基準 §2.1、§7、§22A.19、§37 ADR-001。

<a id="kd-11"></a>
## KD-11：現場畫面只呈現完成任務所需資訊

- **決策**：Field UI 聚焦「今日任務 → 證據 → 完成」。查核範本庫與範本設定、資料庫 ID、storage key 與後台設定不放在現場操作畫面。見 [PR-10](02-principles.md#pr-10)。
- **狀態**：已決定。
- **考慮過但沒選**：把管理及設定功能直接放進現場畫面。
- **為什麼選這個**：降低現場工程師的操作負擔與拍錯需求的機率。
- **代價**：進階設定與例外處理要由 Admin UI 或後端流程承接。
- **什麼情況要重新討論**：Pilot 顯示現場工程師因缺少必要資訊而無法完成任務時，調整呈現內容，但不暴露底層儲存與資料庫細節。
- **依據**：架構基準 §6.1–6.2、§31、§37 ADR-008。

<a id="kd-12"></a>
## KD-12：Admin／Field 共用單一前端程式庫

- **決策**：Admin UI 與 Field UI **必須**放在同一個 React application，以 `/admin/*`、`/field/*` 路由與權限區分；**必須**依路由拆分程式碼，Field 的程式包不得載入 Admin 的模組。
- **狀態**：已決定（團隊於 [#5](https://github.com/speko-tw/inspect-flow/issues/5) 裁定 [OQ-21](05-open-questions.md#oq-21)，採來源 §5.1 的建議）。
- **考慮過但沒選**：同一 repo 內分成兩個 app 加共用套件。
- **為什麼選這個**：一套 build、一條 CI、一次部署；API client、登入與元件共用；符合模組化單體方向（[KD-10](#kd-10)）。
- **代價**：沒有依路由拆分時，Field 會載入 Admin 的程式；日後要拆開需要搬遷。
- **什麼情況要重新討論**：Field PWA 需要獨立發布週期，或兩者差異大到共用成本高於分開維護時，評估拆分。
- **依據**：架構基準 §5.1；團隊裁定 [OQ-21](05-open-questions.md#oq-21)。

<a id="kd-13"></a>
## KD-13：清單端點採 cursor-based 分頁

- **決策**：`/api/v1` 清單端點的分頁**必須**採 cursor-based 分頁，不用 offset/limit。
- **狀態**：已決定。
- **考慮過但沒選**：offset/limit 分頁。
- **為什麼選這個**：現場查核的照片與任務清單偏向捲動瀏覽，cursor-based 分頁在資料持續新增時不會因位移量偏移而跳頁或重複。
- **代價**：不能直接跳到指定頁碼；cursor 的排序鍵必須穩定，見 [KD-14](#kd-14)（時間欄位精度到秒，需搭配 UUID 排序）。
- **什麼情況要重新討論**：後台管理畫面需要「跳到第 N 頁」這類操作時，評估是否額外提供 offset/limit 介面。
- **依據**：負責人決定（PR #30，2026-09-26）；架構基準無對應章節。

<a id="kd-14"></a>
## KD-14：時間欄位採 ISO 8601（RFC 3339）、UTC、精度到秒

- **決策**：API 回應中的時間欄位**必須**使用 ISO 8601（RFC 3339）字串，一律 UTC 並帶 `Z` 後綴，精度到秒（例如 `2026-09-26T08:30:00Z`）。
- **狀態**：已決定；輸入端的解析寬鬆度（是否接受小數秒、`+08:00` 偏移）不在本決策範圍，之後另議。
- **考慮過但沒選**：Unix epoch 數值、毫秒精度、本地時區字串。
- **為什麼選這個**：系統多為人類操作，秒級精度已足夠辨識操作先後，且字串格式比 epoch 對人類判讀與除錯更直接。
- **代價**：同一秒可能有多筆記錄，排序與 cursor 不得只靠時間欄位，必須以「時間＋UUID」為鍵（可評估搭配 [KD-07](#kd-07) 提及的 UUIDv7 提升同秒排序穩定性）。
- **什麼情況要重新討論**：出現需要秒級以下精度才能區分的業務情境（例如高頻自動化寫入）時，重新評估精度。
- **依據**：負責人決定（PR #30，2026-09-26）；架構基準無對應章節。

<a id="kd-15"></a>
## KD-15：`error.code` 採 dot-namespace 命名，對照表由程式列舉自動產生

- **決策**：`error.code` **必須**採 dot-namespace 命名（`<resource>.<reason>`，例如 `task.not_found`）；`error.code` 對照表**必須**由程式的列舉自動產生，不手寫維護獨立文件。不特定於單一資源的跨資源共用錯誤，依錯誤性質分類型 namespace：`request.*`（請求本身的問題，例如 `request.validation_failed`）、`resource.*`（不特定於某資源的通用資源錯誤，例如框架產生的 `resource.not_found`）、`server.*`（伺服器端錯誤，例如 `server.internal_error`）；資源專屬錯誤仍用 `<resource>.<reason>`。
- **狀態**：已決定。
- **考慮過但沒選**：SCREAMING_SNAKE_CASE 全域列舉、泛用少數碼、手寫維護對照表文件。
- **為什麼選這個**：dot-namespace 讓前端能依資源分類做程式化分支；對照表自動產生可避免列舉與文件長期不同步；跨資源共用錯誤依性質分為 `request`／`resource`／`server` 三類，讓歸屬判斷有固定規則可循，不必逐一個案討論。
- **代價**：每個資源都要維護自己的 reason 列舉；新增跨資源共用的錯誤原因時，須先判斷屬於 `request`／`resource`／`server` 三類中的哪一類，而非任意新增 namespace。
- **什麼情況要重新討論**：出現大量跨資源共用、難以歸入單一 `<resource>` 的錯誤原因時，重新評估命名法。
- **依據**：負責人決定（PR #30，2026-09-26）；架構基準無對應章節。

## KD-24：Admin 是人員身上的開關，不是角色

- **決策**：系統管理者（Admin）**是**人員身上的一個開關（`is_admin`），**不是**一個角色；具備 Admin 的人可以管理系統設定、人員、公司、角色定義，並直接查看、修改所有專案，也可以指派、收回**其他人**的 Admin 權限（內建 `admin` 除外，它的 Admin 權限不能被任何人收回，見 [KD-44](#kd-44)）。專案權限代碼全部放行，含新增、刪除與簽核、匯出等特殊動作，不必是專案成員（[#144](https://github.com/speko-tw/inspect-flow/issues/144#issuecomment-5852180954)）。依 [KD-69](#kd-69)，Admin 在兩層權限判斷（人員模組權限與專案角色）都放行，不需逐項勾選模組權限；指派模組權限的委派者也只有 Admin 能做。
- **狀態**：已決定。
- **考慮過但沒選**：無，issue #63 未列出替代方案。與架構基準 §17 範例矩陣的差異：§17 把 `ADMIN` 列為角色之一。
- **為什麼選這個**：這是 `authentication` 與 `domain-model` 的前提（依負責人 #63 決定）。
- **代價**：授權檢查需要先判斷 `is_admin`，再依 [KD-69](#kd-69) 判斷人員模組權限與專案角色的權限，邏輯不能合併成單一角色查詢。
- **什麼情況要重新討論**：無，屬已決定的權限模型基礎假設。
- **依據**：負責人決定（#63，2026-09-26）；取代架構基準 §17 的範例矩陣；指派與收回他人 Admin 權限的補充依負責人裁定（[#259](https://github.com/speko-tw/inspect-flow/issues/259)，2026-09-29）；兩層判斷都放行與委派者只能由 Admin 指派，依負責人裁定（[#538](https://github.com/speko-tw/inspect-flow/issues/538)，2026-10-09），見 [KD-69](#kd-69)。

## KD-25：權限模型＝資料 × 動作，系統存權限代碼

- **決策**：權限**必須**表示為「資料 × 動作」：讀取、新增、修改、刪除，再加上特殊動作（例如簽核、匯出列印）；系統存的是權限代碼，例如 `report.read`、`report.approve`。權限分兩種：人員模組權限（逐人勾選）與專案動作權限（組成專案角色），兩種都用同一種代碼格式，模組歸屬用獨立欄位表達（[KD-69](#kd-69)）。
- **狀態**：已決定。
- **考慮過但沒選**：無，issue #63 未列出替代方案。與架構基準 §17 範例矩陣的差異：§17 以固定角色對功能列表。
- **為什麼選這個**：這是 [KD-26](#kd-26) 可自訂角色的資料基礎——角色本質是一組權限代碼的集合，而不是寫死的功能表（依負責人 #63 決定）。
- **代價**：新增一項功能時，除了寫程式邏輯，還要定義並登記對應的權限代碼；權限代碼的命名規則待相關規格定案，不必然沿用 [KD-15](#kd-15) 的 `error.code` 命名（KD-15 只涵蓋錯誤碼）。
- **什麼情況要重新討論**：權限代碼數量快速膨脹、難以維護時，重新評估分類方式。
- **依據**：負責人決定（#63，2026-09-26）；架構基準無對應章節。

## KD-27：專案角色掛在專案成員（ProjectMember）上

- **決策**：專案角色**必須**掛在專案成員（`ProjectMember`）上：一個人在同一個專案可以同時擁有多個專案角色，權限加總；角色由有權限的人設定，之後可以再修改。全公司層級的能力**不用角色**，依 [KD-69](#kd-69) 以人員模組權限直接勾給人。
- **狀態**：已決定。
- **考慮過但沒選**：無，issue #63 未列出替代方案。與架構基準 §17 範例矩陣的差異：§17 的角色不分專案範圍。

<a id="kd-37"></a>
## KD-37：查核結果由現場對每個查核項次自行判定符合／不符合

- **決策**：每個查核項次**必須**各自有「符合」與「不符合」選項，由現場人員自行選擇，**不得**只替整個查核項目組選一個結果，也**不得**預設符合；系統**不得**依標準值自動判定結果。一個查核項次**得**有多個實測欄位（例如長、寬、高），欄位與標準值由內業事先設定，標準值通常取自計畫書，按原文以文字輸入，系統不解析 `±`、`≥` 等條件；不需量測的項次不強制填實際值。結果另有「不適用」，各結果的必填內容與實測欄位的型別見 [KD-54](#kd-54)。數值標準另有結構化欄位（見 [KD-52](#kd-52)），實測欄位的型別與必填規則已由 [KD-54](#kd-54) 裁定，現場填值的實作屬 0.7.x；系統**不得**依標準值自動判定，0.7.x 的範圍依 [KD-65](#kd-65)。
- **狀態**：已決定；`N/A`（不適用）、嚴重度與實測欄位的型別、必填已由 [KD-54](#kd-54) 補完（[OQ-06](05-open-questions.md#oq-06) 已裁定）；簡易改善追蹤依 [KD-65](#kd-65) 排入 0.7.x。KD-65 不做限期提醒與自動通知，也不依標準值自動判定，嚴重度不阻擋任務完成；完整缺失管理與更進階的改善流程不在 KD-65 範圍。
- **考慮過但沒選**：以查核項目組為單位選一個結果；系統依標準值自動判定符合／不符合。
- **為什麼選這個**：不同項次的查核結果可能不同，統一判定會掩蓋個別項次的實際狀況；標準值通常取自計畫書，格式不一致，系統解析風險高。
- **代價**：每個查核項次都要各自記錄結果與（若有）多筆實測值；欄位型別、單位與必填規則見 [KD-54](#kd-54)，完整 schema 由規格制定。
- **什麼情況要重新討論**：檢視 [KD-65](#kd-65) 的簡易改善追蹤是否足夠，或之後要加限期提醒或自動判定時，一併檢視本決策是否需要調整。
- **依據**：負責人決定（#76，2026-09-28）；架構基準 §38 Result 的未定案項目，見 [OQ-06](05-open-questions.md#oq-06)（已裁定）；其餘部分由 [KD-54](#kd-54) 補完（負責人裁定（[#76 留言](https://github.com/speko-tw/inspect-flow/issues/76#issuecomment-5965076758)，2026-10-03））。

<a id="kd-38"></a>
## KD-38：查核項次由內業設定，照片依覆蓋規則佐證

- **決策**：查驗流程**必須**是一套共通流程，不因進料／施工／測試等報表樣板差異而分成不同流程；一個查核項目組下**得**有多個查核項次，項次內容由內業事先設定。現場人員自行選擇每張照片要佐證哪些查核項次，一張照片**得**覆蓋多個項次；每個查核項次**必須**至少被一張非總覽照片覆蓋。**得**額外提供「總覽照片」選項，由現場人員選擇是否拍攝；有拍就在該組報表中排第一張，且**不計入**最低覆蓋要求。
- **狀態**：已決定；每項次可多張照片、不設張數上限、總覽照片可多張與照片註記，由 [KD-50](#kd-50) 補充，見 [OQ-05](05-open-questions.md#oq-05)（已裁定）。
- **考慮過但沒選**：依進料／施工／測試建立三套不同查驗流程；固定「每幾個項次配一張照片」的規則；把總覽照片列為必拍項目。
- **為什麼選這個**：報表樣板差異不代表查驗流程本身不同；由現場人員自行選擇佐證關係比系統預先固定配對更貼近實際拍攝情況。
- **代價**：完成度驗證需要依「每個項次至少一張非總覽照片」的規則檢查，而非簡單的照片數量比對；範本快照需要保存查核項次清單供現場端渲染。
- **什麼情況要重新討論**：照片張數規則或總覽照片的排列規則調整時，連同 [KD-50](#kd-50) 一併檢視。
- **依據**：負責人決定（#75，2026-09-28）；架構基準 §38 Template 的未定案項目裁定，見 [OQ-05](05-open-questions.md#oq-05)。2026-10-02 的補充裁定見 [KD-50](#kd-50)。

<a id="kd-39"></a>
## KD-39：Project 必填欄位與專案編號可重複

- **決策**：一個工程案建立一筆 `Project`；必填欄位為專案編號／代號、工程名稱、業主／委託單位、整體工程地點。`project_code`（專案編號）**必須**允許重複，資料庫**不得**對此欄位加唯一約束；系統內部的 Project ID（UUID）才必須唯一。新建或修改 Project 時，若 `project_code` 與既有 Project 重複，系統**必須**跳出警告提示使用者，但**不得**阻擋建立或儲存。預計開工日、預計完工日為選填；其他參與單位不列為建立專案的必填欄位。`Project` 建立後**必須**直接可用，不要求額外啟用步驟。
- **狀態**：已決定。
- **考慮過但沒選**：以 `project_code` 作為唯一業務識別（原架構基準假設，`database-foundation` DBF-R13「必須唯一」的規則已被本決策取代）；建立時要求額外啟用流程；重複時直接阻擋建立。
- **為什麼選這個**：現場實務上專案編號可能重複使用或由不同單位各自編碼，不宜由系統強制唯一；建立後即可使用可以縮短內業建立查核工項的前置時間；重複時提示但不阻擋，兼顧提醒使用者與不影響作業。
- **代價**：既有 `backend/app/models/project.py`（`project_code` 目前 `unique=True`）與 `database-foundation` DBF-R13、`domain-model` 規格的唯一約束假設須另開 task 修改並新增 migration；規格修改見 [#246](https://github.com/speko-tw/inspect-flow/issues/246)，程式修改見 [#247](https://github.com/speko-tw/inspect-flow/issues/247)，不在本次變更範圍內。
- **什麼情況要重新討論**：若未來需要以 `project_code` 做唯一查詢鍵，另行評估是否新增複合唯一約束（例如搭配客戶或年度）。

## KD-40：工項分類與分區皆依專案需求選用

- **決策**：每個專案的內業人員**必須**依該專案需求設定要查核的工項（查核項目本身是必要設定，不得省略），**不得**套用公司共用的固定工項分類。工項分類（例如空調風管、給排水、電力設備）與分區（例如一樓 A 區、二樓 B 區）是否使用，**皆**依專案需求選用，不強制每個專案都要建立這兩層組織方式。若專案正式建立分區，查核工項**必須**按分區分開建立與執行；若未建立分區，工區**得**只是同一查核工項的選項或資訊，合併為一個查核工項。
- **狀態**：已決定；分類固定兩層、範本庫複製與名稱規則已由 [KD-47](#kd-47)、[KD-48](#kd-48) 裁定，分區**不**強制為分類的子層，見 [OQ-04](05-open-questions.md#oq-04)（已裁定）；任務地點與分區名稱規則見 [OQ-03](05-open-questions.md#oq-03)（已裁定）及 [KD-58](#kd-58)。
- **考慮過但沒選**：全公司共用一套固定工項分類；分區強制作為分類的子層。
- **為什麼選這個**：不同工程專案查核內容差異大，固定分類無法適用所有專案；分區是否需要視專案規模而定，不宜強制。
- **代價**：查核工項的資料模型需要支援「有分區」與「無分區」兩種情境；分類階層與命名規則已由 [KD-48](#kd-48) 裁定（固定兩層、同層名稱不得重複、不設代號），任務地點與分區名稱規則見 [KD-58](#kd-58)。
- **什麼情況要重新討論**：若分區規則或分區與分類的關係需要調整，一併檢視本決策與 [KD-58](#kd-58)。
- **依據**：負責人決定（#74、#73，2026-09-28）；架構基準 §38 Work Item、§12.8 的未定案項目裁定，見 [OQ-04](05-open-questions.md#oq-04)、[OQ-03](05-open-questions.md#oq-03)。2026-10-02 的補充裁定見 [KD-47](#kd-47)、[KD-48](#kd-48)。

## KD-41：查驗是共通流程，報表樣板與匯入格式是獨立模組

- **決策**：查驗流程**必須**是一套共通機制：內業設定查核項次，現場填結果與實測值並拍佐證照片，內業再產出報表；建立查驗時**不得**選定或處理輸出報表樣板。報表**必須**是獨立的功能模組，**得**匯入不同樣板格式。
- **狀態**：已決定（僅涵蓋以上流程界線）；具體匯入格式、樣板欄位對應、選樣板時機、簽署欄位與 Revision 規則未定，見 [OQ-07](05-open-questions.md#oq-07)。

- **為什麼選這個**：範例文件的表單差異只是輸出報表的樣板格式，查驗本身的資料蒐集方式不應因此分裂成多套流程。

## KD-42：任務完成後可修正資料，計畫在所有任務完成時自動完成

- **決策**：`Inspection Task` 標記完成後，若資料有錯字、文字或圖片需要修正，現場人員與內業人員**皆得**修改；此為已完成查核後的資料修正，**不要求**重新查核，也**不**因修正而改回待確認或要求再按一次完成，任務維持「已完成」。`Inspection Plan` 底下所有任務都完成時，系統**必須**自動將計畫設為「已完成」；人員**不得**手動將計畫改為已完成。「封存」與取消封存由內業手動操作；計畫與任務的其他狀態轉換（含取消任務不計入完成判斷）見 [KD-56](#kd-56)。
- **狀態**：已決定（僅涵蓋以上範圍）；Plan／Task 的任務草稿與派出、自動進行中、任務取消與恢復、全部取消時計畫自動已取消、已完成不重開與封存已由 [KD-56](#kd-56) 補完，報告核發與新版取代見 [KD-57](#kd-57)；Evidence／Report 的其他狀態、其他原因的作廢、失敗與更正路徑未定，見 [OQ-09](05-open-questions.md#oq-09)。專案查核項目被修改時，選「不要重新查核」同樣只更正內容、不重查，選「要」則只作廢被修改的查核項目，見 [KD-55](#kd-55)；兩者層級不同：本決策修的是已完成任務自己的資料，KD-55 處理的是專案查核項目（標準）的修改。
- **考慮過但沒選**：任務修正後改回待確認狀態，要求重新完成；開放人員手動將計畫改為已完成（負責人已於本次討論中明確撤回）。
- **為什麼選這個**：已完成任務的資料修正屬於更正性質，不是推翻查核結果，不需要重新走一次完成流程；計畫狀態應反映任務進度的客觀結果，不需要人工介入。
- **代價**：需要記錄任務完成後的修改紀錄（誰、何時、改了什麼），具體欄位與機制待規格對齊；計畫的完成判定需要在每次任務狀態變化時重新檢查是否全部完成。
- **什麼情況要重新討論**：若未來確認需要開放人員手動將計畫改為已完成，須先由負責人另行裁定，不得逕自實作。
- **依據**：負責人決定（#78，2026-09-28）；架構基準 §18、§20.6、§20.17 的未定案項目部分裁定，見 [OQ-09](05-open-questions.md#oq-09)。決策本文中「不得手動將計畫改為已完成」「封存與取消封存手動」的措辭，由負責人確認（[#78 留言](https://github.com/speko-tw/inspect-flow/issues/78#issuecomment-5968037640)，2026-10-03）。

## KD-43：初始化只建系統資料，首次設定用一次性首次登入碼

- **決策**：初始化指令（`make init`）**必須**只建立資料庫、內建 `admin`，並在終端機印出一次**首次登入碼**；**不得**建立範本角色、詢問公司或任何個人資料，**不得**設定 `admin` 的密碼。首次登入碼 24 小時有效，資料庫只存雜湊；輸錯 10 次（15 分鐘內）鎖 15 分鐘，計數與密碼登入失敗分開，被鎖只寫應用程式日誌、不寫稽核紀錄。`admin` 還沒有密碼時重跑初始化指令，作廢舊碼並印出新碼；已設定密碼則拒絕。首次開網頁的流程固定為：輸入首次登入碼、設定 `admin` 密碼（碼隨即作廢）、新增第一個使用者；這段流程的稽核紀錄視為系統事件，操作者記為 `admin`。第一個使用者由系統產生臨時密碼，只在畫面顯示一次，首次登入必須變更；畫面提供「給予 admin 權限」勾選框，預設不勾。`admin` 忘記密碼時，只能在伺服器端用重設指令（互動輸入兩次密碼、寫稽核紀錄）重設；一般使用者的設定密碼指令移除。負責人裁定（#261，2026-09-29）：角色一律由 Admin 之後在系統內自行新增，初始化不建立三個範本角色。
- **狀態**：已決定。
- **考慮過但沒選**：初始化指令詢問並建立兩個帳號、email 與姓名與密碼在指令中輸入（原 [KD-22](#kd-22)）。
- **為什麼選這個**：初始化指令不再經手個人資料與密碼，個人資料與密碼都在網頁上設定；首次登入碼有時效、只存雜湊、有鎖定，被看到也有限度。以上理由是依裁定內容整理，負責人未逐項說明。
- **代價**：使用者多一步輸入首次登入碼；`admin` 已設定密碼後忘記，必須有伺服器端存取才能重設；首次登入碼的鎖定與稽核規則要另外實作與驗收。
- **什麼情況要重新討論**：部署改成多台伺服器、或需要在沒有伺服器端存取的情況下重設 `admin` 密碼時。
- **依據**：負責人裁定（[#259](https://github.com/speko-tw/inspect-flow/issues/259)，2026-09-29）；取代 [KD-22](#kd-22)。

## KD-44：內建 admin 代表系統本身

- **決策**：內建 `admin`（`is_system`）代表系統本身：**不屬於**任何公司，沒有部門、地點、工號、姓名；帳號名稱固定為 `admin`；email 選填。它**不得**被停用，任何人都**不得**收回它的 Admin 權限；它的 `created_by` 指向自己。系統自動觸發的事件，操作者記為 `admin`。
- **狀態**：已決定。
- **考慮過但沒選**：內建 `admin` 也要有公司與姓名（原 [KD-22](#kd-22) 與 [KD-16](#kd-16) 的必填欄位）。
- **為什麼選這個**：`admin` 是安裝時就存在的系統帳號，不是某一個人；初始化又不再詢問個人資料（[KD-43](#kd-43)），沒有資料可填。
- **代價**：`User` 的公司、姓名、email 等欄位對內建 `admin` 要允許空值，資料庫約束與 Service 層要能區分內建帳號與一般帳號。

## KD-45：使用者有帳號名稱，可用帳號名稱或 email 登入

- **決策**：每個 `User` 有內部 UUID，另有**必填**的帳號名稱與 email（內建 `admin` 的 email 例外，見 [KD-44](#kd-44)）；兩者都能登入，輸入含 `@` 視為 email，否則視為帳號名稱。帳號名稱 3～32 字元，英文字母開頭，只能用英文字母、數字與 `.`、`_`、`-`（不可中文、不可 `@`）；不分大小寫，一律存成小寫；保留字為 `admin`、`system`、`root`；只有具 Admin 權限的人能修改，修改要寫稽核紀錄；外部（AD）帳號以外部來源為準，不能手動修改。
- **狀態**：已決定。
- **考慮過但沒選**：只用 email 登入、不設帳號名稱（原 [KD-18](#kd-18)）。
- **為什麼選這個**：沒有 email 或不想用 email 的人也要有登入識別；用有無 `@` 判斷輸入的是哪一種，登入畫面只需要一個輸入欄。以上理由是依裁定內容整理，負責人未逐項說明。

- **什麼情況要重新討論**：外部身分來源串接後，帳號名稱的格式或唯一性與外部來源衝突時。
- **依據**：負責人裁定（[#259](https://github.com/speko-tw/inspect-flow/issues/259)，2026-09-29）；取代 [KD-18](#kd-18)。

<a id="kd-46"></a>
## KD-46：使用者的公司是可選的，工號、部門、地點跟著公司

- **決策**：`User` 的中文姓名**必填**、英文姓名選填（內建 `admin` 例外，見 [KD-44](#kd-44)）。人員**不一定**屬於公司，最多連結一家（[KD-23](#kd-23)）。工號、部門、地點在連結公司之前不能填；換公司或解除連結時，這三個欄位清空並寫稽核紀錄；工號在**同一家公司內**不得重複。沒有公司的人（獨立或外部人員）也可以加入專案、被指派角色：專案角色跟著人，不跟著公司。本系統建立的帳號，這些欄位由 Admin 修改；外部來源匯入的帳號，任何人都不能修改這些基本欄位（沿用原 [KD-16](#kd-16)）。
- **狀態**：已決定。
- **考慮過但沒選**：每個人都必須屬於一家公司、工號全系統唯一（原 [KD-16](#kd-16)、[KD-23](#kd-23)）。
- **為什麼選這個**：獨立或外部人員本來就不隸屬於任何一家公司；工號是公司內部編號，不同公司之間可能撞號。以上理由是依裁定內容整理，負責人未逐項說明。
- **代價**：換公司會清掉工號、部門、地點，操作前要提示；工號唯一約束要改成「同公司內唯一」，沒有公司的人不受工號約束。
- **什麼情況要重新討論**：需要一個人同時屬於多家公司時。
- **依據**：負責人裁定（[#259](https://github.com/speko-tw/inspect-flow/issues/259)，2026-09-29）；取代 [KD-16](#kd-16) 的必填欄位規則。

<a id="kd-47"></a>
## KD-47：範本庫是獨立於專案的系統，套用即複製、選用

- **決策**：**必須**有一個獨立於專案的範本庫；所有專案都**得**從範本庫挑項目，**套用（複製）**成自己的查核項目。範本庫為選用，專案**得**不使用查核範本、從零建立查核項目。套用時複製一份，之後修改查核範本只影響之後才套用的專案，**不得**回頭改動已套用的專案；專案**必須**記錄來源查核範本名稱與套用時間（見 [KD-03](#kd-03)）。查核範本的單位有兩種：可以只存單一查核項目，也可以存整個系統（含其下所有查核項目）；套用時也一樣，可套用單一查核項目或整個系統。專案中已有同名查核項目時，套用**必須**拒絕並提示哪些項目已存在；需要第二份時，先把既有項目改名再套用。
- **狀態**：已決定。「同名」的比對規則（空白、大小寫）與比對範圍、拒絕時的錯誤內容，裁定沒有說明，由規格定；改名是否觸發 [KD-55](#kd-55) 的重新查核詢問，裁定也沒有說明，待規格確認（整理者列出，非完全確定已涵蓋全部）。
- **考慮過但沒選**：專案直接引用範本庫的目前內容，查核範本一改全部連動；要求每個專案都必須從範本庫建立。同一範本重複套用到同一專案（2026-10-04 情境對答的選項）：照樣套用、讓專案出現重複項目；提醒後讓內業決定是否仍套用。
- **為什麼選這個**：每個專案要查核的內容不盡相同（[KD-40](#kd-40)），專案需要能自由調整；複製後各自獨立，已進行中的專案不會被查核範本修改影響。以上理由是依裁定內容整理，負責人未逐項說明。拒絕重複套用的理由是整理者自己推得的，裁定本身只選了「擋下並提示」：同一專案出現兩個同名查核項目，內業與現場都難以分辨，也與範本內同層不得重名（[KD-48](#kd-48)）的做法一致。
- **代價**：查核範本修改不會同步到已套用的專案，專案要自行更新；套用時必須複製整個結構（分類、查核項目、查核項次、檢查標準、照片要求）並寫入來源與時間，並先與專案現有查核項目比對；真的需要第二份時，內業要先改名再套用，多一個步驟。
- **什麼情況要重新討論**：出現「查核範本更新後要通知或同步已套用專案」的需求時；內業反映「先改名再套用」太麻煩，或常需要同一範本套用多份時。
- **依據**：負責人裁定（[#74 留言](https://github.com/speko-tw/inspect-flow/issues/74#issuecomment-5956038822)，2026-10-02）；[#78 留言](https://github.com/speko-tw/inspect-flow/issues/78#issuecomment-5956039701)（2026-10-02）；查核範本的單位依[負責人裁定（#313，2026-10-02）](https://github.com/speko-tw/inspect-flow/issues/313)；查核範本與報告範本是兩種不同的東西，依[負責人確認（#313，2026-10-02）](https://github.com/speko-tw/inspect-flow/issues/313)，報告範本不受本決策影響，見 [KD-05](#kd-05)。範本庫與套用的架構基準背景為 §2.4、§12.3–12.7（沿用 [template-system 規格](../specs/template-system/spec.md)的引用）。新增的「同名則拒絕套用並提示」規則：架構基準無對應章節，裁定來源為[#313 留言](https://github.com/speko-tw/inspect-flow/issues/313#issuecomment-5974836112)（2026-10-04）。

<a id="kd-48"></a>
## KD-48：查核範本只存結構，分類固定兩層，同一層名稱不得重複

- **決策**：查核範本內容**只存結構**：分類、查核項目、查核項次、檢查標準、照片要求；**不存**現場結果與照片。分類先固定兩層「工程類別 → 系統」，其下為查核項目（試做，日後調整另開 issue）。名稱規則：同一層之下**不得**重名，不同層**得**重名；目前只用名稱、不設代號，需要時另提。專案內是否使用分類與分區，仍依 [KD-40](#kd-40) 選用；分區不是分類的子層。
- **狀態**：已決定（分類層數為試做）；名稱比對的細節（空白、大小寫）未說明，由規格定。
- **考慮過但沒選**：全公司共用一套固定工項分類（[KD-40](#kd-40) 已排除）；查核範本連同現場結果或照片一起存；先不限制分類階層；同時設代號。
- **為什麼選這個**：查核範本是「要查什麼」的結構，現場結果與照片屬於個別專案的執行紀錄；先固定兩層可以先落地、日後依使用情況調整。以上理由是依裁定內容整理，負責人未逐項說明。
- **代價**：固定兩層可能不符合部分工程的分類習慣，要調整時需另開 issue 與規格變更；沒有代號就沒有穩定的短識別，匯入匯出或報表引用時只能靠名稱與內部 UUID（[KD-07](#kd-07)）。
- **什麼情況要重新討論**：試做後發現兩層不夠或太多；需要代號供報表或外部系統引用時。
- **依據**：負責人裁定（[#74 留言](https://github.com/speko-tw/inspect-flow/issues/74#issuecomment-5956038822)，2026-10-02）。

## KD-49：範本管理權限涵蓋跨專案查核項目

- **決策**：「管理範本庫」是範本模組的模組權限，逐人勾選，由 Admin 或被委派管理範本模組的人授予（委派只代表可以替別人開通範本模組權限，不附帶維護範本庫的能力）；Admin 擁有全部權限（[KD-69](#kd-69)）。此權限沿用 [#313](https://github.com/speko-tw/inspect-flow/issues/313) 裁定的範本管理行為：得跨專案瀏覽查核項目，並把任何專案的查核項目存成範本；這項跨專案瀏覽只用於存成範本，**不得**因此取得任何專案內的查核動作權限。套用範本到專案需要範本模組「可使用」（唯讀範本庫）加專案角色含「編輯查核項目」；只有「管理範本庫」能改範本庫。查核範本建議與審核流程留待之後版本，目前不設。
- **狀態**：已決定。0.3.x 現行固定的 `template_admin` 與 Admin 管理範本是過渡行為，見 [KD-69](#kd-69)。
- **考慮過但沒選**：固定、寫死的 `template_admin` 系統角色；以全公司角色承載「管理範本庫」。
- **為什麼選這個**：範本庫獨立於專案（[KD-47](#kd-47)），管理權限因此不屬於任何專案，由範本模組自己的模組權限承擔，不必另設全公司角色；逐人勾選可沿用跨專案瀏覽與存成範本的行為。以上理由依裁定內容整理，負責人未逐項說明。
- **代價**：授權檢查需區分 Admin、人員模組權限與專案角色（[KD-69](#kd-69)）；具有「管理範本庫」權限者可跨專案瀏覽查核項目並存成範本，授予時須視為敏感權限並寫稽核紀錄（[KD-29](#kd-29)）。
- **什麼情況要重新討論**：模組權限的範圍或 Admin 全權原則改變時（[KD-69](#kd-69)）；要加入查核範本建議與審核流程時。
- **依據**：範本管理行為依負責人裁定（[#313](https://github.com/speko-tw/inspect-flow/issues/313) 內文，2026-10-02）；權限歸屬依負責人裁定（[#538](https://github.com/speko-tw/inspect-flow/issues/538)，2026-10-09），詳見 [KD-69](#kd-69)。

<a id="kd-50"></a>
## KD-50：每個項次可有多張照片，每張照片可加現場註記

- **決策**：每個查核項次的佐證照片**得**有多張，最少 1 張（沿用 [KD-38](#kd-38) 的最低覆蓋），**不設**張數上限。總覽照片**得**有多張，全部排在該查核項目組的最前面；仍為選拍，不計入各項次的最低覆蓋。每一張照片（總覽與佐證項次的照片）都**得**加上現場工程師的文字註記（照片註記）：有填寫就**必須**呈現在報告中，留白則不顯示；註記一律保留。照片註記是文字說明，與 [OQ-12](05-open-questions.md#oq-12)（#81）討論的「在照片上畫標註」不同。
- **狀態**：已決定；「註記一律保留」在現場版與內業版之間如何沿用，裁定沒有細說，由規格確認。
- **考慮過但沒選**：每個項次固定一張照片（[KD-38](#kd-38) 已排除）；訂張數上限；總覽照片只能一張。
- **為什麼選這個**：現場實際需要多角度、多張照片佐證同一個項次，註記讓現場工程師能說明照片內容（也用於文件拍照的說明，見 [KD-53](#kd-53)）。以上理由是依裁定內容整理，負責人未逐項說明。
- **代價**：沒有張數上限，儲存容量與報告版面都要預留彈性（[PR-02](02-principles.md#pr-02)）；註記欄位要隨現場版、內業版與報表資料一路帶下去；`Evidence Requirement` 的 `max_count` 對照片不適用。
- **什麼情況要重新討論**：照片量造成容量或報告長度問題時，評估上限；需要在照片上畫標註時，另見 [OQ-12](05-open-questions.md#oq-12)。
- **依據**：負責人裁定（[#75 留言](https://github.com/speko-tw/inspect-flow/issues/75#issuecomment-5956039268)，2026-10-02）；補充 [KD-38](#kd-38)。

<a id="kd-51"></a>
## KD-51：本系統定位為工程查核系統，長期涵蓋一級自主檢查與二級監造抽查

- **決策**：InspectFlow 是「工程查核系統」，涵蓋公共與私人工程的施工查驗、材料設備（進料）查驗等。長期使用對象包含廠商自主檢查（一級）與監造抽查（二級），**必須**在同一系統串起來；現階段甲方以監造／PCM 抽查為主，MVP 以抽查紀錄表為核心。資料結構**必須**預留「自主檢查／抽查」的區分與「由誰檢查」。檢查時機與停留點，MVP **不做**，之後再加。缺失改善追蹤屬 [#76](https://github.com/speko-tw/inspect-flow/issues/76)（0.7.x）、簽認屬 [#77](https://github.com/speko-tw/inspect-flow/issues/77)（0.8.x），不在此決定。
- **狀態**：已決定。
- **考慮過但沒選**：只做抽查、不考慮自主檢查（資料結構不預留區分）。
- **為什麼選這個**：一級自主檢查與二級抽查是同一條品管鏈，分成兩套系統會讓資料無法串接；MVP 先聚焦目前甲方的實際用法。以上理由是依裁定內容整理，負責人未逐項說明。
- **代價**：資料模型要多預留「檢查層級」與「檢查者」欄位，即使 MVP 只用到抽查；一級自主檢查的流程與畫面不在 MVP 範圍，日後要另行規格。
- **什麼情況要重新討論**：要開始支援廠商自主檢查，或要加入檢查時機與停留點時。
- **依據**：負責人裁定（[#313](https://github.com/speko-tw/inspect-flow/issues/313) 追加裁定第 15～18 題，2026-10-02）。

<a id="kd-52"></a>
## KD-52：每個查核項次的檢查標準分文字與數值兩種

- **決策**：每個查核項次**得**選用「文字標準」或「數值標準」。文字標準沿用 [KD-37](#kd-37)：按計畫書原文以文字記錄，系統不解析。數值標準的欄位為：標準值、條件（`≤`、`≥`、`＝`、範圍）、單位、容許誤差。條件為「範圍」時有兩種形式，由內業設定時**擇一**：**區間形式**（下限、上限，例如 3.0～3.6 m）與**標準值與誤差形式**（標準值 ± 容許誤差，例如 3.3 ± 0.3 m）；其他條件（`≤`、`≥`、`＝`）維持原有欄位。0.3.x 的查核範本**只定義**這兩種標準欄位；實測值輸入屬 [#76](https://github.com/speko-tw/inspect-flow/issues/76)（0.7.x，規則見 [KD-54](#kd-54)）；系統不依標準值自動判定（[KD-37](#kd-37)、[KD-65](#kd-65)）。
- **狀態**：已決定（僅涵蓋以上範圍）；範圍條件兩種形式各自的欄位與驗證，裁定沒有說明，由規格定；實測值的輸入規則已由 [KD-54](#kd-54) 裁定、0.7.x 實作；系統不依標準值自動判定（[KD-37](#kd-37)、[KD-65](#kd-65)）。
- **考慮過但沒選**：數值標準也只存文字原文（[KD-37](#kd-37) 目前做法）。範圍條件的形式（2026-10-04 情境對答的選項）：只維持標準值 ± 容許誤差一種；範圍改成只填下限與上限一種。
- **為什麼選這個**：標準值、條件、單位與容許誤差結構化後，日後才能做實測值判定；0.3.x 先定義欄位，避免到 0.7.x 才回頭改查核範本結構。範圍條件兩種形式並存，推測是因為同一個範圍在計畫書裡可能寫成區間，也可能寫成標準值加減誤差，兩種都能照原樣設定。以上理由是依裁定內容整理，負責人未逐項說明；範圍形式的最後一句是整理者自己推得的理由，裁定本身只選了「兩種形式」。
- **代價**：查核範本與專案複本要多存一組數值標準欄位，範圍條件還要多存形式與下限、上限；[KD-37](#kd-37)「系統不解析、不自動判定」的範圍縮為文字標準與 #76 裁定前的暫行規則，兩者需在規格對齊。[KD-54](#kd-54) 規定實測欄位的單位與數值標準單位相同；兩種形式都只有一個單位（區間的下限、上限同單位），該規定仍成立（依裁定範例整理）。
- **什麼情況要重新討論**：之後要加自動判定時（須另行裁定，目前依 [KD-37](#kd-37)、[KD-65](#kd-65) 不自動判定）；內業反映兩種形式不敷使用時。
- **依據**：負責人裁定（[#313](https://github.com/speko-tw/inspect-flow/issues/313) 追加裁定第 15～18 題，2026-10-02）。檢查標準的架構基準背景為 §12.5（範本項目與查核項次）、§38 Result（量測值的未定案項目，見 [OQ-06](05-open-questions.md#oq-06)），章節對應非完全確定。新增的範圍條件兩種形式：架構基準無對應章節，裁定來源為[#313 留言](https://github.com/speko-tw/inspect-flow/issues/313#issuecomment-5974836112)（2026-10-04）。

<a id="kd-53"></a>
## KD-53：MVP 佐證只收照片，佐證類型未來可擴充

- **決策**：MVP 的佐證**只收照片**。額外文件（例如出廠證明、試驗報告）拍成照片，並以照片註記說明（[KD-50](#kd-50)）；報告功能（0.8.x）提供「補充文件」區，可附文件或連結；串接文件管理系統屬未來。佐證類型未來可能擴充（例如文件、量測數值、簽名、影片）。**不設**固定的檢討時點：有需要時開 issue，由負責人裁定後寫入規格再實作。原 `TEXT` 類型：規格已定不建立（TPL-Q4，規格設計，非負責人裁定；見 [`template-system` 規格](../specs/template-system/spec.md)），MVP 只支援照片。
- **狀態**：已決定。
- **考慮過但沒選**：MVP 同時支援 `NUMBER`、`BOOLEAN`、`SIGNATURE`、`DOCUMENT`（[OQ-20](05-open-questions.md#oq-20) 列出的另一選項）。
- **為什麼選這個**：MVP 先聚焦照片佐證，額外文件以照片加註記處理已能滿足現場需求，其餘類型有需要再加。以上理由是依裁定內容整理，負責人未逐項說明。
- **代價**：文件類佐證在 MVP 只有照片畫質，沒有原始檔案；補充文件要等 0.8.x 的報告功能才能附上。
- **什麼情況要重新討論**：實際出現要附原始文件或檔案、量測值、簽名、影片的需求時，由負責人開 issue 裁定。
- **依據**：負責人裁定（[#88 留言](https://github.com/speko-tw/inspect-flow/issues/88#issuecomment-5956040233)，2026-10-02）；補充見 [#88 補充留言](https://github.com/speko-tw/inspect-flow/issues/88#issuecomment-5956189277)（2026-10-02）。

<a id="kd-54"></a>
## KD-54：查核項次結果分符合／不符合／不適用，並規定各結果的必填內容

- **決策**：每個查核項次的結果有三種：「符合」「不符合」「不適用」（N/A）。
  - 選「不符合」時，**必須**選嚴重度（輕微、一般、嚴重），並**必須**填註解說明問題。
  - 選「不適用」時，**必須**填原因；照片選填。
  - 項次設有實測欄位時，**必須**全部填寫才能選「符合」或「不符合」；量不到時改選「不適用」並寫原因。
  - 實測欄位的型別由內業設定：「數字」（**必須**設單位，只接受數字）或「文字」（自由填寫）。項次設有數值標準時，對應實測欄位的單位**必須**與該數值標準單位相同，由系統自動帶入、不得另設；現場自行換算，單位換算不在本次範圍。
  - 版本劃分（依 [KD-52](#kd-52) 的範圍劃分整理，不是負責人裁定）：實測欄位的定義（型別、單位）屬範本結構，由 0.3.x 範本規格定義；現場填值屬 0.7.x（依 KD-52 與 [06](06-versioning-and-milestone-governance.md)）。
  - 不在本次裁定：不符合後的簡易改善追蹤另依 [KD-65](#kd-65) 排入 0.7.x；KD-65 不做限期提醒與自動通知，也不依標準值自動判定（見 [OQ-06](05-open-questions.md#oq-06)）。系統**不得**依標準值自動判定的規定仍依 [KD-37](#kd-37)。
- **狀態**：已決定（僅涵蓋以上範圍）；嚴重度對任務完成判定與報告呈現的影響，裁定沒有說明，待規格或 0.7.x 處理。
- **考慮過但沒選**：維持只有符合與不符合、不擴充欄位（[OQ-06](05-open-questions.md#oq-06) 列出的另一選項）。
- **為什麼選這個**：現場有些項次量不到或不適用，只有符合與不符合會逼人選錯；不符合要有嚴重度與說明、不適用要有原因，之後才分得出差別；實測欄位全部填完才能判定，避免漏量。以上理由是依裁定內容整理，負責人未逐項說明。
- **代價**：每個查核項次要多記錄嚴重度、註解與不適用原因；內業要為每個實測欄位設定型別，數字欄位還要設單位。[KD-37](#kd-37)「標準值按原文以文字輸入、系統不解析」與「數字欄位必須設單位、只接受數字」的適用範圍，裁定沒有說明，需在規格對齊。數值標準與對應實測欄位使用相同單位，現場需自行換算。
- **什麼情況要重新討論**：檢視 [KD-65](#kd-65) 的簡易改善追蹤是否足夠，或之後要加限期提醒與自動判定時；現場試用發現三種結果或必填規則不敷使用時。
- **依據**：負責人裁定（[#76 留言](https://github.com/speko-tw/inspect-flow/issues/76#issuecomment-5965076758)，2026-10-03）；補完 [OQ-06](05-open-questions.md#oq-06) 原本未定的部分，與 [KD-37](#kd-37)、[KD-52](#kd-52) 並用；單位相同、不得另設，依負責人裁定（[#76 留言](https://github.com/speko-tw/inspect-flow/issues/76#issuecomment-5965931420)，2026-10-03）。實測欄位定義與填值的版本劃分是依 KD-52 的範圍劃分整理，裁定本身沒有說明。

<a id="kd-55"></a>
## KD-55：修改專案查核項目時詢問是否重新查核，選「要」則只作廢被修改的查核項目

- **決策**：
  - 內業修改專案查核項目並存檔時，系統**必須**跳出選單詢問「這次修改要讓現場重新查核嗎？」，並清楚警告：選「要」時，被修改項目過去的查核（結果與照片）會作廢，需要補查。
  - 選「要」：只作廢同一專案內用到被修改項次的任務裡**被修改的那個查核項目**，以新標準補查；舊結果與照片標示「標準變更作廢」存檔。同一任務其他項目的結果與照片**保留**；已完成的任務退回「進行中」，補查後再完成（負責人補充裁定，見[#103 留言](https://github.com/speko-tw/inspect-flow/issues/103#issuecomment-5970063986)，取代原本「用到該項次的任務全部作廢」的做法）。
  - 草稿任務還沒有結果與照片，不涉及作廢（依裁定整理，裁定沒有逐字說明）。
  - 選「不要」：只更正內容（例如錯字），不重查；同一專案內用到該項次的已建立任務（未開始、進行中、已完成）**一併更正**為修改後的內容，只更正文字，不動結果與照片，任務狀態不變；已發出的報告不受影響。這是 [PR-04](02-principles.md#pr-04)「任務需求快照不改寫」的明確例外，僅限內業選擇「不要」重新查核的更正；系統記錄誰、何時、改了什麼；精神與 [KD-42](#kd-42)（已完成任務可修正錯字、不重查）一致。
  - 系統**必須**記錄是誰、何時、選了什麼。
  - 作廢的照片、結果與當時標準**不刪除**，標示「標準變更作廢」存檔，內業人員**必須**找得到；報告不使用作廢資料。作廢項目的紀錄整份保留、只標示作廢，不改寫，符合 [PR-04](02-principles.md#pr-04)。
  - 系統資料與報告分開：已發出的報告存在報告系統，不受影響；之後產生報告一律從系統資料即時撈取。
  - 只影響被修改的查核項目；同一任務的其他項目與沒有用到該項次的任務都不受影響。
- **狀態**：已決定（僅涵蓋以上範圍）。原列為未定的兩項：無結果的任務直接套用新標準，已由 [`state-machines` 規格](../specs/state-machines/spec.md)定案（規格設計，非負責人裁定；任務狀態維持原狀見 STM-R04，「直接套用新標準」出自規格「Inspection Task」段）；新舊標準在資料上如何並存，規格沒有定案，仍待後續規格（`domain-model`、`inspection-planning`）依各自責任定義。其他原因的作廢與失敗路徑仍未定，見 [OQ-09](05-open-questions.md#oq-09)。完成的計畫遇作廢退回進行中、任務取消與已完成任務不重開，見 [KD-56](#kd-56)。
- **與其他議題的關係**：作廢資料不刪除與 [G-05](05-open-questions.md#g-05)（證據刪除與保留）有關，但 G-05 仍未裁定，本決策不代為決定證據刪除 API 與保留期限；已發出報告不受影響、之後從系統資料即時撈取，與 [G-06](05-open-questions.md#g-06)／[G-07](05-open-questions.md#g-07)（報告狀態與快照邊界）有關，這兩題仍未裁定，報告狀態機與快照邊界不因本決策而定。
- **考慮過但沒選**：
  - 第一輪（出自裁定前的情境對答，紀錄見 [#78 留言](https://github.com/speko-tw/inspect-flow/issues/78#issuecomment-5966398101)）：
    - 已建立的任務一律維持舊標準，要用新標準就刪除重建。
    - 只有未開始的任務自動換新標準，已開始或已完成的不動。
    - 內業改標準時，系統詢問是否套用到未開始的任務（負責人先選此項，接著補充「標準改了就要重查」，被整體做法取代）。
    - 怎樣算「已開始」（打開就算、存下資料才算、只有完成才不動）：被「不論進度一律重查」取代。
    - 已完成但未出報告的任務：不動，或交給內業逐一勾選是否重查；負責人選一律重查（範圍後來由第二輪縮小為被修改的項目）。
    - 作廢的照片與結果真的刪除；負責人選作廢存檔，內業要找得到。
    - 判斷是否觸發重查：任何修改都觸發（含錯字），或由系統自動判斷「改到要查什麼、怎樣算合格」才觸發；最後採用的是每次修改都由內業自己選，系統記錄並清楚警告作廢後果，即本決策。
  - 第二輪（選項表見[負責人留言](https://github.com/speko-tw/inspect-flow/issues/103#issuecomment-5970063986)；括號為負責人的選擇）：
    - 整個任務作廢重查（選只重查被修改的項目）。
- **為什麼選這個**：標準改了，舊查核不一定還成立，所以由內業決定要不要重查；只改錯字不該逼現場重做；同一任務其他項目的標準沒變，已查的結果與照片仍然有效，只作廢被改的那一項，現場不必整個任務重做；作廢資料不刪除，之後才能追查當時依據什麼標準、誰決定重查。以上理由是依裁定內容整理，負責人未逐項說明。
- **代價**：選「要」會讓已完成的任務退回「進行中」，現場要補查被修改的項目；一個任務裡的資料要分出有效與作廢，作廢要標在項目層級；作廢資料要額外保留並讓內業查得到；報告從系統資料即時撈取，已發出的報告與之後重新產生的報告內容可能不同（依裁定內容整理，與 G-06／G-07 相關）；記錄「誰、何時、選了什麼」的具體欄位待規格制定。
- **什麼情況要重新討論**：0.4.x 規格設計項目層級作廢的資料結構時；G-05、G-06、G-07 裁定後，一併檢視本決策是否相容；現場試用發現詢問流程不敷使用，或只重查被修改的項目不夠（例如整個任務都得重來）時。
- **依據**：議題背景為架構基準 §2.5、§12.9（需求快照與套用複製）、§18（狀態機）；裁定為負責人裁定（[#78 留言](https://github.com/speko-tw/inspect-flow/issues/78#issuecomment-5966290670)，2026-10-03；選「不要」時一併更正已建立任務見[補充裁定](https://github.com/speko-tw/inspect-flow/issues/78#issuecomment-5966446983)，同日），補完 [OQ-09](05-open-questions.md#oq-09) 的「專案副本與任務快照分工」；選「要」的範圍由負責人裁定（[#103 留言](https://github.com/speko-tw/inspect-flow/issues/103#issuecomment-5970063986)，2026-10-03，查核計畫補充題）改為只作廢被修改的查核項目；與 [KD-03](#kd-03)、[KD-42](#kd-42)、[PR-04](02-principles.md#pr-04) 並用。

<a id="kd-56"></a>
## KD-56：計畫狀態依任務自動變更，任務派出後現場才看得到、未完成可取消與恢復、已完成不可取消，有不符合仍可完成並標示「有缺失」

- **決策**：
  - 任務派出：任務建立後先為「草稿」，現場看不到；內業按「派出」後現場才看得到。計畫有任務派出時（第一個任務派出時），系統**必須**自動將計畫改為「進行中」（負責人第二輪裁定，[#103 留言](https://github.com/speko-tw/inspect-flow/issues/103#issuecomment-5969654262)）。未派出的草稿任務**得**直接刪除；派出後只能取消、不能刪除（負責人補充裁定，[#103 留言](https://github.com/speko-tw/inspect-flow/issues/103#issuecomment-5970063986)）。
  - 計畫完成：底下任務全部完成時，系統**必須**自動改為「已完成」，人員**不得**手動將計畫改為已完成（[KD-42](#kd-42)）；已取消的任務不計入完成判斷。計畫底下仍有草稿任務時，計畫**不算**完成：草稿須派出並查完，或刪除後，計畫才完成（負責人補充裁定，[#103 留言](https://github.com/speko-tw/inspect-flow/issues/103#issuecomment-5970063986)）。
  - 計畫已取消：計畫底下的任務全部取消時，系統**必須**自動將計畫改為「已取消」（新增的計畫狀態）。與完成判斷的關係：底下**有任務完成**、其餘任務取消，計畫為「已完成」；底下**沒有任何任務完成**、全部取消，計畫才是「已取消」。（兩者的分界是依「取消不計入完成判斷」整理，裁定沒有逐字說明。）
  - 封存：「封存」與取消封存由內業**手動**操作；**任何狀態**的計畫（進行中、已完成、已取消）都**得**封存。計畫封存後，底下任務**唯讀**；須先取消封存，才能查核、取消或恢復任務（依業界慣例提出，負責人同意，[#103 留言](https://github.com/speko-tw/inspect-flow/issues/103#issuecomment-5970063986)）。
  - 任務取消：未完成的任務（未開始、進行中）內業都**得**取消，**必須**填原因；已記錄的照片與結果保留，任務顯示「已取消」，**不計入**計畫完成判斷。**已完成的任務不得取消。**
  - 任務恢復：取消的任務**得**恢復，回到取消前的狀態繼續查核。取消期間若專案查核項目的標準被修改，恢復時**改用目前的標準**，任務原有結果中被修改的項目標示待重查（同 [KD-55](#kd-55) 的項目層級作廢）（負責人裁定，[#103 留言](https://github.com/speko-tw/inspect-flow/issues/103#issuecomment-5970733042)，2026-10-03）。
  - 已完成的任務**不開放**重新打開。要重新查核，走 [KD-55](#kd-55)（修改專案查核項目並選「要」重新查核，只作廢被修改的查核項目，任務退回「進行中」補查）；錯字與照片修正依 [KD-42](#kd-42)，任務維持已完成。
  - 計畫已完成後，若有任務因 [KD-55](#kd-55) 作廢被修改的項目、退回「進行中」，系統**必須**自動將計畫退回「進行中」，補查完成後再自動改回「已完成」。已封存的計畫**必須**先取消封存，才能修改標準（封存後任務唯讀，見上）。
  - 任務有「不符合」的項次（[KD-54](#kd-54)）時，資料齊全即可完成任務，計畫照常自動完成；任務清單與報告**必須**明顯標示「有缺失」。不符合後的簡易改善追蹤依 [KD-65](#kd-65)（0.7.x），不在本決策範圍（見 [KD-54](#kd-54)）。
- **狀態**：已決定（僅涵蓋以上範圍）。原列為未定的項目，已由 [`state-machines` 規格](../specs/state-machines/spec.md)收掉；以下是**規格設計**，不是負責人新的裁定：
  - 計畫在第一個任務派出前與沒有任務時為 `DRAFT`，**不設**「就緒」（READY）；計畫底下有草稿任務時，不得判為已完成或已取消（STM-R17）。
  - 恢復任務**不要求**原因，沿用取消的權限代碼；恢復後與取消封存後，計畫狀態都依目前任務集合重新推導（STM-R14、STM-R17）。
  - 原清單中「取消封存的操作與權限」：取消封存由內業操作（上方決策已裁定「封存與取消封存由內業手動操作」），權限代碼依權限規格（見規格「Inspection Plan」轉換表、STM-R16）。
  - 「有缺失」是任務清單上的旗標，不是狀態值；含「不符合」仍可完成（STM-R10）。
- **權限**：派出、取消與恢復任務、封存與取消封存**得**由哪些人執行，依 [OQ-08](05-open-questions.md#oq-08)、[KD-24](#kd-24)～[KD-29](#kd-29)（Admin 自訂角色與權限代碼）設定，具體代碼由規格制定；裁定只說「內業」，這裡不寫死職稱。
- **考慮過但沒選**：
  - 第一輪（出自裁定前的情境對答，紀錄見 [#78 留言](https://github.com/speko-tw/inspect-flow/issues/78#issuecomment-5967478534)）：
    - 計畫狀態全自動、不設封存；開始與封存都由內業手動。
    - 任務只能刪除、不留紀錄；改由現場提出、內業確認才取消。
    - 計畫已完成後遇標準變更作廢：計畫維持「已完成」不退回。
    - 有不符合的任務：不標示就可完成；或要改善完才算完成。
  - 第二輪（選項表見[負責人留言](https://github.com/speko-tw/inspect-flow/issues/103#issuecomment-5969654262)；括號為負責人的選擇）：
    - 任務組成：一項一任務；兩種都提供（選一任務多項）。
    - 取消範圍：只有未開始可取消；含已完成都可取消（選未完成都可取消、已完成不可取消）。
    - 取消後不可恢復、要重建新任務（選可恢復）。
    - 全部取消時：維持進行中、由內業手動封存；自動改為已完成（選新增「已取消」狀態）。
    - 派出：建立即派出；整個計畫一起派出（選每個任務按「派出」才可見）。
  - 第三輪（選項表見[負責人留言](https://github.com/speko-tw/inspect-flow/issues/103#issuecomment-5970063986)；括號為負責人的選擇）：
    - 草稿不算數、不擋計畫完成（選草稿處理掉才算完成）。
    - 草稿也只能取消、不能刪除（選未派出的草稿可直接刪除）。
    - 封存後任務是否唯讀：留言只列業界慣例預設一個選項，負責人同意，沒有列出其他選項。
- **為什麼選這個**：以下理由是依裁定內容整理，負責人未逐項說明。計畫狀態反映任務進度的客觀結果，由系統自動變更才不會與任務脫節（延續 [KD-42](#kd-42)）；封存是內業整理案件的管理動作，系統無從判斷，所以留給人，任何狀態都能封存才不會有收不掉的計畫。取消的任務保留並要求原因，事後才查得到為什麼不做；不計入完成判斷，計畫才不會被取消的任務卡住；可恢復，誤按取消時不必重建任務、也不會丟掉已記錄的照片與結果。已完成不重開也不能取消，重查一律走標準變更，讓「改了標準才重查」只有一條路，歷史（[PR-04](02-principles.md#pr-04)）才不亂。草稿先不給現場看，內業才有時間把任務建好再放出去。全部取消與已完成分開，是因為什麼都沒查成的計畫不應顯示為「已完成」。完成的計畫遇作廢退回進行中，狀態才不會與實際進度矛盾。草稿須處理完計畫才算完成，是因為還有沒派出的草稿時，計畫已完成會漏掉內業打算派出的工作；未派出的草稿現場沒看過、也沒有紀錄，直接刪除不會丟資料，派出後現場可能已記錄，所以只能取消，取消的資料保留；封存是收尾整理，封存後再動任務會讓整理好的紀錄變動，所以要先取消封存。有不符合不擋完成，是因為查核的工作是如實記錄現場，不是要求全部合格；改善屬 0.7.x。
- **代價**：計畫狀態會在任務變化時自動來回（完成、退回、再完成、已取消），每次任務狀態變化都要重新判斷；任務多了「草稿」與「派出」一步，內業建完任務必須記得派出；恢復任務要記住取消前的狀態；封存的計畫要改標準或操作任務得先取消封存，多一步；草稿沒處理完計畫不會完成，內業漏派或漏刪會讓計畫一直停在進行中；「有缺失」要在清單與報告上額外呈現。
- **什麼情況要重新討論**：現場試用發現計畫自動狀態不敷使用（例如需要手動結案）；現場試用發現派出、取消或恢復流程不順（負責人整體原則是先簡單做、實際用過再調整）；0.7.x 決定不符合後的改善追蹤時，一併檢視「有缺失」與任務完成的關係；`state-machines` 規格整理出裁定沒有說明的狀態與轉換時。
- **依據**：議題背景為架構基準 §18（狀態機）；裁定為負責人裁定（[#78 留言](https://github.com/speko-tw/inspect-flow/issues/78#issuecomment-5967467998)，2026-10-03，第 1、2、3、5 題與第 2 題補充；取消須填原因出自此留言）與負責人裁定（[#103 留言](https://github.com/speko-tw/inspect-flow/issues/103#issuecomment-5969654262)，2026-10-03，任務組成、取消範圍與恢復、全部取消、封存、派出）與負責人補充裁定（[#103 留言](https://github.com/speko-tw/inspect-flow/issues/103#issuecomment-5970063986)，2026-10-03，草稿與計畫完成、草稿刪除、封存後任務唯讀；封存後唯讀為依業界慣例提出、負責人同意）；補完 [OQ-09](05-open-questions.md#oq-09) 的計畫與任務部分；與 [KD-42](#kd-42)、[KD-54](#kd-54)、[KD-55](#kd-55) 並用。

## KD-57：報告由有權限者直接核發、不需送審，有錯時出新版取代舊版

- **決策**：
  - 報告產生後，有權限者**得**直接核發，**不需**送審；審核流程之後再加，本次不做。
  - 已核發的報告有錯時，**必須**出新版取代；舊版**必須**保留，並標示「已被新版取代」，**不得**覆蓋或刪除（與 [PR-06](02-principles.md#pr-06)「已核發版次不可覆蓋」一致）。
  - 「有權限者」依 [OQ-08](05-open-questions.md#oq-08)、[KD-24](#kd-24)～[KD-29](#kd-29)（Admin 自訂角色與權限代碼），不寫固定職稱；核發對應哪一個權限代碼，由規格制定。
- **狀態**：已決定（僅涵蓋以上範圍）。**未定**：`Report` 的其他狀態（產製中、產製失敗等）、完整狀態機與版次快照邊界，仍依 [G-06](05-open-questions.md#g-06)、[G-07](05-open-questions.md#g-07) 待規格整合；[PR-15](02-principles.md#pr-15) 的「產製失敗不得誤標為已完成」不因本決策改變。審核流程加入前，送審與核准類狀態（原 §20.6 列舉的 `UNDER_REVIEW`、`APPROVED`）是否保留，裁定沒有說明，待規格確認。「新版」與版次序號（REV.n）的對應、舊版是否仍可下載，裁定沒有說明，待規格確認。
- **與其他議題的關係**：[KD-55](#kd-55) 規定已發出的報告不受標準變更影響、之後產生的報告從系統資料即時撈取；本決策規定發出的報告有錯時如何更正（出新版、舊版標示被取代），兩者都不允許悄悄改變已核發的內容。
- **考慮過但沒選**（出自裁定前的情境對答，紀錄見 [#78 留言](https://github.com/speko-tw/inspect-flow/issues/78#issuecomment-5967478534)）：
  - 報告一定要審，且「送審」與「核准」分成兩個動作。
  - 是否送審改成每個專案可開關。
  - 已核發報告有錯時，舊版直接作廢。
- **為什麼選這個**：以下理由是依裁定內容整理，負責人未逐項說明。第一階段先把產出與核發做通，審核流程等實際需要再加，避免一開始就綁死流程；舊版保留並標示被取代，之後才查得到當時交付的內容，也符合已核發版次不可覆蓋的原則。
- **代價**：核發前沒有第二個人把關，錯誤要靠事後出新版更正；舊版要長期保存並在介面上標示，報告列表要能分辨現行版與被取代的版本。
- **什麼情況要重新討論**：加入審核流程時（須另行裁定送審與核准的規則，不得逕自實作）；G-06、G-07 裁定後，一併檢視本決策是否相容。
- **依據**：議題背景為架構基準 §20.6–20.8（Report 狀態與版次）、§18（狀態機）；裁定為負責人裁定（[#78 留言](https://github.com/speko-tw/inspect-flow/issues/78#issuecomment-5967467998)，[#94 留言](https://github.com/speko-tw/inspect-flow/issues/94#issuecomment-5967468330)，2026-10-03，第 4 題）；部分裁定 [G-06](05-open-questions.md#g-06)；與 [KD-55](#kd-55)、[PR-06](02-principles.md#pr-06)、[PR-15](02-principles.md#pr-15) 並用。

## KD-58：任務地點選用專案分區並可補充文字

- **決策**：`Project` 得依需要設定分區。專案有分區時，`Inspection Task` **必須**從該專案分區清單選一個，並**得**填選填補充文字；專案沒有分區時，任務只填補充文字。分區名稱由內業自訂，MVP 不規定編碼格式；同一專案內分區名稱去除空白後不分大小寫唯一。WBS 整合不納入 MVP，有對接需求時另開規格。
- **狀態**：已決定；分區名稱自訂、不規定編碼格式與同專案名稱唯一是依業界慣例整理的技術預設，非負責人另行裁定，後續得調整。
- **考慮過但沒選**：任務地點只用純自由文字；以棟別、樓層、區域、座標四欄組成結構化編碼。
- **為什麼選這個**：以下理由是依裁定內容整理，負責人未逐項說明。選用分區可沿用專案已設定的名稱，讓任務地點一致且可篩選；小型專案未設定分區時仍可直接補充文字，避免承擔固定結構化欄位的填寫負擔。WBS 對接另開規格，可避免 MVP 預設外部編碼契約。
- **代價**：有分區的專案需先維護分區清單；分區名稱的技術預設未來可依實際需求調整，WBS 對接需求須另行定義。
- **什麼情況要重新討論**：分區命名或唯一規則造成實際操作問題，或需要與 WBS 對接時，重新檢視技術預設或另開規格。
- **依據**：架構基準 §12.8、§38 Location；負責人裁定（[#73 留言](https://github.com/speko-tw/inspect-flow/issues/73#issuecomment-5976192382)，2026-10-04）；與 [KD-40](#kd-40)、[OQ-03](05-open-questions.md#oq-03) 並用。

## KD-59：Field UI 與 Admin Dashboard 合併排入 0.5.x

- **決策**：Field UI 與 Admin Dashboard 合併為 0.5.x，並將原 0.9.x、0.10.x、0.11.x 的能力依序調整為 0.8.x、0.9.x、0.10.x。0.5.x 目標是先做出兩個前端介面的雛形，並走過內業派任務、現場看任務與開始查核、後台看進度與工作量的大致使用情境；細節依試用回饋迭代。管理後台涵蓋原定的今日工作量、完成數、完成率、專案進度、工程師進度、唯讀總覽、管理畫面與查詢 API；完成數與完成率於 0.5.x 依 Task 狀態計算，0.7.x 完成驗證上線後，同一指標改採伺服器驗證結果，見 [KD-66](#kd-66)。原 0.8.x 範圍沒有其他依賴證據或伺服器完成驗證的管理後台指標。0.5.x 規格立即開寫，實作依 0.4.x API 進度開工。

## KD-61：現場版先上傳，內業版由後端依編輯操作產生

- **決策**：現場拍照後由前端壓縮產生現場版並直接上傳，不保存拍攝原圖。內業版由後端依內業編輯操作從現場版產生，前端只提供預覽。MVP 採 Online-first，不做離線佇列；上傳失敗時照片留在畫面上，可自動重試後手動重送。
- **狀態**：已決定；現場版與內業版是僅有的兩種照片，見 [KD-32](#kd-32)。
- **考慮過但沒選**：保存原始拍攝圖；用戶端直接產生內業版；MVP 先做離線佇列與重新連線同步。
- **為什麼選這個**：只保存兩版符合既有照片模型；由後端產生內業版可讓正式報告用圖一致且可追溯；離線同步複雜度高，列為後續能力。
- **代價**：現場上傳需網路連線；後端須依編輯參數產生並保存內業版。
- **什麼情況要重新討論**：試用顯示現場網路條件使 Online-first 無法完成核心流程時，重新評估離線能力。
- **依據**：架構基準 §13A.5、§13A.7–13A.8、§30 Phase 6、§35；維護者依負責人授權決定（2026-10-04，#388），負責人可推翻；與 [KD-32](#kd-32)、[KD-33](#kd-33) 並用。

## KD-62：依任務完成與報告引用狀態管理照片刪除

- **決策**：任務完成前，拍照者或內業**得**刪除未完成任務的照片；系統採軟刪除並寫入稽核紀錄。任務完成後**不得**刪除照片，只能依 [KD-42](#kd-42) 修正。已被核發報告引用的照片**不得**刪除；依 [KD-55](#kd-55) 作廢的資料保留。MVP 不做自動清除，保存期限隨專案。
- **狀態**：已決定；具體存取與呈現方式由 `field-evidence` 規格制定。
- **考慮過但沒選**：硬刪除已被核發報告引用的照片；由系統自動清除作廢資料。
- **為什麼選這個**：軟刪除與稽核保留歷史脈絡，避免已核發報告失去其引用證據；保存期限隨專案，避免另訂全系統保留期。
- **代價**：系統需保留刪除標記與操作紀錄；專案需承擔作廢資料保存空間。
- **什麼情況要重新討論**：法規、客戶契約或容量資料要求調整保存期限或刪除限制時。
- **依據**：架構基準 §13A.2、§13A.11、§15、§20.11；維護者依負責人授權決定（2026-10-04，#388），負責人可推翻；與 [KD-32](#kd-32)、[KD-42](#kd-42)、[KD-55](#kd-55)、[KD-56](#kd-56)、[KD-57](#kd-57)、[PR-05](02-principles.md#pr-05)、[PR-06](02-principles.md#pr-06)、[PR-07](02-principles.md#pr-07) 並用。

## KD-63：照片上傳採固定大小上限、有限重試與冪等鍵

- **決策**：單檔上限為 30 MB，且得由設定檔調整。前端遇上傳失敗自動重試 3 次，採指數退避，之後顯示手動重送。每次上傳帶前端產生的 UUID 作冪等鍵；後端重複收到同一鍵時回傳原結果。

- **代價**：前後端須共同保存並檢查冪等鍵；較大檔案仍受設定的單檔上限約束。
- **什麼情況要重新討論**：試用上傳資料顯示大小上限或重試策略妨礙正常使用時。
- **依據**：架構基準 §22.9、§35；維護者依負責人授權決定（2026-10-04，#388），負責人可推翻；與 [KD-61](#kd-61) 並用。

## KD-65：0.7.x 提供簡易的不符合改善追蹤

## KD-66：管理後台完成數與完成率依任務狀態計算

- **決策**：管理後台完成數與完成率依 `Task` 狀態計算，排入 0.5.x 交付。0.7.x 完成驗證上線後，同一指標自動改為經伺服器驗證的完成，不拆成兩個指標；原 0.8.x 範圍沒有其他必須依證據或伺服器完成驗證才得出的指標。
- **狀態**：已決定；本條不新增指標名稱。
- **考慮過但沒選**：將同一完成指標拆成不同儀表板指標；另開 0.6.x／0.7.x 管理後台指標 issue。
- **為什麼選這個**：同一指標隨完成判定能力提升而使用可得的判定來源，避免重複計數；不另加原 0.8.x 範圍沒有的指標。
- **代價**：0.5.x 的完成統計依當時 Task 狀態；0.7.x 上線後需切換為伺服器完成驗證結果，維持同一指標。
- **什麼情況要重新討論**：任務完成定義或伺服器完成驗證方式改變時。
- **依據**：架構基準 §30 Phase 7–8；維護者依負責人授權決定（2026-10-04，#388），負責人可推翻；與 [KD-56](#kd-56) 及 Phase 7 完成驗證規劃並用。

## KD-68：範本管理採階層清單與單頁分段詳情

- **決策**：範本管理桌面介面採左側階層清單（工程類別 → 系統 → 查核項目）、右側所選內容詳情；手機以清單與詳情單欄切換。查核項目在同一頁依基本資料、查核項次卡片與預覽分段編輯，項次內依「要記錄什麼 → 判定標準 → 照片」排列，可收合，不設逐步過關的精靈。新增與重新命名在詳情區使用分開的入口。具體介面與契約依 [#427 定案摘要](https://github.com/speko-tw/inspect-flow/issues/427#issuecomment-5981195507)及規格驗收；通用要求見 [PR-19](02-principles.md#pr-19)。
- **狀態**：已決定（負責人親手操作原型後核可）。
- **考慮過但沒選**：所有表單在樹列內展開，查核項目採每一步完成後才能前進的精靈。
- **為什麼選這個**：清單保留尋找脈絡，詳情集中操作；使用者可直接返回任一項次修正並隨時預覽。樹列內的長表單在手機容易擁擠，逐步精靈讓反覆維護與局部修改多出跨步操作。
- **代價**：須維護清單選取、展開與詳情草稿的狀態，並確保手機切換後仍能返回原位置。
- **什麼情況要重新討論**：負責人實機試用顯示此模式仍無法順利完成範本管理任務時。
- **依據**：架構基準 §5.3、§6.1–6.2、§31（介面脈絡）；具體選型為負責人指示（2026-10-04，[#431](https://github.com/speko-tw/inspect-flow/issues/431)），並於[#427 定案](https://github.com/speko-tw/inspect-flow/issues/427#issuecomment-5981195507)。

## KD-69：兩層權限模型：人員模組權限加專案角色，模組邊界單向

- **背景（負責人要點）**：開專案、管理範本庫、看全部專案進度都是「逐人給予」的能力，不該綁在角色上；角色只應該存在專案裡（例如專案工程師、現場工程師）。負責人也希望各功能模組將來可以各自獨立，新增模組時不必改既有的授權結構。負責人原話：「系統管理員當然什麼都可以做，但他可以授予一些人權限，讓他們可以做某些、也可以做模組的編輯的動作。」（其中「模組的編輯」後經負責人修訂，委派不附帶編輯能力，見下方委派。）示意圖、方案比較與業界參考見 [07-permission-model.md](07-permission-model.md)。
- **決策**：
  - **兩層權限，每層資料只放在一個模組**：第 1 層在人員模組，放身分、帳號、啟用／停用、系統管理者開關，以及**逐人勾選的模組權限**（例：專案模組「可使用」「開設專案」「看全部專案進度」，範本模組「可使用」「管理範本庫」）。第 2 層在專案模組，放專案、成員、**專案角色**與專案內動作權限；查核模組等功能模組掛在專案底下。
  - **角色只存在專案內**（專案角色是專案內動作權限的套餐；角色定義全系統共用、由 Admin 維護）。系統**不設全公司角色**，全公司層級的能力一律用模組權限。系統安裝時預建三個專案角色「專案工程師」「現場工程師」「專案查閱人員」，Admin 可修改名稱與內容；預設內容見 [OQ-08](05-open-questions.md#oq-08)。
  - **判斷順序**：專案外的事只看第 1 層；專案內的事兩層都要通過；Admin 兩層都放行。模組權限**不會**自動給任何專案內的動作權限：人員必須先是該專案的成員、被指派專案角色，專案內動作（查核項目、計畫與任務、派出、現場查核等）一律由專案角色決定。
  - **模組**：專案模組（專案本身：基本資料、成員、角色；共用底層）、查核模組（掛在專案底下）、範本模組。日後採購、報告等模組同樣掛在專案底下、共用同一份專案資料。用到哪個模組，就要有該模組的「可使用」：專案內的查核動作需要查核模組「可使用」加專案角色；專案基本資料的檢視與管理、成員管理需要專案模組「可使用」加專案角色。
  - **模組邊界單向**：專案模組做權限判斷時只向人員模組問四件事：他是誰、帳號有效嗎、是不是系統管理者、有沒有模組權限 X；不得直接讀人員資料表或管理者欄位（顯示用的成員列表等既有查詢不受此限）。專案模組也不直接讀查核模組的資料表，專案進度由查核模組提供唯讀查詢。
  - **新模組接入規則**：（1）宣告模組權限項目，第一項通常是「可使用此模組」；（2）宣告專案動作權限項目；（3）人員頁與角色編輯畫面自動多出選項；（4）後端多一種「需要模組權限」的存取宣告。
  - **開設專案**：「開設專案」是專案模組的模組權限，逐人給予，不綁角色；勾選時系統自動一併勾上專案模組「可使用」，已具「開設專案」時不得單獨收回「可使用」。具此權限者即使尚未加入任何專案，登入後也看得到「我的專案」頁與「新增專案」入口。**非管理者**開專案時，在同一個動作內自動成為該專案成員並取得「建立者角色」（預設「專案工程師」，Admin 可改）；**Admin 開專案不自動成為成員**，可選填一位專案工程師，一步完成交接；建立者不能自行挑選角色，任一步失敗整筆回滾。
  - **建立者角色**：被設為建立者角色的角色，系統一律保留「調整專案」與「管理成員」兩項，不能移除；改設其他角色為建立者角色前，先檢查新角色具備這兩項；要刪除目前的建立者角色，須先改設另一個。
  - **修改專案**：非 Admin 只能修改「自己是成員、且角色含調整專案」的專案（自己開的專案自動包含在內）；跨專案只有唯讀的「看全部專案進度」；修改所有專案只限 Admin。
  - **看全部專案進度**：專案模組的模組權限，本身即可看各專案的任務清單、狀態、地點、建議指派，不需另開查核模組「可使用」；可見欄位固定為這四項白名單，所有入口一致；看不到照片與查核結果（照片與結果的下載另行檢查權限）；要看照片與結果，須加入該專案並取得唯讀的專案角色（例如「專案查閱人員」）。只有 Admin 能授予這項權限。
  - **範本**：套用範本需要範本模組「可使用」（唯讀範本庫）加專案角色含「編輯查核項目」；只有「管理範本庫」能改範本庫（含跨專案瀏覽查核項目並存成範本，見 [KD-49](#kd-49)）。
  - **委派**：Admin 什麼都能做，也可以授權特定人員管理某個模組的權限。委派以模組為單位（「可授予 X 模組權限」），只代表「可以替別人開通、收回該模組的權限」，**不附帶任何模組的編輯能力**（要維護範本庫須另勾「管理範本庫」）；被委派者不能替自己授權、不能把委派權轉給別人，只有 Admin 能指派與收回委派者，也只有 Admin 能授予「看全部專案進度」；每次授予與收回（含委派的指派與收回）都寫稽核紀錄。
  - **權限組合**：提供「權限組合」，一鍵勾選多個模組權限；組合不是角色，修改組合**不會**追改已套用過的人。預設三組：「公司主管」＝專案模組可使用、看全部專案進度；「專案工程師常用」＝專案模組可使用、開設專案、查核模組可使用、範本模組可使用；「現場工程師常用」＝專案模組可使用、查核模組可使用；Admin 可增減修改。套用時逐項檢查授權範圍，任一項超出（例如被委派者套用含其他模組權限的組合）即整組不套用並說明原因。
  - **指派專案角色的限制**：持有管理成員權限的非管理者只能指派 Admin 事先核准的角色（預設「現場工程師」「專案查閱人員」），下拉選單只列可指派的角色，也不能修改自己的角色；後端擋下違規指派並寫稽核。專案工程師可把外部公司人員（例如業主代表、監造）加入專案，但只能指派唯讀這類可指派角色；外部人員的帳號與模組開通仍由 Admin 負責；不再限制非管理者只能加同公司人員。
  - **停用與啟用**：離職先停用帳號，已登入裝置立即失效（每次請求重新檢查帳號狀態）；停用前，若此人是某專案唯一的專案工程師，先提醒；模組權限與成員關係保留，成員清單標「已停用」；重新啟用前列出將恢復的模組權限、專案成員身分與未完成任務，由 Admin 勾選確認後才恢復；停用與啟用都寫稽核紀錄。
  - **上線回填**：改造時以 migration 自動補上「可使用」：既有專案成員補專案模組與查核模組「可使用」，`template_admin` 轉為範本模組「管理範本庫」並含範本模組「可使用」，可套用範本者補範本模組「可使用」。回填只寫在 migration，並以自動化測試驗證新舊有效權限一致（涵蓋示範與試用資料庫），不另設人工盤點流程。
  - **過渡行為**：v0.3.x 先交付 Admin 可管理範本；規格合併後到程式完成前，現行 `template_admin` 與只有 Admin 能開設專案的行為維持不變。

- **狀態**：已決定。以下是依業界慣例或兩位專家審查整理的規格設計，非負責人另行裁定，後續得調整：模組權限代碼命名與權限代碼加範圍屬性（模組權限／專案動作權限）；預設角色的權限內容細目；「專案查閱人員」只含讀取類代碼；全系統只有一個權限計算入口，所有路徑（登入者權限摘要、存取檢查、只看成員身分的端點）都經它；補登缺漏的讀取類權限代碼；專案模組不直接讀查核資料表；被委派者用的最小欄位人員查詢與「需模組委派」存取級別；新增與修改專案、被擋的違規指派、自動蘊含與回填產生的授權（標示來源）寫稽核；非管理者不得移除專案最後一位持管理成員權限者；收回「可使用」前顯示影響；重新啟用時未勾選項目的處理；預設權限組合以外的組合由誰維護；過渡期列出全部專案的條件。**待確認**：範本模組管理者從專案「存成範本」時能看到哪些專案；報告模組的權限項目（等正式報告規格再定）。
- **考慮過但沒選**：
  - **方案 B：全公司角色加專案角色**：要維護兩份角色清單，同名角色可能出現兩次，也打破「角色只存在專案內」；全公司角色的資料表、API、畫面與影響預覽要整套新建，改動成本最高。
  - **方案 C：一份混合角色**（角色同時含開專案與派任務）：一張角色表橫跨兩個模組，每項權限都要判斷「在這裡生不生效」，清單越長越亂，將來模組獨立時還得拆表。
  - 專案與查核合為單一模組；被委派者可再轉委派；委派附帶模組編輯能力；Admin 開專案自動成為成員；非管理者可指派任意角色。
- **為什麼選這個**：以下理由依裁定內容整理，負責人未逐項說明。每層資料只放在一個模組、邊界單向，新增模組時只需宣告權限項目，不必改既有授權結構，將來模組可以各自獨立；模組權限逐人給予，直接對應「開專案、管範本、看全部進度各自獨立給人」的需求；角色只留在專案內，同一個人在不同專案可有不同職責，又不會與全公司層級的權限混在一起；委派只管「開通權限」而不附帶編輯能力，讓「誰能改範本庫」只看一欄；可指派角色白名單與不能改自己的角色，依最小權限原則避免專案工程師自行升權。
- **代價**：授權檢查要先判斷 Admin，再判斷模組權限，專案內再判斷專案角色（見 [KD-24](#kd-24)）；人員頁需提供模組權限勾選、權限組合與委派的管理畫面；模組權限與專案角色可能互相缺漏，加入成員時須提示尚未開通的模組；既有 `template_admin` 與既有成員需 migration 回填；跨模組目前有三處直接讀對方資料的寫法須收斂（登入者權限摘要 `services/access_summary.py`、專案 API 直接查人員與公司表 `api/v1/projects.py`、專案服務直接讀管理者欄位 `services/inspection_planning.py`）；預建角色與預設組合需在安裝與 migration 時冪等建立。
- **什麼情況要重新討論**：新增模組或權限項目數量使勾選難以維護時；委派範圍需要更細（例如單項權限）或需要轉委派時；Admin 全權原則改變時。
- **備註（業界參考，不是依據來源）**：施工管理與營建雲端協作類產品（例如 Procore、Autodesk Construction Cloud）也把公司層與專案層權限分開管理，與本決策方向相近；沒有證據顯示公司層一定要逐人勾選，誰能建專案、建立者是否自動成為成員也沒有查到確切資料，這兩點依負責人裁定。此備註不構成任何「必須」。
- **依據**：架構基準 §17；負責人裁定（[#538 留言](https://github.com/speko-tw/inspect-flow/issues/538#issuecomment-6081228914)，2026-10-09：兩層模型與第 1～5 項）；補充裁定（[#538 留言](https://github.com/speko-tw/inspect-flow/issues/538#issuecomment-6081327833)，2026-10-09：第 6～9 項）；第 8～24 項與其修訂記在 [#538 內文](https://github.com/speko-tw/inspect-flow/issues/538)（2026-10-09）；範本管理行為見 [#313](https://github.com/speko-tw/inspect-flow/issues/313)；權限表見 [OQ-08](05-open-questions.md#oq-08)，完整說明見 [07-permission-model.md](07-permission-model.md)；與 [KD-24](#kd-24)～[KD-27](#kd-27)、[KD-29](#kd-29)、[KD-49](#kd-49) 並用。

## 技術棧卡片

卡片的「不要用」指出與本階段目標不合的做法。標為「建議」或「待定」時，卡片不替團隊拍板。

<a id="stack-backend-language"></a>
### Backend 語言

- **選用**：Python 3.12 作為基準版本。
- **負責什麼**：Backend API、業務規則、報告與影像處理。
- **狀態**：建議。
- **為什麼**：生態與團隊維護成本適合現階段；依賴的精確版本由 lockfile 固定。
- **不要用**：未經驗證就追最新 Python major。
- **未來升級路線**：新版 Python 經依賴、測試及 image 驗證後再升級。
- **依據**：架構基準 §4.1。

<a id="stack-web-api"></a>
### Web API

- **選用**：FastAPI；API 採 REST／JSON，照片上傳採 `multipart/form-data`。
- **負責什麼**：外部 API、驗證入口、上傳、授權入口與 OpenAPI 文件。
- **狀態**：建議（FastAPI）；API 邊界已決定，見 [KD-01](#kd-01)。
- **為什麼**：型別整合與文件產生方便內部系統開發。
- **不要用**：把大量業務邏輯寫在 route，或讓前端直接連資料庫。
- **未來升級路線**：維持 `/api/v1` 契約；框架版本由測試後的 lockfile 固定。
- **依據**：架構基準 §4.2、§7.1、§14。

<a id="stack-asgi-server"></a>
### ASGI 伺服器

- **選用**：uvicorn。
- **負責什麼**：本機開發時啟動 FastAPI（`make run-backend`）。
- **狀態**：建議；正式部署用什麼伺服器不在此決定，留給 pilot-deployment（[#109](https://github.com/speko-tw/inspect-flow/issues/109)）。
- **為什麼**：FastAPI 需要 ASGI 伺服器才能執行；uvicorn 是它文件的預設選擇，支援開發用的自動重載。
- **不要用**：把本機開發的啟動方式直接當成正式部署設定。
- **未來升級路線**：部署方式定案後再補正式環境的伺服器設定；依賴版本由 lockfile 固定。
- **依據**：負責人裁定（[PR #212 留言](https://github.com/speko-tw/inspect-flow/pull/212#issuecomment-5851963155)，2026-09-27）；架構基準無對應章節。

<a id="stack-api-schema"></a>
### API Schema

- **選用**：Pydantic v2 系列。
- **負責什麼**：Request／Response 型別與輸入驗證。
- **狀態**：建議。
- **為什麼**：在資料進入 Service 前建立清楚的 API 契約。
- **不要用**：只在前端驗證，或把未驗證的 JSON 直接交給業務規則。
- **未來升級路線**：隨 API 契約演進調整 schema；精確依賴版本由 lockfile 固定。
- **依據**：架構基準 §4.3、§16.1。

<a id="stack-orm"></a>
### ORM 與資料存取

- **選用**：SQLAlchemy 2.x，見 [KD-06](#kd-06)。
- **負責什麼**：讓 Service 存取 SQLite／PostgreSQL。
- **狀態**：已決定。
- **為什麼**：降低資料庫切換時的程式改動。
- **不要用**：到處散落 SQLite 專用 raw SQL；需要 raw SQL 時要標明資料庫相依性。
- **未來升級路線**：先以 PostgreSQL 整合測試確認相容性，再搬移資料。
- **依據**：架構基準 §4.4、§7.3、§32、§37 ADR-005。

<a id="stack-migration"></a>
### Database Migration

- **選用**：Alembic，見 [KD-06](#kd-06)。
- **負責什麼**：建立、升級與追蹤正式 schema。
- **狀態**：已決定。
- **為什麼**：每次 schema 變更都要可審查、可重現。
- **不要用**：正式環境靠 `create_all()` 或未記錄的手動 ALTER。
- **未來升級路線**：SQLite 與 PostgreSQL 都要跑 migration 驗證。
- **依據**：架構基準 §4.5、§22A.9、§27.3。

<a id="stack-frontend"></a>
### Frontend

- **選用**：React、TypeScript、Vite；Admin／Field 共用單一程式庫，見 [KD-12](#kd-12)。
- **負責什麼**：現場與後台操作畫面、API Client、前端建置。
- **狀態**：建議（工具）；已決定（單一程式庫，見 [KD-12](#kd-12)）。
- **為什麼**：支援手機介面與 Dashboard，TypeScript 可減少欄位錯誤。
- **不要用**：把資料庫或 storage key 當作前端存取契約。
- **未來升級路線**：如差異擴大，評估拆分；實際套件版由 lockfile 固定。
- **依據**：架構基準 §5.1–5.2、§37 ADR-008。

<a id="stack-pwa"></a>
### PWA

- **選用**：現場 Web 朝 PWA 相容設計；MVP 先採 Online-first。
- **負責什麼**：手機與平板使用路徑，保留日後安裝與離線草稿能力。
- **狀態**：建議；完整離線同步是延後能力。
- **為什麼**：工程師可用 iPhone、iPad 或 Android 開啟 Web App。
- **不要用**：把 PWA 相容等同已完成離線同步。
- **未來升級路線**：依 Pilot 網路資料，再加入 cache、draft、待上傳佇列與同步。
- **依據**：架構基準 §5.3、§13A.14、§34–35。

<a id="stack-database"></a>
### 資料庫

- **選用**：MVP 用 SQLite；`foreign_keys = ON`、WAL **應**在連線初始化時確認。見 [KD-08](#kd-08)。
- **負責什麼**：人員、專案、範本、任務、證據 metadata 與報告資料。
- **狀態**：已決定（SQLite）；建議（兩項 PRAGMA）。
- **為什麼**：Pilot 規模可先降低維運負擔。
- **不要用**：多台後端經 NAS 共用同一個 SQLite 檔。
- **未來升級路線**：併發、鎖定或維運需求增加時轉 PostgreSQL。
- **依據**：架構基準 §9–10、§32、§37 ADR-003。

<a id="stack-photo-storage"></a>
### 照片儲存

- **選用**：本機持久化儲存與 Storage 介面；檔案和 DB metadata 分離。見 [KD-02](#kd-02)。
- **負責什麼**：現場版、內業版兩張照片的檔案存取（見 [KD-32](#kd-32)）。
- **狀態**：已決定（分離與介面）；建議（第一版本機儲存）。
- **為什麼**：避免照片 BLOB 撐大 SQLite，也保留遷移彈性。
- **不要用**：原檔名當唯一 key；業務邏輯直接寫死檔案路徑。
- **未來升級路線**：以 MinIO、S3 或 NAS 實作相同 Storage 介面；照片版本模型見 [KD-32](#kd-32)、[G-02](05-open-questions.md#g-02)（已裁定）。
- **依據**：架構基準 §2.3、§7.4、§13.1–13.2、§33。

<a id="stack-image-processing"></a>
### 現場影像處理

- **選用**：前端即時預覽；後端可用 Pillow 依編輯參數產生內業版。見 [KD-32](#kd-32)、[KD-33](#kd-33)、[OQ-14](05-open-questions.md#oq-14)。
- **負責什麼**：現場端裁切、旋轉、亮度等編修，以及內業端加工產生內業版。
- **狀態**：待定（Frontend Render 或 Backend Render）；照片只保存現場版、內業版兩張已決定（見 [KD-32](#kd-32)）。
- **為什麼**：前端預覽反應快；後端處理有利結果一致與重現。
- **不要用**：另外保存原始拍攝檔案或編輯中間版本；提供會增刪現場內容的標準修圖功能。
- **未來升級路線**：離線時先存現場版與編輯參數，連線後再上傳及產生內業版；見 [G-03](05-open-questions.md#g-03)。
- **依據**：架構基準 §13A.2、§13A.5–13A.8、§13A.14；照片版本模型依負責人決定（#90～#92，2026-09-28）。

<a id="stack-docx"></a>
### DOCX 產製

- **選用**：版本化的報告範本（DOCX 報告版面）；Python 端**應**先評估 `python-docx`，複雜樣板可評估 `docxtpl`。見 [KD-05](#kd-05)。
- **負責什麼**：用 Report View Model 產生可編輯的正式 Word 文件。
- **狀態**：已決定（DOCX 輸出與報告範本版本）；建議（函式庫）。
- **為什麼**：業主與標案常沿用 Word 表單；版次要能對應報告範本的版本。
- **不要用**：從瀏覽器 UI state 拼正式報告，或把 DOCX 當暫存下載。
- **未來升級路線**：增加不同業主樣板與 View Model Builder，不改歷史文件。
- **依據**：架構基準 §20.2–20.5、§20.19、§37 ADR-009。

<a id="stack-pdf"></a>
### PDF 轉換

- **選用**：以 DOCX 為來源產出 PDF；轉換器待 Pilot 驗證，見 [KD-05](#kd-05)、[OQ-15](05-open-questions.md#oq-15)。
- **負責什麼**：產生提交與歸檔用 PDF。
- **狀態**：已決定（PDF 輸出）；待定（LibreOffice Headless 或受控轉換服務）。
- **為什麼**：兩種格式要共享報告資料與正式版面。
- **不要用**：只以 HTML 列印 PDF 當正式報告；未實測就指定 Production 轉換器。
- **未來升級路線**：依字型、表格、圖片、頁碼、分頁及簽名欄實測結果選轉換服務。
- **依據**：架構基準 §20.3–20.4、§20.20–20.22。

<a id="stack-auth"></a>
### 認證與授權

- **選用**：內部帳號搭配 Server-managed Session 與 HttpOnly Cookie（Secure、SameSite），見 [KD-30](#kd-30)；密碼以 Argon2id 雜湊，見 [KD-31](#kd-31)。兩者由負責人裁定，見 [OQ-13](05-open-questions.md#oq-13)。
- **負責什麼**：登入、目前使用者與 API 權限檢查。
- **狀態**：建議（內部帳號）；已決定（Session 與 HttpOnly Cookie、Argon2id，見 [KD-30](#kd-30)、[KD-31](#kd-31)）；已決定（權限機制，見 [KD-24](#kd-24)～[KD-29](#kd-29)）。
- **為什麼**：先滿足內部系統需求，不必在 MVP 建完整 OAuth 基礎設施。
- **不要用**：把長效 JWT 直接放在 browser localStorage。
- **未來升級路線**：`User` 已預留外部身分來源欄位與同步比對規則，見 [KD-20](#kd-20)；實際串接方式（含 Corporate SSO）另開「外部身分同步」規格，見 [docs/specs/README.md](../specs/README.md#index)，本卡不預先寫串接方式。角色矩陣已裁定，見 [OQ-08](05-open-questions.md#oq-08)。
- **依據**：架構基準 §17、§35、§36；Session 與密碼雜湊為負責人決定（#82，2026-09-26）。

<a id="stack-deployment"></a>
### 部署

- **選用**：Linux Server、Docker Engine、Docker Compose 與版本化 image，見 [KD-09](#kd-09)。
- **負責什麼**：啟動 Web、API、Reverse Proxy；掛載持久化資料。

- **為什麼**：單機 Pilot 可重現部署與更新，不先引入多節點編排。
- **不要用**：正式環境臨時改 container 程式或把資料放在暫存層。

<a id="stack-reverse-proxy"></a>
### Reverse Proxy 與 HTTPS

- **選用**：正式環境提供 HTTPS；Caddy、Nginx 或企業現有 Proxy 可選。見 [KD-09](#kd-09)。
- **負責什麼**：將 `/api/*` 導向後端，其餘請求導向前端。
- **狀態**：已決定（HTTPS）；建議（Caddy）；待定（正式 Proxy 選型）。
- **為什麼**：使用者不需要直接連 API 容器埠。
- **不要用**：把 API 或未受控資料庫埠直接暴露給一般使用者。
- **未來升級路線**：可改接企業 Proxy 或 Load Balancer，保留外部 HTTPS 入口。
- **依據**：架構基準 §22.5、§22.10–22.11。

<a id="stack-tests"></a>
### 測試工具

- **選用**：Backend 以 pytest；Frontend component 可用 Vitest；關鍵流程可用 Playwright。
- **負責什麼**：驗證 task generation、快照、Evidence、權限、完整使用者流程與 PostgreSQL 相容性。
- **狀態**：建議（工具）；關鍵流程與跨資料庫驗證為來源要求。
- **為什麼**：任務與正式報告的資料正確性要能重複驗證。
- **不要用**：只測 UI 顯示而略過後端完成驗證或報告內容。
- **未來升級路線**：隨正式報告樣板增加 DOCX/PDF 資料與版面測試。

<a id="stack-ci"></a>
### CI

- **選用**：GitHub Actions；每次 PR 執行 lint、後端測試、前端測試、build 與 PostgreSQL 相容性測試。見 [KD-09](#kd-09)。

- **負責什麼**：基本 lint、格式與型別檢查。formatter 管排版、linter 管寫法、型別檢查器管型別，三者不重疊。
- **狀態**：
