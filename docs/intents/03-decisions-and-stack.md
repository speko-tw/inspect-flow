# 關鍵決策與技術棧

**這份文件回答**：InspectFlow 選了哪些架構方向？各項工具負責什麼？
**什麼時候讀**：選技術、調整模組邊界、規劃資料遷移、製作報告或部署服務時。

本文件保留 KD-01 到 KD-12 的編號。技術棧卡片另標「已決定／建議／待定」。卡片狀態依架構基準正文判定，不以 §36 的表格直接推定。規則強度見本目錄 README；尚未定案的細節見 [待決議](05-open-questions.md)。

## 關鍵決策

<a id="kd-01"></a>
## KD-01：外部用戶端只透過後端 API 存取資料

- **決策**：Field Web、Admin Web 等外部用戶端**必須**經後端 API 讀寫資料；前端**不得**直接連資料庫或檔案儲存。後端 Report Service 可直接使用服務、資料存取與儲存介面，不必呼叫自己的 HTTP API。見 [PR-01](02-principles.md#pr-01)。
- **狀態**：已決定。
- **考慮過但沒選**：前端直接連資料庫或組出儲存路徑。
- **為什麼選這個**：權限、驗證與業務規則集中在後端；換資料庫時，前端契約可維持穩定。
- **代價**：外部存取要先定義 API；後端要維護 API 契約。
- **什麼情況要重新討論**：新增獨立外部服務，且現有 API 無法滿足資料交換需求時，檢查 API 契約與授權邊界；前端禁直連的要求仍有效。
- **依據**：架構基準 §2.2、§20.2、§37 ADR-002。

<a id="kd-02"></a>
## KD-02：照片檔案與關聯式資料分開存放

- **決策**：資料庫保存 Evidence metadata；檔案存入 Storage。後端產生 storage key，不以原始檔名當唯一識別。業務邏輯經 Storage 介面讀寫檔案。見 [PR-02](02-principles.md#pr-02)。
- **狀態**：已決定。
- **考慮過但沒選**：照片以 BLOB 放進 SQLite；原始檔名直接當 storage key。
- **為什麼選這個**：照片是容量主因；分開存放可控制資料庫大小，並保留物件儲存遷移路徑。
- **代價**：檔案與資料庫需要配對備份，也要處理兩邊寫入失敗。原圖與 Variant 的唯一資料來源仍見 [G-02](05-open-questions.md#g-02)。
- **什麼情況要重新討論**：本機檔案容量、備份或存取需求超出單機能力時，評估 MinIO、S3 或 NAS；Storage 介面仍維持。
- **依據**：架構基準 §2.3、§7.4、§13.1–13.2、§33、§37 ADR-004。

<a id="kd-03"></a>
## KD-03：範本版本化，任務建立時固定需求

- **決策**：`Inspection Template` **必須**版本化。建立 `Inspection Task` 時，**必須**把當時的需求固定為 `Task Requirement Snapshot`。後續範本異動不得改寫舊任務的需求。見 [PR-04](02-principles.md#pr-04)。
- **狀態**：已決定。
- **考慮過但沒選**：任務每次查詢都讀範本的目前版本。
- **為什麼選這個**：系統要能回答「任務建立當時要求什麼」。
- **代價**：任務需要自己的需求資料，且要保存來源需求的關聯。
- **什麼情況要重新討論**：若新需求要修改已建立任務，先定義更正或重新建立任務的流程；不能直接改寫歷史快照。
- **依據**：架構基準 §2.5、§12.9、§37 ADR-006。

<a id="kd-04"></a>
## KD-04：照片編輯不覆蓋原圖

- **決策**：照片可裁切、旋轉或調整亮度，但**不得**覆蓋原圖。編輯結果另存 Evidence Variant，並保存操作參數、建立者、時間與雜湊。縮放檢視可只影響畫面。見 [PR-05](02-principles.md#pr-05)。
- **狀態**：已決定。
- **考慮過但沒選**：直接改寫原圖；把物件移除、新增或生成式修圖列為標準功能。
- **為什麼選這個**：照片是查核證據，裁切與調亮可能改變判讀，必須能回看原圖。
- **代價**：同一筆 Evidence 可能有多個檔案；需要保存 Variant 系譜。刪除與保留期限見 [G-05](05-open-questions.md#g-05)。
- **什麼情況要重新討論**：新增影像操作、標註或業主要求揭露編輯資訊時，檢查證據可追溯性與允許操作清單。
- **依據**：架構基準 §13A.2–13A.6、§37 ADR-010。

<a id="kd-05"></a>
## KD-05：DOCX 與 PDF 是 MVP 的正式交付物

- **決策**：MVP **必須**產出 DOCX 與 PDF。報告從後端 Report View Model 和版本化 DOCX 範本產生；HTML 可做預覽，不能取代正式文件。報告需保存範本版本、文件編號、版次、快照、檔案鍵、雜湊與產製資訊。見 [PR-06](02-principles.md#pr-06)。
- **狀態**：已決定；完整核准、簽名與核發流程仍待決議，見 [OQ-07](05-open-questions.md#oq-07)、[G-11](05-open-questions.md#g-11)。
- **考慮過但沒選**：只從 HTML 直接列印 PDF；只提供一次性下載檔。
- **為什麼選這個**：業主、監造與標案文件需要可提交、可歸檔、可追溯的正式產物。
- **代價**：需要管理 DOCX 範本、版面驗收及 PDF 轉換。轉換工具見 [OQ-15](05-open-questions.md#oq-15)。
- **什麼情況要重新討論**：正式收件規範改變，且 DOCX／PDF 不再滿足交付要求時，新增決策並評估舊報告的保存方式。
- **依據**：架構基準 §20.1–20.7、§20.22、§30 Phase 9、§37 ADR-009。

<a id="kd-06"></a>
## KD-06：資料庫存取用 SQLAlchemy，結構演進用 Alembic

- **決策**：資料庫存取**必須**經 SQLAlchemy。Schema 變更**必須**走 Alembic migration。正式環境**不得**靠 `Base.metadata.create_all()` 或未記錄的手動 ALTER 管理版本。見 [PR-03](02-principles.md#pr-03)。
- **狀態**：已決定。
- **考慮過但沒選**：正式環境直接建立表格或手動改 schema；大量使用 SQLite 專用 SQL。
- **為什麼選這個**：把 SQLite 換成 PostgreSQL 時，資料庫差異較容易收斂在資料存取與 migration 層。
- **代價**：每次 schema 變更都要寫、審查及驗證 migration。
- **什麼情況要重新討論**：導入 SQLAlchemy 無法支援的資料庫能力時，記錄相依性並以雙資料庫測試驗證；正式 schema 變更仍需可追蹤。
- **依據**：架構基準 §4.4–4.5、§22A.9、§32、§37 ADR-005。

<a id="kd-07"></a>
## KD-07：主要實體以 UUID 識別

- **決策**：Project、User、Plan、Task、Evidence 等主要實體使用 UUID。UUIDv7 **得**優先評估。人類可讀的業務編號與 UUID 分開保存。
- **狀態**：已決定；UUID 版本待實作選擇。
- **考慮過但沒選**：完全依賴 SQLite AUTOINCREMENT 作為跨系統身分。
- **為什麼選這個**：減少資料合併時撞號的風險，並保留離線用戶端自行產生 ID 的空間。
- **代價**：UUID 較長；畫面與文件還要另外使用可讀的業務編號。
- **什麼情況要重新討論**：離線建立、跨系統合併或排序效能提出具體需求時，選定 UUID 版本與產生位置；不改用自增值作為唯一對外識別。
- **依據**：架構基準 §11、§37 ADR-007。

<a id="kd-08"></a>
## KD-08：MVP 先用單機 SQLite

- **決策**：MVP 使用 SQLite。多台後端**不得**透過網路檔案系統共用同一個 SQLite 檔。連線初始化**應**確認 `foreign_keys = ON` 與 WAL；來源把兩項 PRAGMA 稱為「建議確認」，不是額外的 ADR 強制項。
- **狀態**：已決定；PRAGMA 屬建議設定。
- **考慮過但沒選**：MVP 一開始就維運 PostgreSQL；多台伺服器共用同一個 SQLite 檔。
- **為什麼選這個**：Pilot 規模小、schema 尚在變動，先降低資料庫維運成本。
- **代價**：寫入併發及資料庫維運能力有限；備份須處理 WAL 的一致性。
- **什麼情況要重新討論**：需要第二台後端、同時寫入明顯增加，或備份、鎖定、監控需求超出 SQLite 能力時，轉向 PostgreSQL。
- **依據**：架構基準 §9.1–9.2、§10、§23、§37 ADR-003。

<a id="kd-09"></a>
## KD-09：Pilot 與正式環境採 Linux 和 Docker Compose

- **決策**：Pilot／Production 使用 Linux Server、Docker Engine、Docker Compose 與持久化儲存。正式變更經 Git、審查、CI、版本化 image；migration 必須納入發布流程。見 [PR-13](02-principles.md#pr-13)。
- **狀態**：已決定；migration 與服務啟動的先後順序暫定，見 [PR-13](02-principles.md#pr-13)、[G-09](05-open-questions.md#g-09)。
- **考慮過但沒選**：個人電腦、臨時 VM、沒有持久化磁碟的主機，或第一天就導入多節點編排。
- **為什麼選這個**：開發與正式環境較易重現，也能以固定流程備份、更新及回滾。
- **代價**：Compose 本身不提供多節點協調與自動容錯；部署仍需要維運程序。
- **什麼情況要重新討論**：需要多節點、高可用、自動容錯或大量後端副本時，評估編排平台。部署順序的來源歧義見 [G-09](05-open-questions.md#g-09)。
- **依據**：架構基準 §22.1–22.7、§22A.7、§22A.19、§37 ADR-011。

<a id="kd-10"></a>
## KD-10：第一版使用模組化單體

- **決策**：第一版只有一個 Backend Application。API、Service、Persistence 與 Storage 保持清楚邊界。見 [PR-11](02-principles.md#pr-11)。
- **狀態**：已決定。
- **考慮過但沒選**：為尚未出現的規模需求先導入微服務、訊息系統或多節點編排。
- **為什麼選這個**：縮短開發與部署路徑，同時保留日後拆分模組的空間。
- **代價**：模組共用部署單位，不能單獨擴充某個模組。
- **什麼情況要重新討論**：特定模組有可量測的獨立擴充、部署或隔離需求時，評估拆分；只因「未來可能變大」不足以拆分。
- **依據**：架構基準 §2.1、§7、§22A.19、§37 ADR-001。

<a id="kd-11"></a>
## KD-11：現場畫面只呈現完成任務所需資訊

- **決策**：Field UI 聚焦「今日任務 → 證據 → 完成」。範本版本、資料庫 ID、storage key 與後台設定不放在現場操作畫面。見 [PR-10](02-principles.md#pr-10)。
- **狀態**：已決定。
- **考慮過但沒選**：把管理及設定功能直接放進現場畫面。
- **為什麼選這個**：降低現場工程師的操作負擔與拍錯需求的機率。
- **代價**：進階設定與例外處理要由 Admin UI 或後端流程承接。
- **什麼情況要重新討論**：Pilot 顯示現場工程師因缺少必要資訊而無法完成任務時，調整呈現內容，但不暴露底層儲存與資料庫細節。
- **依據**：架構基準 §6.1–6.2、§31、§37 ADR-008。

<a id="kd-12"></a>
## KD-12：Admin／Field 共用單一前端程式庫

- **決策**：Admin UI 與 Field UI **必須**放在同一個 React application，以 `/admin/*`、`/field/*` 路由與權限區分；**必須**依路由拆分程式碼，Field 的程式包不得載入 Admin 的模組。
- **狀態**：已決定（團隊於 [#5](https://github.com/speko-tw/inspect-flow/issues/5) 裁定 [OQ-21](05-open-questions.md#oq-21)，採來源 §5.1 的建議）。
- **考慮過但沒選**：同一 repo 內分成兩個 app 加共用套件。
- **為什麼選這個**：一套 build、一條 CI、一次部署；API client、登入與元件共用；符合模組化單體方向（[KD-10](#kd-10)）。
- **代價**：沒有依路由拆分時，Field 會載入 Admin 的程式；日後要拆開需要搬遷。
- **什麼情況要重新討論**：Field PWA 需要獨立發布週期，或兩者差異大到共用成本高於分開維護時，評估拆分。
- **依據**：架構基準 §5.1；團隊裁定 [OQ-21](05-open-questions.md#oq-21)。

## 技術棧卡片

卡片的「不要用」指出與本階段目標不合的做法。標為「建議」或「待定」時，卡片不替團隊拍板。

<a id="stack-backend-language"></a>
### Backend 語言

- **選用**：Python 3.12 作為基準版本。
- **負責什麼**：Backend API、業務規則、報告與影像處理。
- **狀態**：建議。
- **為什麼**：生態與團隊維護成本適合現階段；依賴的精確版本由 lockfile 固定。
- **不要用**：未經驗證就追最新 Python major。
- **未來升級路線**：新版 Python 經依賴、測試及 image 驗證後再升級。
- **依據**：架構基準 §4.1。

<a id="stack-web-api"></a>
### Web API

- **選用**：FastAPI；API 採 REST／JSON，照片上傳採 `multipart/form-data`。
- **負責什麼**：外部 API、驗證入口、上傳、授權入口與 OpenAPI 文件。
- **狀態**：建議（FastAPI）；API 邊界已決定，見 [KD-01](#kd-01)。
- **為什麼**：型別整合與文件產生方便內部系統開發。
- **不要用**：把大量業務邏輯寫在 route，或讓前端直接連資料庫。
- **未來升級路線**：維持 `/api/v1` 契約；框架版本由測試後的 lockfile 固定。
- **依據**：架構基準 §4.2、§7.1、§14。

<a id="stack-api-schema"></a>
### API Schema

- **選用**：Pydantic v2 系列。
- **負責什麼**：Request／Response 型別與輸入驗證。
- **狀態**：建議。
- **為什麼**：在資料進入 Service 前建立清楚的 API 契約。
- **不要用**：只在前端驗證，或把未驗證的 JSON 直接交給業務規則。
- **未來升級路線**：隨 API 契約演進調整 schema；精確依賴版本由 lockfile 固定。
- **依據**：架構基準 §4.3、§16.1。

<a id="stack-orm"></a>
### ORM 與資料存取

- **選用**：SQLAlchemy 2.x，見 [KD-06](#kd-06)。
- **負責什麼**：讓 Service 存取 SQLite／PostgreSQL。
- **狀態**：已決定。
- **為什麼**：降低資料庫切換時的程式改動。
- **不要用**：到處散落 SQLite 專用 raw SQL；需要 raw SQL 時要標明資料庫相依性。
- **未來升級路線**：先以 PostgreSQL 整合測試確認相容性，再搬移資料。
- **依據**：架構基準 §4.4、§7.3、§32、§37 ADR-005。

<a id="stack-migration"></a>
### Database Migration

- **選用**：Alembic，見 [KD-06](#kd-06)。
- **負責什麼**：建立、升級與追蹤正式 schema。
- **狀態**：已決定。
- **為什麼**：每次 schema 變更都要可審查、可重現。
- **不要用**：正式環境靠 `create_all()` 或未記錄的手動 ALTER。
- **未來升級路線**：SQLite 與 PostgreSQL 都要跑 migration 驗證。
- **依據**：架構基準 §4.5、§22A.9、§27.3。

<a id="stack-frontend"></a>
### Frontend

- **選用**：React、TypeScript、Vite；Admin／Field 共用單一程式庫，見 [KD-12](#kd-12)。
- **負責什麼**：現場與後台操作畫面、API Client、前端建置。
- **狀態**：建議（工具）；已決定（單一程式庫，見 [KD-12](#kd-12)）。
- **為什麼**：支援手機介面與 Dashboard，TypeScript 可減少欄位錯誤。
- **不要用**：把資料庫或 storage key 當作前端存取契約。
- **未來升級路線**：如差異擴大，評估拆分；實際套件版由 lockfile 固定。
- **依據**：架構基準 §5.1–5.2、§37 ADR-008。

<a id="stack-pwa"></a>
### PWA

- **選用**：現場 Web 朝 PWA 相容設計；MVP 先採 Online-first。
- **負責什麼**：手機與平板使用路徑，保留日後安裝與離線草稿能力。
- **狀態**：建議；完整離線同步是延後能力。
- **為什麼**：工程師可用 iPhone、iPad 或 Android 開啟 Web App。
- **不要用**：把 PWA 相容等同已完成離線同步。
- **未來升級路線**：依 Pilot 網路資料，再加入 cache、draft、待上傳佇列與同步。
- **依據**：架構基準 §5.3、§13A.14、§34–35。

<a id="stack-database"></a>
### 資料庫

- **選用**：MVP 用 SQLite；`foreign_keys = ON`、WAL **應**在連線初始化時確認。見 [KD-08](#kd-08)。
- **負責什麼**：人員、專案、範本、任務、證據 metadata 與報告資料。
- **狀態**：已決定（SQLite）；建議（兩項 PRAGMA）。
- **為什麼**：Pilot 規模可先降低維運負擔。
- **不要用**：多台後端經 NAS 共用同一個 SQLite 檔。
- **未來升級路線**：併發、鎖定或維運需求增加時轉 PostgreSQL。
- **依據**：架構基準 §9–10、§32、§37 ADR-003。

<a id="stack-photo-storage"></a>
### 照片儲存

- **選用**：本機持久化儲存與 Storage 介面；檔案和 DB metadata 分離。見 [KD-02](#kd-02)。
- **負責什麼**：原圖、編輯版及後續縮圖的檔案存取。
- **狀態**：已決定（分離與介面）；建議（第一版本機儲存）。
- **為什麼**：避免照片 BLOB 撐大 SQLite，也保留遷移彈性。
- **不要用**：原檔名當唯一 key；業務邏輯直接寫死檔案路徑。
- **未來升級路線**：以 MinIO、S3 或 NAS 實作相同 Storage 介面；原圖模型見 [G-02](05-open-questions.md#g-02)。
- **依據**：架構基準 §2.3、§7.4、§13.1–13.2、§33。

<a id="stack-image-processing"></a>
### 現場影像處理

- **選用**：前端即時預覽；後端可用 Pillow 依編輯參數產生 Variant。見 [KD-04](#kd-04)、[OQ-14](05-open-questions.md#oq-14)。
- **負責什麼**：裁切、旋轉、亮度等非破壞式編輯。
- **狀態**：待定（Frontend Render 或 Backend Render）；原圖不可覆蓋已決定。
- **為什麼**：前端預覽反應快；後端處理有利結果一致與重現。
- **不要用**：直接覆蓋原圖，或提供會增刪現場內容的標準修圖功能。
- **未來升級路線**：離線時先存原圖與編輯參數，連線後再上傳及產生 Variant。
- **依據**：架構基準 §13A.2、§13A.5–13A.8、§13A.14。

<a id="stack-docx"></a>
### DOCX 產製

- **選用**：版本化 DOCX 範本；Python 端**應**先評估 `python-docx`，複雜樣板可評估 `docxtpl`。見 [KD-05](#kd-05)。
- **負責什麼**：用 Report View Model 產生可編輯的正式 Word 文件。
- **狀態**：已決定（DOCX 輸出與範本版本）；建議（函式庫）。
- **為什麼**：業主與標案常沿用 Word 表單；版次要能對應範本。
- **不要用**：從瀏覽器 UI state 拼正式報告，或把 DOCX 當暫存下載。
- **未來升級路線**：增加不同業主樣板與 View Model Builder，不改歷史文件。
- **依據**：架構基準 §20.2–20.5、§20.19、§37 ADR-009。

<a id="stack-pdf"></a>
### PDF 轉換

- **選用**：以 DOCX 為來源產出 PDF；轉換器待 Pilot 驗證，見 [KD-05](#kd-05)、[OQ-15](05-open-questions.md#oq-15)。
- **負責什麼**：產生提交與歸檔用 PDF。
- **狀態**：已決定（PDF 輸出）；待定（LibreOffice Headless 或受控轉換服務）。
- **為什麼**：兩種格式要共享報告資料與正式版面。
- **不要用**：只以 HTML 列印 PDF 當正式報告；未實測就指定 Production 轉換器。
- **未來升級路線**：依字型、表格、圖片、頁碼、分頁及簽名欄實測結果選轉換服務。
- **依據**：架構基準 §20.3–20.4、§20.20–20.22。

<a id="stack-auth"></a>
### 認證與授權

- **選用**：內部帳號搭配 HttpOnly Secure Cookie；Session 或短效 token 待定，見 [OQ-13](05-open-questions.md#oq-13)。
- **負責什麼**：登入、目前使用者與 API 權限檢查。
- **狀態**：建議（內部帳號與安全 Cookie）；待定（Session／token 與權限表）。
- **為什麼**：先滿足內部系統需求，不必在 MVP 建完整 OAuth 基礎設施。
- **不要用**：把長效 JWT 直接放在 browser localStorage。
- **未來升級路線**：需求出現後再評估 Corporate SSO；角色矩陣見 [OQ-08](05-open-questions.md#oq-08)。
- **依據**：架構基準 §17、§35、§36。

<a id="stack-deployment"></a>
### 部署

- **選用**：Linux Server、Docker Engine、Docker Compose 與版本化 image，見 [KD-09](#kd-09)。
- **負責什麼**：啟動 Web、API、Reverse Proxy；掛載持久化資料。
- **狀態**：已決定。
- **為什麼**：單機 Pilot 可重現部署與更新，不先引入多節點編排。
- **不要用**：正式環境臨時改 container 程式或把資料放在暫存層。
- **未來升級路線**：第二階段可在 Compose 接 PostgreSQL；多節點需求再評估編排。
- **依據**：架構基準 §22.1、§22.5–22.8、§22A.12、§37 ADR-011。

<a id="stack-reverse-proxy"></a>
### Reverse Proxy 與 HTTPS

- **選用**：正式環境提供 HTTPS；Caddy、Nginx 或企業現有 Proxy 可選。見 [KD-09](#kd-09)。
- **負責什麼**：將 `/api/*` 導向後端，其餘請求導向前端。
- **狀態**：已決定（HTTPS）；建議（Caddy）；待定（正式 Proxy 選型）。
- **為什麼**：使用者不需要直接連 API 容器埠。
- **不要用**：把 API 或未受控資料庫埠直接暴露給一般使用者。
- **未來升級路線**：可改接企業 Proxy 或 Load Balancer，保留外部 HTTPS 入口。
- **依據**：架構基準 §22.5、§22.10–22.11。

<a id="stack-tests"></a>
### 測試工具

- **選用**：Backend 以 pytest；Frontend component 可用 Vitest；關鍵流程可用 Playwright。
- **負責什麼**：驗證 task generation、快照、Evidence、權限、完整使用者流程與 PostgreSQL 相容性。
- **狀態**：建議（工具）；關鍵流程與跨資料庫驗證為來源要求。
- **為什麼**：任務與正式報告的資料正確性要能重複驗證。
- **不要用**：只測 UI 顯示而略過後端完成驗證或報告內容。
- **未來升級路線**：隨正式報告樣板增加 DOCX/PDF 資料與版面測試。
- **依據**：架構基準 §13A.15、§20.20、§27.1–27.4。

<a id="stack-ci"></a>
### CI

- **選用**：GitHub Actions；每次 PR 執行 lint、後端測試、前端測試、build 與 PostgreSQL 相容性測試。見 [KD-09](#kd-09)。
- **負責什麼**：在版本化 image 進入正式發布前擋下失敗變更。
- **狀態**：已決定（CI 閘門）；已決定（CI 平台採 GitHub Actions，團隊於 [#5](https://github.com/speko-tw/inspect-flow/issues/5) 選定，非架構基準來源）。理由：repo 在 GitHub，檢查結果可直接接上分支保護與 PR 審查。
- **為什麼**：正式環境只部署已審查、已建置、已驗證的產物。
- **不要用**：CI 失敗仍發布，或在 Production 現場編譯臨時版本。
- **未來升級路線**：部署自動化可稍後加入；先維持可重現的手動發布流程。
- **依據**：架構基準 §22A.4–22A.7、§28、§37 ADR-011。

<a id="stack-code-quality"></a>
### 程式品質工具

- **選用**：Python 用 ruff（format 與 lint）；Frontend 用 Prettier（格式）、ESLint（lint）、TypeScript（型別）；Python 型別檢查用 pyright。
- **負責什麼**：基本 lint、格式與型別檢查。formatter 管排版、linter 管寫法、型別檢查器管型別，三者不重疊。
- **狀態**：
  - 已決定：ruff、ESLint、TypeScript、Prettier（團隊於 [#5](https://github.com/speko-tw/inspect-flow/issues/5) 選定，非架構基準來源）；起始設定見 `skeleton` 規格。
  - 已決定：pyright，先 `basic`、再逐個模組改 `strict`（團隊於 [#5](https://github.com/speko-tw/inspect-flow/issues/5) 裁定 [OQ-16](05-open-questions.md#oq-16)）。
  - 已決定：程式碼行寬上限 79 字元，依 PEP 8，全專案程式碼一律適用（專案負責人指定，非架構基準來源；Markdown 文件不受此限）；formatter 與 linter 設定**必須**與之一致。
  - Python 風格以 PEP 8 為基準。起始規則集與新增規則的方式由 `skeleton` 規格與設定檔維護。
- **為什麼**：維持基本一致性，同時避免 MVP 一開始導入過多規則。pyright 與 VS Code 的 Pylance 同一引擎，編輯器與 CI 的結果一致。
- **不要用**：未經團隊評估就把多套重疊的 lint 或架構框架加入發布閘門。
- **未來升級路線**：依程式量與缺陷資料調整檢查；pyright 逐個模組改為 `strict`。
- **依據**：架構基準 §29。
