# 關鍵決策（Key Decisions）

ADR-lite 格式的決策記錄。每筆只收錄架構基準文件明確拍板的決策（已列入 §37 的 ADR，或以不含糊語氣重
申的規則），不包含仍在權衡中的「建議」——那些留在 [06-open-questions.md](06-open-questions.md)，並標
註來源傾向作為目前的預設假設。排序依對實作者的重要性，非來源文件原本的 ADR 編號順序；每筆仍附上原
ADR 編號以利對照。

## KD-01 — 前端僅能透過後端 API 存取資料

- **決策**：所有外部用戶端（Field Web、Admin Web，含由 UI 觸發報告產製的操作）一律透過 Backend API
  取得與寫入資料；禁止前端直接讀寫資料庫或檔案儲存。後端內部服務（例如 Report Service）直接透過
  Service／Persistence／Storage 介面存取自己的資料，不需要對自身發出 HTTP API 呼叫。
- **考慮過的替代方案**：前端直接連線資料庫（架構基準文件明確以圖示列為禁止做法並否決）。
- **理由**：集中權限控管、集中資料驗證、集中商業邏輯；資料庫由 SQLite 換成 PostgreSQL 時前端不必重
  寫；未來 App、PWA、第三方介面可共用同一套 API。
- **接受的取捨**：所有外部用戶端存取都必須繞經一層 API，前期開發速度會比「前端直連資料庫」慢一點。
- **重新檢討條件**：架構基準文件未給出重新檢討條件——本決策視為長期原則，不因規模成長而鬆動。
- **依據**：架構基準 §2.2、§20.2、§37 ADR-002。

## KD-02 — 照片與檔案不進關聯式資料庫

- **決策**：資料庫只保存證據的 metadata；實際檔案內容存放於檔案／物件儲存，透過 Storage 抽象層存
  取，儲存鍵由後端以 UUID 產生。
- **考慮過的替代方案**：把照片以 BLOB 形式直接存進 SQLite；以使用者原始檔名作為儲存鍵（兩者皆被明確
  否決）。
- **理由**：避免資料庫因大量照片而膨脹，簡化備份與 migration；為未來從本機儲存遷移到 MinIO／S3／NAS
  做準備。
- **接受的取捨**：需要額外維護一層 Storage 抽象與檔案／資料庫兩邊的一致性，而不是單一資料庫交易就能
  搞定。
- **重新檢討條件**：當儲存需求從本機檔案系統成長到需要物件儲存（MinIO／S3／NAS）時，切換儲存實作，
  但 Storage 介面契約與資料庫端 metadata 結構不需要改變。
- **依據**：架構基準 §2.3、§13.1–13.2、§33、§37 ADR-004。

## KD-03 — 範本版本化，任務建立時凍結需求快照

- **決策**：`Inspection Template` 版本化（v1、v2……）；`Inspection Task` 建立時，把當時生效的
  `Requirement` 複製為 `Task Requirement Snapshot`，任務日後不再受範本變動影響。
- **考慮過的替代方案**：任務直接參照「目前版本」的範本需求（會導致範本一改，過去任務的要求被默默重
  新解讀，因而被否決）。
- **理由**：工程稽查資料的歷史追溯性要求，任務當初實際被要求證明什麼，必須永遠可查。
- **接受的取捨**：需要多維護一張快照表，且範本與快照之間需要保留 `source_requirement_id` 這類回溯關
  聯，資料模型比「永遠讀最新範本」複雜。
- **重新檢討條件**：架構基準文件未給出重新檢討條件——本決策是歷史追溯要求的直接結果，不因規模成長而
  鬆動。
- **依據**：架構基準 §2.5、§12.9、§37 ADR-006。

## KD-04 — 證據影像採非破壞式編輯

- **決策**：現場工程師得對照片做縮放檢視、裁切、旋轉、亮度（對比為可選）等調整，但原圖永不覆蓋；每
  次編輯產生新的 Evidence Variant，保留編輯參數、建立者、時間與 SHA-256。
- **考慮過的替代方案**：直接覆蓋原始照片；提供物件移除／新增、Generative Fill、AI Retouch、內容替換
  等會改變照片實質內容的編輯功能（兩者皆被明確否決為標準功能）。
- **理由**：查核照片具有證據性質，業主／監造可能需要確認原始影像；裁切／調亮可能改變視覺判讀；為未
  來稽核或電子簽章保留原始檔完整性。
- **接受的取捨**：需要多一套 Variant 資料模型與儲存空間（同一張證據可能對應多個檔案版本）。
- **重新檢討條件**：架構基準文件未給出重新檢討條件——原圖不可覆蓋是評證完整性的長期要求。
- **依據**：架構基準 §13A.2、§13A.6、§37 ADR-010。

## KD-05 — DOCX 與 PDF 為正式核心交付物

- **決策**：InspectFlow 的 Report 模組屬於核心產品能力；MVP 的正式完成條件必須包含 DOCX（Word）與
  PDF 輸出，而不只是 Dashboard 可視化；正式輸出流程為「Inspection Data → Report View Model → DOCX
  Template → DOCX → PDF」。
- **考慮過的替代方案**：僅做「HTML → 直接列印成 PDF」作為唯一正式輸出；把報告當成用完即丟的暫存下載
  檔（兩者皆被明確否決）；原先「先做 HTML，再考慮 PDF」的排序策略，被本決策修正。
- **理由**：工程查核結果最終要對應業主、監造、政府標案、品質文件與歸檔需求；HTML 適合開發期快速預
  覽，但不能取代正式 Word／PDF 文件流程。
- **接受的取捨**：報告產製需要維護 DOCX 範本、DOCX 產生器與 DOCX→PDF 轉換服務，比純 HTML 預覽的實作
  成本高，且需要在 Pilot 階段做字型／表格／中文／圖片／分頁的實測驗證。
- **重新檢討條件**：架構基準文件未給出重新檢討條件——DOCX/PDF 為核心交付物視為長期定位，不因規模成
  長而鬆動；實際採用哪一種 DOCX→PDF 轉換工具則仍待 Pilot 驗證後決定（見
  [06-open-questions.md](06-open-questions.md)）。
- **依據**：架構基準 §20.1–20.3、§20.22、§37 ADR-009。

## KD-06 — SQLAlchemy + Alembic 為唯一的結構演進路徑

- **決策**：資料庫存取一律透過 SQLAlchemy，Schema 演進一律透過 Alembic migration；正式環境禁止依賴
  `Base.metadata.create_all()` 管理 Schema。
- **考慮過的替代方案**：以 `Base.metadata.create_all()` 或手動 `ALTER` 管理正式環境 Schema；大量使用
  SQLite-specific raw SQL（皆被明確否決）。
- **理由**：這是 SQLite 未來能平滑轉換到 PostgreSQL 的關鍵層；CI 定期以 PostgreSQL 執行整合測試，避免
  日後才發現大量程式碼依賴 SQLite-only 行為。
- **接受的取捨**：所有 Schema 變更都要走 migration 流程，比直接改資料庫多一道審核與版本管理成本。
- **重新檢討條件**：架構基準文件未給出重新檢討條件——本決策本身就是支援未來資料庫遷移的基礎設施，不
  隨規模調整。
- **依據**：架構基準 §4.4–4.5、§32、§37 ADR-005。

## KD-07 — UUID（優先考慮 UUIDv7）作為主要 Entity 識別碼

- **決策**：主要 entity（Project、User、Inspection Plan、Task、Evidence 等）使用 UUID 作為識別碼，得
  優先考慮 UUIDv7；另外保留人類可讀的業務編號（如 `project_code`、`employee_no`）作為獨立欄位，兩者
  用途不同、不可混用。
- **考慮過的替代方案**：完全依賴 SQLite AUTOINCREMENT 作為跨系統 identity（明確被否決）。
- **理由**：未來離線用戶端可自行產生 ID；避免不同來源資料合併時撞號；讓資料庫 migration 更簡單；對未
  來分散式環境更友善。
- **接受的取捨**：UUID 比自增整數占用更多儲存空間，且對人類不易記憶，因此需要另外維護人類可讀的業務
  編號。
- **重新檢討條件**：架構基準文件未給出重新檢討條件——具體採用哪一版 UUID（例如是否確定用 UUIDv7）仍
  是「得」等級的偏好，非鎖定版本。
- **依據**：架構基準 §11、§37 ADR-007。

## KD-08 — SQLite 作為 MVP 資料庫

- **決策**：第一階段使用 SQLite，且僅限單一 Backend Host 存取，不透過 network filesystem 讓多台伺服
  器共同讀寫同一個 `.db` 檔。`PRAGMA foreign_keys = ON` 與 `PRAGMA journal_mode = WAL` 是連線初始化
  時**應**確認的建議設定（架構基準 §9.2 用語為「建議確認」），非本決策鎖定為 ADR 等級必須項目的一部
  分。
- **考慮過的替代方案**：一開始就採用 PostgreSQL（因為目前使用者數少、schema 仍在變動、不想先維運一
  套 DB Server 而暫不採用）；多伺服器共享同一個 SQLite 檔（明確被否決）。
- **理由**：低維運成本、schema 容易迭代，符合小規模 Pilot 需求；系統最大資料量來源其實是照片而非關聯
  式資料列。
- **接受的取捨**：不具備多伺服器高並發寫入能力、缺乏正式 DB Server 等級的備份／監控機制。
- **重新檢討條件**：當出現以下任一狀況即應轉換至 PostgreSQL：同時寫入明顯增加、多專案同時使用、多
  Backend instance、需要更完整 transaction／locking、正式環境備份／監控要求提高、Dashboard 查詢量明
  顯增加、需要更強 JSON／索引／報表能力、或資料庫需要獨立維運。
- **依據**：架構基準 §9–10、§37 ADR-003。

## KD-09 — Linux + Docker Compose 為標準部署基準

- **決策**：Pilot／Production 標準運行環境為 Linux Server，並以 Docker Engine + Docker Compose 部
  署；所有正式變更必須經 Git → Review → CI → Image Build → Versioned Release → Migration → Compose
  Deployment。
- **考慮過的替代方案**：Windows 桌機、個人筆電、臨時 VM、無持久化磁碟的容器主機作為正式主機；第一天
  就導入 Kubernetes／Nomad 等企業容器平台（皆被明確否決）。
- **理由**：確保開發、測試與正式環境具有一致、可重現的 runtime，降低安裝與維運成本；對內部系統與中小
  型負載，Compose 可以長期使用。
- **接受的取捨**：不具備 Kubernetes 等平台的自動 failover、大規模水平擴充與多節點協調能力。
- **重新檢討條件**：只有在真正出現大量 backend replica、多節點協調、高可用性、自動 failover 或大型分
  散式負載時，才需要評估 Kubernetes／Nomad 等企業容器平台；不得因為「未來可能變大」就提前導入。
- **依據**：架構基準 §22.1–22.2、§22A.19、§37 ADR-011。

## KD-10 — 模組化單體，而非 Microservices

- **決策**：第一版採單一 Backend Application（Modular Monolith），內部模組邊界清楚，但部署上是一個
  服務。
- **考慮過的替代方案**：Microservices、Kubernetes、Kafka、Redis Cluster、API Gateway、Event Bus、
  CQRS、分散式資料庫、複雜 Workflow Engine（皆因避免 MVP 階段不必要的複雜度而被否決）。
- **理由**：同時取得快速開發、容易 debug、容易部署、容易備份、容易理解，並保留未來仍可拆分的能力。
- **接受的取捨**：所有模組共用同一個部署單位與資源配額，無法針對單一模組獨立擴充或獨立部署。
- **重新檢討條件**：出現大量 backend replica、多節點協調、高可用性、自動 failover 或大型分散式負載
  等真實規模需求時，才評估拆分或導入編排平台（與 KD-09 共用同一觸發條件）。
- **依據**：架構基準 §2.1、§37 ADR-001。

## KD-11 — Field UI 精簡化，複雜度留在 Admin

- **決策**：現場工程師只處理「任務 → 證據 → 完成」，不接觸 Template Version、Database ID、
  Requirement Schema、Project Configuration、Storage Key 等後台概念；系統複雜度集中在 Backend／
  Admin UI。
- **考慮過的替代方案**：讓現場 UI 直接暴露範本版本、資料庫 ID、需求 Schema 等後台管理功能（被明確列
  為不應出現在現場畫面的項目）。
- **理由**：現場效率比後台功能豐富度更重要；把系統複雜度放在 Backend／Admin，而非 Field UI。
- **接受的取捨**：現場工程師若真的需要進階操作（例如手動調整需求），必須改由後台代為處理，現場端不
  提供對應入口。
- **重新檢討條件**：架構基準文件未給出重新檢討條件；Pilot 階段的現場可用性回饋（依據：架構基準
  §31）可能調整現場 UI 的細節設計，但「複雜度留在後台」這個定位本身未被列為可調整項目。
- **依據**：架構基準 §6.1–6.2、§37 ADR-008。
