# 設計原則（Design Principles）

每一次變更都應對照檢查的常設原則。條目依「對實作者的重要性」排序，而非依來源文件的章節順序；反覆出
現在來源文件多處的同一個論點，在此合併為一條原則並列出所有出處。每條原則給出：規則本身、理由、對貢
獻者的意涵，以及一個違反範例。決策記錄見 [04-key-decisions.md](04-key-decisions.md)；名詞定義見
[05-glossary.md](05-glossary.md)。

## PR-01 — 前端僅能透過後端 API 存取資料，且業務規則必須由後端覆核

**規則。** 所有**外部用戶端**（Field Web、Admin Web，包括由 UI 觸發報告產製的操作）都**必須**透過
Backend API 存取與寫入資料，任何前端都不得直接讀寫資料庫或檔案儲存；前端渲染的是後端回傳的規則資
料，能不能真的完成一個任務，**必須**由後端重新驗證一次，不可只靠前端判斷。**後端內部服務**（例如
Report Service）則直接透過 Service／Persistence／Storage 介面存取自己的資料，不需要、也不要求對自
身發出 HTTP API 呼叫（依據：架構基準 §2.2、§2.4、§7.1–7.2、§14、§16.4–16.6、§20.2）。

**理由。** 集中權限控管、資料驗證與商業邏輯；讓 SQLite 換成 PostgreSQL 時前端不必重寫；讓未來的
App、PWA、第三方介面可以共用同一套 API；也讓 `/api/v1` 這個 contract 在資料庫／儲存體遷移過程中維持
穩定（依據：架構基準 §2.2）。正式報告產製的資料流本身就是「Database → Report Service → Report View
Model → Template Engine → DOCX／PDF」，Report Service 屬於後端內部模組，不是外部前端
（依據：架構基準 §20.2）。

**對貢獻者的意涵。** 任何從 UI 出發的讀寫都必須經過一個有版本號的後端端點；不得在前端內嵌資料庫連
線、儲存體 SDK 或檔案系統路徑；「是否可以完成」這類判斷永遠在後端重跑一次，前端的判斷只是 UX 提示。
後端服務之間（例如 Report Service 讀取 Database／Storage）不受此限，得直接呼叫內部介面，不必繞經
`/api/v1`。

**違反範例。** 前端元件直接開啟 SQLite／PostgreSQL 連線；前端自行組出儲存路徑讀取照片檔案，而不是呼
叫後端端點；前端僅依自己的檢查結果就把任務標記完成，不經後端 `/tasks/{id}/complete` 覆核；Report
Service 為了取得自己資料庫裡的資料，繞一圈自我呼叫 HTTP API，而非直接使用內部 Service／Persistence
介面。

## PR-02 — 檔案與關聯式資料分離，儲存鍵由後端產生

**規則。** 照片等證據檔案**禁止**以 BLOB 形式塞進關聯式資料庫；資料庫只保存 metadata
（`evidence_id`、`task_id`、`requirement_id`、`storage_key`、檔名、MIME type、檔案大小、SHA-256、
`captured_at`、`uploaded_at`），實際檔案內容存放於檔案／物件儲存（依據：架構基準 §2.3）。儲存鍵
（storage key）**必須**由後端以 Evidence 的 UUID 產生，**不得**使用使用者原始檔名作為唯一識別；原始
檔名只作為附帶 metadata 保存（依據：架構基準 §13.2）。

**理由。** 避免資料庫因大量照片而膨脹；讓未來從本機儲存搬到 MinIO/S3/NAS 時不需要重新設計；避免使用
者原始檔名衝突或攜帶不可信資訊（依據：架構基準 §2.3、§13.2）。

**對貢獻者的意涵。** 所有檔案存取一律經過 `Storage` 抽象介面（`save`/`open`/`delete`），業務邏輯不得
依賴特定儲存體實作（依據：架構基準 §7.4、§33）。新增欄位存放大型二進位內容前，先確認是否該走
Storage 而非資料庫欄位。

**違反範例。** 在資料庫新增一個欄位直接存放圖片位元組；服務層直接呼叫
`open("/storage/photos/...")` 而不經過儲存抽象層；以 `IMG_1234.jpg` 這類使用者原始檔名作為 storage
key 的唯一識別。

## PR-03 — 資料庫存取與結構演進必須透過抽象層

**規則。** 資料庫存取**必須**透過 SQLAlchemy，結構演進**必須**透過 Alembic migration；正式環境**禁
止**依賴 `Base.metadata.create_all()` 管理 Schema，也**禁止**在正式資料庫上手動 `ALTER` 而不留下對應
migration；應避免大量 SQLite-specific 的 raw SQL，如需使用，必須標註其資料庫相依性
（依據：架構基準 §4.4–4.5、§7.3、§22A.9、§22A.12）。

**理由。** 這一層是 SQLite 未來能平滑轉換到 PostgreSQL 的關鍵；CI 定期以 PostgreSQL 執行 migration 與
整合測試，可以避免一年後才發現大量程式碼依賴 SQLite-only 行為（依據：架構基準 §4.4、§27.3、§32）。

**對貢獻者的意涵。** 從第一天開始必須遵守以下 8 點（依據：架構基準 §32）：SQL 一律透過
SQLAlchemy；Schema 一律透過 Alembic；不依賴 SQLite AUTOINCREMENT 作為跨系統 identity；照片不進資料
庫；避免 SQLite-specific raw SQL；CI 定期跑 PostgreSQL 整合測試；timestamp／boolean／JSON 等型別要考
慮跨資料庫行為一致性；資料庫存取不得出現在前端。

**違反範例。** 新功能直接寫一段只有 SQLite 支援語法的 raw SQL，且未標註資料庫相依性；用
`Base.metadata.create_all()` 在正式環境建立新資料表，而不是產生一份 Alembic migration。

## PR-04 — 歷史查核資料不因範本異動而改變

**規則。** `Inspection Template` **必須**版本化（v1、v2、v3……）；當 `Inspection Task` 被建立時，其實
際執行需求**必須**被複製成 `Task Requirement Snapshot`，固定下來。即使日後範本改到 v4，過去已建立的
Task 仍保存建立當下的要求，不因範本異動而被重新解讀（依據：架構基準 §2.5、§12.9）。

**理由。** 工程稽查系統的歷史追溯性非常重要：必須永遠能回答「這個任務當初實際要求證明什麼」，且答案
不受後續範本編輯影響（依據：架構基準 §2.5）。

**對貢獻者的意涵。** 任何完成度檢查或報告查詢，**必須**讀取任務自己的 `task_requirements` 快照，**不
得**直接 join 到目前版本的 `template_items` / `evidence_requirements`。

**違反範例。** 完成度檢查或報表產製時，直接查詢「目前」的範本需求表，而不是任務自己的需求快照。

## PR-05 — 證據影像採非破壞式編輯，原圖不得就地覆寫

**規則。** 現場工程師得對照片做有限度的調整（縮放檢視、裁切、旋轉、亮度，對比為可選項），但**不得**
覆蓋原始照片；每次編輯**必須**產生新的 `Evidence Variant`（`EDITED`），並保留原圖、其 SHA-256，以及
產生該 Variant 所用的編輯參數（依據：架構基準 §13A.2、§13A.4）。物件移除／新增、Generative Fill、AI
Retouch、內容替換等會改變證據實質內容的操作，**禁止**作為標準功能提供（依據：架構基準 §13A.6）。

**理由。** 查核照片具有證據性質：業主或監造可能要求確認原始影像；裁切可能移除周邊現場資訊；亮度調整
可能改變視覺判讀；若未來導入稽核或電子簽章，原始檔案的完整性至關重要
（依據：架構基準 §13A.3、§37 ADR-010）。

**對貢獻者的意涵。** 任何「照片美化」類功能都必須是新增（產生新 Variant），且僅限提升可讀性／版面表
現的操作；**不得**就地改寫 `ORIGINAL` Variant 的原始位元組。刪除、保留期限與軟刪除政策目前**不**在
本原則規範範圍內，待 [06-open-questions.md](06-open-questions.md) G-05 定案後再補上具體規則，本原則
不預先禁止刪除。

**違反範例。** 編輯流程把調整後的像素直接寫回原始檔案；新增一個以 AI 生成內容改變照片實質內容的「編
輯」功能，作為標準功能項目。

## PR-06 — 正式報告是版本化、不可覆蓋的快照實體

**規則。** 一份產生的 Report **必須**是一個持久化實體（`reports`），擁有自己的 id、文件編號、版次、
狀態、DOCX／PDF 儲存鍵，以及產生當下所用資料的**快照（Data Snapshot）**——不是用完即丟的暫存檔
（依據：架構基準 §20.6、§20.7）。若之後現場資料被修改或補件，**不得**讓已核發的版次（例如 `REV.0`）
悄悄改變；應改為產生新版次（`REV.1`），而不是覆蓋舊版次（依據：架構基準 §20.7）。

**理由。** 對業主／政府標案交付物而言，已核發的版次必須維持核發當下的樣貌，即使之後現場資料被更正或
補充（依據：架構基準 §20.7）。Dashboard 只是監控介面，DOCX／PDF 才是真正的正式、可歸檔交付物，因此
報告產製屬於核心產品能力，不是可有可無的附屬功能（依據：架構基準 §20.1、§20.22、§37 ADR-009）。

**對貢獻者的意涵。** 報告產製**必須**讀取（或產生）一份不可變的資料快照來渲染，**不得**就地重新渲染
並覆蓋一個已經 `ISSUED` 的版次的 DOCX／PDF 檔案。

**違反範例。** 「重新整理報告」功能就地重新渲染並覆蓋一個已核發版次的 DOCX／PDF，而不是產生新版次。

## PR-07 — 端到端可追溯性

**規則。** **報告中使用的照片及其影像衍生物**（Report Photo → Variant → Original Evidence）**必須**
可以沿著鏈路回溯至來源證據（依據：架構基準 §20.11、§13A.9）。**一般 Evidence**（不限於照片，含
TEXT 等其他類型）**必須**可以沿著 Evidence → Task Requirement Snapshot → Task → Inspection Plan →
Project 回溯（依據：架構基準 §12.9–12.10、§20.11）。在 [06-open-questions.md](06-open-questions.md)
G-02（Original 的唯一來源）定案前，本原則**不**要求 `ORIGINAL` 必須額外對應一筆
`Evidence Variant` 資料列；原圖究竟是 `Evidence.storage_key` 本身、還是一筆
`variant_type = ORIGINAL` 的 Variant 記錄，留待 G-02 裁決。

**理由。** 對業主／監造／政府稽核而言，必須隨時能回答「報告裡這張照片到底來自哪一筆原始查核紀錄」；
同時任一筆一般 Evidence 也必須能回答自己隸屬於哪個任務、計畫與專案（依據：架構基準 §20.11）。

**對貢獻者的意涵。** 報告照片與其衍生圖，不得設計出一條會遺失回溯連結的資料路徑；即使是縮圖或為報
告最佳化過的圖片，也必須保留回到來源證據的參照。一般 Evidence 的可追溯性以其對 Task Requirement
Snapshot／Task／Plan／Project 的外鍵關聯為準，**不**強制要求每一筆 Evidence 都走 Variant 鏈——
TEXT 等非影像類型的 Evidence 沒有 Variant 鏈可走（依據：架構基準 §12.10）。

**違反範例。** 產生一個報告用圖片素材，卻沒有任何欄位記錄它是從哪一筆 `Evidence` / `Task` /
`Inspection Plan` / `Project` 衍生出來的；一筆一般 Evidence（例如 TEXT）無法追溯回其所屬 Task 與
Plan。

## PR-08 — 最低限度的稽核紀錄，且伺服器端一律覆核

**規則。** 重要資料**必須**保留建立與最後修改當下的時間與操作者身分，但不要求完整事件溯源
（依據：架構基準 §19）。**應**採用 `created_at` / `created_by` / `updated_at` / `updated_by` 這組建
議欄位形式，從早期即開始保留（依據：架構基準 §19）。這組欄位**只能**呈現「最後一次狀態」，**不是**
完整的操作歷史，無法回答「誰在何時做了哪一次修改、修改前後的值分別是什麼」——完整 `audit_logs` 事
件記錄留待 [06-open-questions.md](06-open-questions.md) 定案。證據編輯操作**必須**保留原始／編輯
後、編輯參數、`created_by`、`created_at` 與雜湊值，即使正式報告預設不顯示這些資訊，系統內部也必須能
夠完整提出（依據：架構基準 §13A.10）。API 錯誤**必須**用結構化的 `error.code` 表達，前端**必須**依
`error.code` 判斷邏輯，**不得**依錯誤訊息文字判斷（依據：架構基準 §25）。

**理由。** MVP 不必建立完整的 audit event sourcing，但至少要能回答「這筆重要資料是誰、何時建立／最
後修改」；這與「誰在何時對哪筆資料做了什麼」這種完整事件歷史是兩件事，後者需要額外的 `audit_logs`
機制才能回答（依據：架構基準 §19）。錯誤訊息文字可能改版，用 code 判斷才能維持前後端契約穩定
（依據：架構基準 §25）。

**對貢獻者的意涵。** 新增任何可變、面向使用者的紀錄（Evidence Variant、Report、Plan、Task）時，不得
省略建立時間與建立者（可變更的記錄還需要最後修改的時間與操作者）；不要把這組欄位當成能回答「歷史上
每一次變動」的完整 audit trail。新增錯誤情境時，先定義 `error.code`，不要只寫錯誤訊息文字。

**違反範例。** 新增一張 Evidence Variant 或一筆 Report 紀錄卻沒有建立時間與建立者；宣稱只靠
`updated_at` / `updated_by` 就能重建一筆資料完整的歷次修改歷史；前端用字串比對錯誤訊息內容來決定分
支邏輯。

## PR-09 — 查核規則以資料表示，而非寫死邏輯

**規則。** 查核規則（要拍哪些照片、要填哪些欄位等）**必須**以 `Template` / `Requirement` 資料表示，
**不得**在前端或後端寫成針對特定項目的 `if/else` 判斷式（依據：架構基準 §2.4）。查核間距
（interval）等欄位目前歸屬 `Template` 還是 `Inspection Plan` 輸入層尚未定案，本原則**不**代為裁決其
資料表歸屬，見 [06-open-questions.md](06-open-questions.md) G-01。

**理由。** 當規則改變（例如電纜橋架查核從「長寬高三張照片」改成「總覽照、高度照、接頭照 × 2」）時，
前端只需依後端回傳的需求資料重新渲染畫面，不需要改版或重新部署（依據：架構基準 §2.4）。

**對貢獻者的意涵。** 新的查核規則應以 `EvidenceRequirement` / `TemplateItem` 紀錄的形式撰寫，而不是
新增程式分支；前端應是任何需求資料的通用渲染器。interval 欄位歸屬定案前，不要預先把它固定寫死在某
一張表的 schema 假設裡。

**違反範例。** 在前端或後端加入類似 `if item == "cable_tray": require_length_photo()` 的程式碼分
支，而不是在範本版本裡新增一筆需求紀錄。

## PR-10 — 現場 UI 力求精簡，且必須適配手機與平板

**規則。** Field UI **不得**讓現場工程師看到 Template Version、Database ID、Requirement Schema、
Project Configuration、Storage Key、metadata 或資料庫管理功能；現場工程師的心智模型只有「今天要做什
麼 → 現在拍什麼 → 還缺什麼 → 是否完成」（依據：架構基準 §6.1）。系統複雜度應留在 Admin UI／後端
（依據：架構基準 §6.2）。現場流程**必須**能在手機、平板上流暢操作
（依據：架構基準 §5.3、§13A.13、§31）。

**理由。** 現場操作速度與低認知負擔的優先度高於功能豐富度；後台才是允許系統複雜度存在的地方
（依據：架構基準 §6.1–6.2）。

**對貢獻者的意涵。** 在 Field UI 新增任何控制項、畫面或術語之前，先確認它是否該放在 Admin UI；Field
UI 的新增項目應由現場工作流程需求驅動，而不是後端實作方便。

**違反範例。** 在現場工程師的任務畫面上出現範本版本選單、原始需求 Schema 編輯器，或資料庫 UUID／
Storage Key。

## PR-11 — MVP 採模組化單體，避免過早導入分散式架構

**規則。** 第一版**不得**在缺乏具體需求的情況下導入 Microservices、Kubernetes、Kafka、Redis
Cluster、API Gateway、Event Bus、CQRS、分散式資料庫或複雜 Workflow Engine；第一版**必須**採用
**Modular Monolith**：內部模組邊界清楚，但部署時仍是單一 Backend Application（依據：架構基準
§2.1）。

**理由。** 同時取得快速開發、容易 debug、容易部署、容易備份、容易理解，並保留未來仍可拆分的可能性
（依據：架構基準 §2.1）。只有在真正出現大量 backend replica、多節點協調、高可用性、自動 failover 或
大型分散式負載時，才需要評估 Kubernetes／Nomad 等企業容器平台，**不得**因為「未來可能變大」就在第一
天導入（依據：架構基準 §22A.19）。

**對貢獻者的意涵。** 在後端內部維持乾淨的模組邊界（API 層 / Service 層 / Persistence / Storage，依
§7），為未來拆分留餘地；但不要為了解決一個第一階段的問題，就新增第二個獨立部署的服務、訊息佇列或編
排層。

**違反範例。** 在兩個後端模組之間加入訊息佇列來解決一個模組化邊界就能解決的問題；把後端拆成兩個獨立
部署的服務，只為了解決一個第一階段規模就能處理的問題。

## PR-12 — 備份與還原必須涵蓋資料庫、照片與報表儲存體（本文件之整合決策，待團隊確認）

**規則。** 至少必須持久化：Database、Photos、Reports 三者（依據：架構基準 §22.12）；照片與資料庫
**必須**視為同一套業務資料，備份時必須能互相對應（依據：架構基準 §23）；每次正式 release 前**應**具
備 Storage Backup Strategy（依據：架構基準 §22A.10）。**本文件為確保可還原性所作之整合決策**：備份
範圍涵蓋資料庫、範本檔案、原圖與衍生照片、已核發之 DOCX／PDF，並定義其一致性邊界——同一次備份／還
原操作必須讓這一組資料回到彼此對應的同一個時間點，而非各自獨立還原；此整合決策待團隊確認。

**理由。** 只備份 SQLite 檔案而遺漏照片，或只備份照片而遺漏資料庫，會留下互相對不上的殘缺資料集
（依據：架構基準 §23）；§22.12 要求的是持久化本身，不直接等同備份策略，但若不持久化就無從備份，因
此持久化清單構成備份範圍的下限（依據：架構基準 §22.12）。

**對貢獻者的意涵。** 新增任何需要長期保存的產出（例如報告檔案、範本檔案）時，必須確認它已被納入備份
範圍與還原程序，而不是預設「資料庫有備份就夠了」；還原驗證時應確認資料庫、照片與已核發文件回到同一
個一致的時間點。

**違反範例。** 備份程序只匯出資料庫，卻沒有同步備份 `storage/photos` 與 `storage/reports`；還原後資
料庫指向的照片或報告檔案卻是不同備份時間點的版本。

> 補充：架構基準文件 §23 針對「資料庫＋照片必須一致備份」講得最明確，§22.12 要求的是持久化
> （Database、Photos、Reports），§22A.10 另要求 Storage Backup Strategy；三處沒有任何一處把「資料
> 庫＋照片＋報表必須一致備份」逐字寫在同一句話裡。這是來源**缺漏**，不是互相矛盾的規則，本原則據此
> 補上一個整合範圍，詳見 [06-open-questions.md](06-open-questions.md) 的「來源缺漏：備份範圍」
> （G-10）。

## PR-13 — 正式環境的變更必須透過版本控管與可重現流程

**規則。** 正式環境**禁止**直接 `vim` 修改原始碼、直接 `pip install` / `npm install`、直接手動改資料
庫 Schema；所有變更**必須**依序經過 Git → Review → Build → Versioned Image → Deploy
（依據：架構基準 §22A.12）。**初次部署**（尚無既有資料與流量）與**升級部署**（已有既有版本在服務）
**必須**視為兩個不同流程：初次部署得依固定、可重現流程啟動所有服務，migration 與服務啟動的先後順序
不影響既有資料（依據：架構基準 §22.16）；升級部署**必須**在啟動新版服務前完成備份與 migration，並
在啟動後執行健康檢查與 smoke test（依據：架構基準 §22.15、§22A.7、§22A.9）。升級時，**必須**先確保
舊版服務不再對資料庫寫入才執行 migration，或採用一套已驗證的向前相容（backward compatible）遷移策
略；任一條件不成立時，**必須**依備份／回滾計畫處理失敗（依據：架構基準 §22A.9、§22A.10）。一個版本
要視為可交付，**必須**滿足完整的 Deployment Definition of Done（依據：架構基準 §22A.20）。

**理由。** 這樣正式環境才可重現；初次部署沒有既有資料與流量風險，順序寬鬆是合理的，但升級部署若沿
用同一套「先啟動再 migration」的順序，舊版程式可能在新 schema 尚未就緒時寫入，或新版程式碼在
migration 完成前就先接受請求；重要 migration 上線前一定要先備份，否則 schema 變更不可逆時將無法回
滾（依據：架構基準 §22A.10、§22A.12）。

**對貢獻者的意涵。** `DEPLOYMENT.md` 應分別寫清楚「初次部署」與「升級部署」兩套流程，不能只抄一份範
例套用到兩種情境；升級流程必須把「舊版寫入隔離或向前相容遷移」「先備份再 migrate」「migration 先於
新版服務啟動」當成硬性順序，並附上失敗時的備份／回滾步驟。

**違反範例。** 把初次部署範例（先啟動、後 migration）直接套用到有既有資料的升級情境；升級部署腳本先
啟動新版服務，之後才補跑 Alembic migration，且沒有先隔離舊版寫入或準備回滾計畫。

> 補充：架構基準文件本身在 §22.15（Startup / Migration 流程）與 §22.16（一鍵部署的真正定義）給出的
> migration／服務啟動順序不同；本文件的判讀是兩者分別對應「升級部署」與「初次部署」兩種情境，而非
> 單純互相矛盾——但這仍是本文件為釐清落差所作的暫定裁決，待團隊確認，完整說明見
> [06-open-questions.md](06-open-questions.md) 的 G-09。

## PR-14 — 正式環境安全與維運底線

**規則。** 正式環境**必須**透過 HTTPS 提供服務（依據：架構基準 §22.10）。`.env` 與其他機密設定
**必須不**提交到 Git Repository，Repository 只保存 `.env.example`（依據：架構基準 §22.9）。Log
**必須不**記錄密碼、Session secret、Authorization token（依據：架構基準 §24）。一個版本要視為可正式
交付，**必須**滿足完整的 Deployment Definition of Done，其中包含備份可執行、回滾路徑存在等可驗證項
目（依據：架構基準 §22A.20）。資料庫連線埠**應**原則上不對外公開，除非有明確維運需求並搭配
firewall 控制（依據：架構基準 §22.11）。Health check 端點**應**不回傳 secret 或敏感設定
（依據：架構基準 §22.14）。

**理由。** 這些是來源文件已明言的安全與維運底線；若只靠 §22A.20 對外部各節的指向，而不把個別條目寫
清楚，容易在實作時遺漏其中一項（依據：架構基準 §22.9–22.14、§22A.20、§23–24）。

**對貢獻者的意涵。** 新增任何對外服務、健康檢查端點或 log 輸出前，先確認是否可能洩漏密碼、token 或
其他敏感設定；資料庫或內部服務連接埠預設不對外公開；部署文件應包含可驗證的備份與還原步驟，而不是只
假設「有跑備份指令就夠了」。

**違反範例。** 把 `.env` 或內含 `SECRET_KEY` 的設定檔提交進 Git；health check 端點回傳資料庫連線字
串或 `SECRET_KEY`；log 裡直接印出使用者密碼或 Authorization header；資料庫埠對外綁定
`0.0.0.0:5432` 卻沒有明確維運需求與 firewall 控制。

## PR-15 — 報告產製失敗不得誤標為已完成，並可安全重試

**規則。** 報告產製（DB read → Image processing → DOCX generation → PDF conversion → File
storage → DB write）任一步驟失敗時，**不得**讓 Report 的狀態被誤標為已完成（如 `GENERATED`）；
**應**採用 `DRAFT` → `GENERATING` → `GENERATED` 的中間狀態，失敗時進入 `GENERATION_FAILED` 並保留
`error_message`，以便安全重新產生（依據：架構基準 §20.17）。牽涉檔案與資料庫兩種資源的操作若中途失
敗（例如 DOCX/PDF 已寫入 Storage 但資料庫交易失敗，或反之），**應**有明確的復原原則，避免留下「檔
案存在但資料庫不知道」或「資料庫記錄存在但檔案遺失」的不一致狀態（依據：架構基準 §20.17）。

**理由。** 報告是核心交付物，若失敗卻被誤標為已完成，使用者可能拿到不存在或損毀的 DOCX／PDF 而不自
知；跨資源操作沒有明確復原原則，會讓失敗後的狀態難以排查與重試（依據：架構基準 §20.17）。

**對貢獻者的意涵。** 新增任何涉及檔案與資料庫兩種資源的寫入流程時，先設計失敗路徑與復原／重試機
制，不要只實作成功路徑；報告狀態機須能表達「產製中」與「產製失敗」，不能只有「未產生」與「已產
生」兩種狀態。

**違反範例。** 報告產製流程只在全部步驟成功後才寫一次 DB record，PDF 轉換失敗時整個沉默失敗，沒有
留下任何可追蹤的失敗狀態與錯誤訊息。

## PR-16 — 實體狀態轉換一律由後端 Service 層掌控

**規則。** `Inspection Plan`／`Inspection Task`／`Template Version`／`Evidence`／`Report` 等實體的
狀態轉換**必須**由後端 Service 層掌控與驗證合法轉換路徑；前端**不得**直接寫入任意字串作為狀態值
（依據：架構基準 §18）。

**理由。** 避免 status 被任意字串亂改而破壞狀態機的合法轉換路徑，也讓「是否可以完成」這類判斷維持
與 PR-01 一致的伺服器端覆核原則（依據：架構基準 §18）。

**對貢獻者的意涵。** 新增狀態欄位或狀態轉換邏輯時，一律在後端 Service 層定義合法的轉換規則；前端只
能請求「轉換到某狀態」的動作（例如呼叫代表明確業務動作的端點），不能直接覆寫狀態欄位值。

**違反範例。** 前端呼叫一個通用的 PATCH 端點，直接把 `status` 欄位設成任意字串，而不是呼叫
`/tasks/{id}/complete` 這類代表明確業務動作的端點。

## PR-17 — API 契約：REST/JSON、檔案上傳與錯誤碼邊界

**規則。** Backend API **必須**採 REST + JSON，並以 `/api/v1` 作為前綴；照片等檔案上傳**必須**採
`multipart/form-data`（依據：架構基準 §14）。API 錯誤**必須**用結構化的 `error.code` 表達（與 PR-08
同一要求，依據：架構基準 §25）。

**理由。** 一開始就加 `/v1` 前綴成本很低，但對未來 API 演進很有價值；統一契約才能讓多個前端與未來第
三方介面穩定整合（依據：架構基準 §14）。

**對貢獻者的意涵。** 新增端點時遵守 `/api/v1` 前綴與 REST/JSON 慣例；檔案上傳一律走
`multipart/form-data`，不要求以 JSON base64 欄位取代大型檔案上傳；新增錯誤情境時，先定義對應的
`error.code`。

**違反範例。** 新增一個不帶版本前綴的端點；用 JSON base64 欄位取代 multipart 上傳大型照片檔案。

## 不可延後的意圖（Costly-to-Retrofit Intents）

以下意圖如果在第一版沒有落實，之後要補救的成本非常高（可能需要資料遷移、破壞既有對外參照，或已經
無法回頭重建遺失的歷史）。它們**必須**在第一次正式釋出時就落實，不能以「之後再補」為由延後：

1. **任務建立當下即凍結需求（Task-time immutable requirements）** — 見 PR-04；範本必須版本化，任務
   建立時必須把當下生效的需求複製成快照並保留來源關聯。事後才補做，等於默默改寫過去任務的定義
   （依據：架構基準 §2.5、§12.4–12.9、§16.2、§37 ADR-006）。
2. **報告產製當下即凍結來源（Report-time frozen provenance）** — 見 PR-06；報告快照、範本版本、所選
   證據／Variant ID、文件編號／版次、產製者與時間、檔案鍵與雜湊都必須保存，已核發文件不得覆蓋。事後
   想從已變動的即時資料重建一份「當初核發的報告」幾乎不可靠
   （依據：架構基準 §20.5–20.8、§20.11、§20.13–20.15、§30 Phase 9）。
3. **原圖保存與 Variant 系譜（Original preservation & variant lineage）** — 見 PR-05；原圖位元組與雜
   湊、每個衍生 Variant 的編輯參數、建立者與時間、以及回溯到原圖的關聯，都必須從第一版就保存。原圖一
   旦遺失或被覆蓋，後續無法重建（依據：架構基準 §13.3、§13A.2–13A.4、§13A.9–13A.11）。
4. **穩定的識別碼與儲存鍵策略（Stable ID & storage key schemes）** — 見 PR-02、
   [04-key-decisions.md](04-key-decisions.md) KD-07；主要 entity 使用 UUID、業務編號與 UUID 分離、
   storage key 由後端產生且不可用使用者原始檔名。一旦外部已經開始參照這些識別碼，事後更換識別碼策略
   會是高風險遷移（依據：架構基準 §11、§13.1–13.2、§20.8/20.11/20.15、§37 ADR-007）。
5. **資料庫與儲存體的抽象層（Storage & DB migration seams）** — 見 PR-02、PR-03；所有資料庫存取經
   SQLAlchemy／Alembic，所有檔案存取經 Storage 抽象層，API contract 不依賴 SQLite 或本機路徑。事後要
   拔除散落各處的檔案路徑硬編碼與 SQLite-only SQL，成本很高（依據：架構基準 §2.2–2.3、§4.4–4.5、
   §7.4、§32–33）。
6. **身分、授權與最低限度稽核 metadata** — 見 PR-01、PR-08；重要寫入從第一版就要記錄操作者與時間；狀
   態變更由 Service 層掌控，指派／權限一律在伺服器端驗證。事後無法回填「當初到底是誰做的」這種歷史資
   訊（依據：架構基準 §7.1–7.2、§16.3–16.6、§17–19、§24）。
7. **一致的備份／還原單位** — 見 PR-12；資料庫、原圖／衍生照片、報告範本與已核發 DOCX／PDF 必須被當
   成同一組可還原資料集，備份時間點必須一致。只備份 SQLite 檔或只備份檔案，會留下互相對不上的殘缺資
   料（依據：架構基準 §20.5/20.15、§22.12、§22A.9–10、§23）。
8. **API 凍結前先講清楚規則與結果語意** — 見 PR-09；`required`／`min_count`／`max_count`、查核結果為
   負面時是否仍可完成任務、間距（interval）規則等如何互動，都必須先講清楚，前端只依伺服器資料渲染、
   依穩定的 `error.code` 判斷。這些語意一旦在 API 凍結後才改變，可能使已蒐集的證據與既有前端行為失
   效；目前查核結果（Result）語意本身仍是 [06-open-questions.md](06-open-questions.md) 中未定案的項
   目，任何後續定案都必須遵守 PR-04 的歷史不可變原則，不能讓已完成任務的既有資料被追溯性改寫
   （依據：架構基準 §2.4、§12.6/12.9、§16.4–16.6、§25）。
