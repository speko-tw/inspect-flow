# 版本與 Milestone 治理（Versioning and Milestone Governance）

**這份文件回答**：InspectFlow 的版本號、GitHub Milestone、Issue 與 Pull Request 的版本歸屬規則是什麼？既有歷史 Issue／PR 的 Milestone 要怎麼整理？
**什麼時候讀**：規劃版本／Roadmap、建立或修改 Issue／PR 的 Milestone、判斷一項工作該歸屬哪個版本系列，或執行既有 GitHub metadata 的版本遷移時。

InspectFlow 在正式發布 `1.0.0` 前持續以 `0.x.x` 系列發展。版本號、Milestone、Issue、PR 各自回答不同問題：

| 項目 | 回答什麼問題 |
|---|---|
| 版本號 | 這個版本已經具備哪些產品能力？ |
| Milestone | 這項工作最晚應該在哪個產品能力版本完成？ |
| Issue | 這次要完成哪一件事？ |
| PR | 這次實際改了什麼，並完成哪個 Issue？ |

追溯鏈：Intent → Spec → Plan → Issue → PR → Milestone → Release。

**依據**：負責人決定（2026-09-26）。

## 1. 版本號

<a id="vg-01"></a>
**VG-01：版本號代表產品能力，不代表時間**

版本號**不得**依開發週次、Sprint、Issue、PR 或 Commit 數量決定，**應**表示已達成的產品能力。

**理由**：看版本號就知道產品能做什麼。（依據：負責人決定（2026-09-26））

<a id="vg-02"></a>
**VG-02：`0.MINOR.PATCH`，`0.10` 是下一個系列不是小數**

1.0 前採 `0.MINOR.PATCH`（例：`0.9.2`、`0.10.0`）；`0.10.0` 是 `0.9.x` 之後的下一個 MINOR 系列，不是小數點意義上的 0.10。

**理由**：避免把版號當十進位小數比大小，讀錯發展順序。（依據：負責人決定（2026-09-26））

<a id="vg-03"></a>
**VG-03：MINOR／PATCH 分工，PATCH 不夾帶新能力**

| 位數 | 用途 |
|---|---|
| MINOR | 新的主要產品能力階段；新能力形成時升 MINOR，不靠累加 PATCH |
| PATCH | 同一能力階段內的 bug fix、validation 補強、安全性、文件、相容性、小型 UX、不改能力範圍的重構 |

新的主要能力**應**進下一個 MINOR，**不應**以 PATCH 發布；已發布外部契約的重大行為改變也**不應**當成一般 PATCH。

**理由**：同一系列的 PATCH 都要能放心升級。（依據：負責人決定（2026-09-26））

<a id="vg-04"></a>
**VG-04：GitHub Milestone 與 Release Tag 分離**

Milestone 用 `0.MINOR.x`（`x` 是系列 wildcard，例：`0.2.x`）；Git tag／GitHub Release 用完整版號 `v0.MINOR.PATCH`（例：`v0.2.0`、`v0.2.1`）。能力完成才發 Release，之後以 PATCH 修正。正式 Milestone 名稱為 `0.1.x`～`0.11.x`；暫不設 Due Date，有交付日期承諾才設。

**理由**：Milestone 是版本系列的規劃單位，Release 才是實際發布的版本。（依據：負責人決定（2026-09-26））

## 2. Phase 與 Milestone

<a id="vg-05"></a>
**VG-05：不得只依 Phase 編號機械決定 Milestone**

Phase 是實作順序與相依；Milestone 是哪個版本系列交付該能力。多數 Phase 與 Milestone 會自然對齊，但共用 Domain Model、State Machine、Infrastructure 或 Decision Issue 可能跨越多個 Phase；**不得**只依 Phase 編號機械決定 Milestone，**應**依「這項工作主要交付什麼能力」判斷。

**理由**：機械對應會讓共用規格被錯誤地綁在單一 Phase 上。（依據：負責人決定（2026-09-26））

<a id="vg-06"></a>
**VG-06：新增系列要說明新能力，不是因為編號用完**

路線圖**得**新增 0.12.x 以後的系列，但**必須**先說明是什麼新能力階段，**不得**只因「0.11 用完了」。

**理由**：版本號代表能力階段，新增系列也要維持這個對應。（依據：負責人決定（2026-09-26））

## 4. 1.0.0 的定義

<a id="vg-07"></a>
**VG-07：1.0.0 靠業務閉環，不靠時間到了**

`1.0.0` 不因開發時間到了而發布；**必須**完成完整業務閉環：Project／User／Permission → Inspection Template → Inspection Plan → Inspection Task → Field Inspection → Evidence → Completion Validation → Dashboard → Report Snapshot → DOCX／PDF → Pilot Deployment → Backup／Restore，並完成至少一次代表性 Pilot 驗證。

發布條件（全部成立）：

- 核心流程可實際使用
- 正式 DOCX／PDF 可產生
- 重要資料可追溯
- 已核發報告不可靜默覆蓋
- Deployment Definition of Done 通過
- Backup／Restore 經驗證
- 沒有阻擋正式使用的已知 Critical 問題
- Pilot 必要修正已完成

`0.11.x` 結束仍未達成時，**得**繼續 `0.12.x`……；**不得**為版號好看強迫發布 `1.0.0`。

**理由**：`1.0.0` 代表對外可信賴的完整能力，不是排程節點。（依據：負責人決定（2026-09-26））

## 5. Milestone 歸屬

**依據**：負責人決定（2026-09-26）。

<a id="vg-08"></a>
**VG-08：Milestone 表示「最晚在哪個版本完成」，與 Priority／Effort 分離**

Milestone 不代表 Sprint、開發者、Priority、Effort 或 Issue 狀態；**不得**因 Priority 高就把 Issue 移到較早的 Milestone。Priority、Effort 的定義與填寫見 [`docs/specs/README.md` 欄位設定](../specs/README.md#issue-pr-fields)。

**理由**：這些資訊已有別的欄位，混用會讓路線圖失真。（依據：負責人決定（2026-09-26））

<a id="issue-ownership-table"></a>
### Issue 歸屬

| Issue 類型 | 歸到 | 例 |
|---|---|---|
| 實作 | 主要交付能力所屬版本；新增 Issue 時**不得**因「目前在做 0.2.x」就全放 0.2.x | 登入 API → 0.2.x |
| `needs-decision` | **必須**有 Milestone；歸「最早因這個決策未完成而無法完成」的版本 | 報告快照時機 → 0.9.x |
| `blocked` | 維持真正所屬的 Milestone，**不得**因暫時無法實作而放錯版本 | — |
| Spec／Plan | 跟著該能力的 Milestone | 撰寫 template-system spec → 0.3.x |
| 開發基礎治理（AGENTS.md、metadata 規則、CI、審查準則、版本治理） | 歸 0.1.x | — |
| Pilot 部署基礎設施（Docker Compose、正式 HTTPS、Backup） | **應**歸 0.10.x | — |

規格索引標為「延後」的能力（例如 `external-identity-sync`）排進路線圖前**不**開 Issue，因此不需要 Milestone；決定要做時，再依 [VG-06](#vg-06)（新增系列的條件）或排入 1.0 之後的版本。（依據：負責人決定（2026-09-27））

<a id="vg-09"></a>
**VG-09：Issue 跨多個版本先判斷能否拆分**

Issue 涵蓋多個版本系列時，先判斷能否作為單一工作完成；不能就**應**拆分。無法拆分時暫用「最早需要它的版本」，並**應**列入 audit 由人確認。Milestone 模糊通常代表範圍模糊。

**理由**：硬塞進一個 Milestone 只是把範圍模糊藏起來，而不是解決它。（依據：負責人決定（2026-09-26））

<a id="pr-ownership-table"></a>
### PR 歸屬

| 情況 | 規則 |
|---|---|
| 關閉一個 Issue | **必須**與該 Issue 同一 Milestone；Issue 的 Milestone 在合併前改了，PR **必須**同步 |
| 關閉多個 Issue，同一 Milestone | 用該 Milestone |
| 關閉多個 Issue，跨 Milestone | 先檢查 PR 是否過大；歷史資料無法拆分則依主要交付能力；仍無法判定**不得**猜測，列人工檢查 |

沒有 Issue 的歷史 PR 屬於整理既有 metadata 的情況，規則見[第 6 節](#existing-metadata-cleanup)。

## 6. 整理既有 Milestone

<a id="vg-10"></a>
**VG-10：整理範圍含已關閉的 Issue／PR**

規則生效後，既有 Issue／PR（含已關閉、已合併）**必須**逐步整理；不因已關閉就保留錯誤 Milestone。

**理由**：歷史 metadata 也是專案歷史的一部分，應保持一致。（依據：負責人決定（2026-09-26））

<a id="vg-11"></a>
**VG-11：整理只改 Milestone**

整理時原則上只改 Milestone；除非另有 Issue 指示，**不得**改 title、body、state、assignee、labels、Priority、Effort、commit、branch、code，**不得**為改 Milestone 而 reopen／close。

**理由**：Migration 是 metadata 整理，不是內容審查或狀態變更。（依據：負責人決定（2026-09-26））

<a id="vg-12"></a>
**VG-12：先 dry-run、分批、每批驗證，不確定就列 `NEEDS_REVIEW`**

1. migration 開始前**必須**先確認本文件已合併進 `main`；合併前**不得**開始大規模修改歷史 metadata。
2. 不應一次改整個 repo；**必須**先做 dry-run 分類。
3. Current＝Proposed 時**不得**產生無意義的更新。
4. 分批進行，**不得**改了大量筆數才驗證；每批**必須**重讀並確認 expected＝actual，有失敗先查明原因再繼續。
5. 無法可靠判斷時**不得**猜測，列入 `NEEDS_REVIEW` 交負責人決定。
6. 已存在的 Milestone **不得**重複建立；未知或其他既有的 Milestone **不得**直接刪除。
7. 這些原則也適用於日後的 metadata audit。

**理由**：一次性大規模修改難以驗證與回滾；不確定時列清單交給人判斷，比自行猜測安全。（依據：負責人決定（2026-09-26））

**沒有 Issue 的歷史 PR**：依 title、body、changed files、相關 Spec、commit、最接近的能力判斷 Milestone；仍無法可靠判斷標 `NEEDS_REVIEW`，**不得**任意分類。

執行步驟、欄位與分批分組見 migration issue（待開，開好後補連結）。

## 7. 何時修改本文件

<a id="vg-13"></a>
**VG-13：改規則才改本文件，例行工作不用**

以下情況要修改本文件：改變 MINOR／PATCH 定義、Milestone 與 Release 的關係、`1.0.0` 定義、新增或重新切分主要產品能力階段、Issue／PR Milestone 歸屬規則。單純新增／完成 Issue、發 PATCH、bug fix 不需要修改本文件；變更等級與流程見 [`docs/specs/README.md` 變更等級](../specs/README.md#change)。

**理由**：讓治理規則本身穩定，不因日常工作而頻繁改版。（依據：負責人決定（2026-09-26））
