# 名詞表（Glossary）

**這份文件回答**：某個中文說法或英文欄位，對應到系統裡的哪一個實體？它跟其他實體是什麼關係？
**什麼時候讀**：命名新欄位、討論資料模型，或看到「work order」這類非正式用語時，先查這裡再自創新名詞。

領域名詞、對應的英文系統實體名、定義，以及它與其他名詞的關聯。凡是原文以中文表達的概念，第一次出現 時保留其來源用語；系統實體名稱一律使用英文（例如 `Inspection Task`、`Evidence`），符合原始碼與資料庫 中的實際命名。

## 「work order」對照說明

GitHub Issue 上使用的非正式用語 **work order**，在架構基準文件中沒有獨立的實體對應；它實際指的是
**`Inspection Task`（查核任務）**——後台建立、指派給現場工程師執行的最小可執行工作單位 （依據：架構基準 §12.8）。撰寫規格或程式碼時請一律使用 `Inspection Task`，不要另外引入 "work order" 作為系統實體名稱，以免與 `Inspection Task` 產生兩套平行詞彙。

## 開發流程用語對照

[docs/specs/README.md](../specs/README.md) 描述開發流程時使用的「任務」「計畫」「範本」「狀態」，分別指 GitHub 上的開發工作（task）、`plan.md`、文件與 issue 範本、規格文件狀態，與本表的 `Inspection Task`、`Inspection Plan`、`Inspection Template`／`Report Template` 及實體狀態無關。規格或程式碼提到領域實體時，一律寫英文實體名。

## 名詞總表

| 中文名稱 | 英文名稱（系統實體名） | 定義 | 關聯 |
|---|---|---|---|
| 專案 | `Project` | 一項工程查核工作所屬的專案；必填欄位為業務編號 `project_code`（可與其他 `Project` 重複，不加資料庫唯一約束）、工程名稱、業主／委託單位、整體工程地點（依據：負責人決定，#71，2026-09-28，見 [KD-39](03-decisions-and-stack.md#kd-39)；取代架構基準 §12.2 的最小佔位欄位）。 | 是 `Inspection Plan` 的上層對象；`Report` 也歸屬於某個 `Project`；內部可依需要選用工項分類與分區（見 [KD-40](03-decisions-and-stack.md#kd-40)）。 |
| 範本庫 | 具體資料表／欄位由 `domain-model` 規格制定 | 獨立於專案的查核範本集合，所有專案都能從中挑項目套用（複製）到自己的查核項目；選用，專案也可從零建立（依據：負責人裁定（[#74 留言](https://github.com/speko-tw/inspect-flow/issues/74#issuecomment-5956038822)，2026-10-02），見 [KD-47](03-decisions-and-stack.md#kd-47)）。 | 由範本管理員維護（[KD-49](03-decisions-and-stack.md#kd-49)）；套用後專案那份與範本各自獨立；只存結構，不存現場結果與照片（[KD-48](03-decisions-and-stack.md#kd-48)）。 |
| 查核範本 | `Inspection Template` | 範本庫中可套用的一份查核結構（單一查核項目或整個系統）：歸在「工程類別 → 系統」兩層分類下，內含查核項目、查核項次、檢查標準與照片要求；修改時直接覆蓋，只保留最新內容，不版本化（依據：負責人裁定（[#78 留言](https://github.com/speko-tw/inspect-flow/issues/78#issuecomment-5956039701)，2026-10-02），見 [KD-03](03-decisions-and-stack.md#kd-03)、[KD-48](03-decisions-and-stack.md#kd-48)；取代架構基準 §12.3 的「邏輯名稱、底下有版本」設計）。查核範本的單位有兩種：單一查核項目，或整個系統（含其下所有查核項目），套用時也一樣（依據：[負責人裁定（#313，2026-10-02）](https://github.com/speko-tw/inspect-flow/issues/313)，見 [KD-47](03-decisions-and-stack.md#kd-47)）。**查核範本不等於報告範本**：前者是範本庫裡用來建立查核項目的結構，後者是正式報告的版面（見「報告範本」）（依據：[負責人確認（#313，2026-10-02）](https://github.com/speko-tw/inspect-flow/issues/313)）。 | 底下直接有 `Template Item`；套用到專案時複製，專案記錄來源查核範本名稱與套用時間；與報告範本（`Report Template`）無關，不可混淆。 |
| 查核範本版本 | `Template Version`（**已取消**） | 原本用來把查核範本固定在特定時間點（v1、v2、v3……）的實體；查核範本改為直接覆蓋、不版本化，此實體不再使用；報告範本版本（`Report Template Version`）不受影響（依據：負責人裁定（[#78 留言](https://github.com/speko-tw/inspect-flow/issues/78#issuecomment-5956039701)，2026-10-02），見 [KD-03](03-decisions-and-stack.md#kd-03)）。保留此列僅供對照舊文件與架構基準 §2.5、§12.4。 | 「快照」改由套用時複製到專案的那一份負責；不要在新的規格或程式碼引入 `Template Version`。 |
| 套用範本 | 具體資料表／欄位由 `domain-model` 規格制定 | 把範本庫的項目複製成專案自己的查核項目，並記錄來源範本名稱與套用時間；由有權限編輯該專案查核項目的人進行；專案已有同名查核項目時拒絕套用並提示哪些項目已存在，需要第二份時先改名再套用（依據：負責人裁定（[#74 留言](https://github.com/speko-tw/inspect-flow/issues/74#issuecomment-5956038822)，2026-10-02；重複套用見[#313 留言](https://github.com/speko-tw/inspect-flow/issues/313#issuecomment-5974836112)，2026-10-04），見 [KD-47](03-decisions-and-stack.md#kd-47)、[KD-49](03-decisions-and-stack.md#kd-49)）。 | 套用後修改範本，不回頭改動已套用的專案；範本被覆蓋後不保證能回看套用當時的內容。 |
| 工程類別、系統 | 具體資料表／欄位由 `domain-model` 規格制定 | 範本分類先固定的兩層：「工程類別 → 系統」，其下為查核項目；試做，日後調整另開 issue；同一層之下名稱不得重複，不同層可重複，目前只用名稱、不設代號（依據：負責人裁定（[#74 留言](https://github.com/speko-tw/inspect-flow/issues/74#issuecomment-5956038822)，2026-10-02），見 [KD-48](03-decisions-and-stack.md#kd-48)）。 | 專案內是否使用分類與分區仍依 [KD-40](03-decisions-and-stack.md#kd-40) 選用；分區不是分類的子層。 |
| 範本項目 — 查核項目組 | `Template Item` | 範本底下的一個查核項目組（有 `sequence`、`title`、`instruction`）；由內業事先設定，其下**得**再細分多個「查核項次」（例如同一通風管項目組下的材料、尺寸），各項次各自判定結果（符合／不符合／不適用，見「查核結果」條目）（依據：架構基準 §12.5；查核項次的業務語意依負責人決定，#75、#76，2026-09-28，見 [KD-37](03-decisions-and-stack.md#kd-37)、[KD-38](03-decisions-and-stack.md#kd-38)）。查核項次的具體資料表／欄位由 `domain-model` 規格制定，不在此預先假設。 | 底下掛著一或多個 `Evidence Requirement`；查核項次與照片的覆蓋規則見 [KD-38](03-decisions-and-stack.md#kd-38)、[KD-50](03-decisions-and-stack.md#kd-50)；每個項次的檢查標準見「檢查標準」條目。 |
| 證據需求 | `Evidence Requirement` | 某個 `Template Item` 要求提供的一項證據定義，例如「PHOTO / LENGTH / required」，含 `type`、`required`、`min_count`、`max_count`（依據：架構基準 §12.6）。 | 是「查核規則即資料」原則（見 [PR-09](02-principles.md#pr-09)）的具體落實；`Inspection Task` 建立時被複製為 `Task Requirement Snapshot`。照片的張數規則（至少 1 張、無上限）見 [KD-50](03-decisions-and-stack.md#kd-50)。 |
| 查核計畫 | `Inspection Plan` | 某個 `Project` 在某一天／某一批的工作，指派給某位 `Inspector`（依據：架構基準 §12.7）。 | 一個 `Inspection Plan` 展開後產生多筆 `Inspection Task`。 |
| 查核任務 | `Inspection Task` | 依 `Inspection Plan` 產生的可執行工作單位，可能對應一個區段／位置（例如「0–10 m」），有自己的狀態機（依據：架構基準 §12.8、§18）。一個任務**得**包含多個查核項目（像一張抽查紀錄表），只查一項就建只含一項的任務（依據：負責人裁定（[#103 留言](https://github.com/speko-tw/inspect-flow/issues/103#issuecomment-5969654262)，2026-10-03）；裁定用語「查核項目」與本表「查核項目組」「查核項次」的對應，待 `inspection-planning` 規格確認）。**Issue 上俗稱的「work order」即指此實體**，見上方對照說明。 | 隸屬於某個 `Inspection Plan`；建立時產生自己的 `Task Requirement Snapshot`（建立任務時必須產生快照；專案查核項目修改後只作廢被修改的查核項目、同一任務補查，見 [KD-55](03-decisions-and-stack.md#kd-55)）；完成後可作為 `Report` 的資料來源之一。 |
| 草稿（任務） | 具體資料表／欄位由 `domain-model` 規格制定 | 任務建立後的起始狀態；現場看不到，內業按「派出」後現場才看得到（依據：架構基準 §18、負責人裁定（[#103 留言](https://github.com/speko-tw/inspect-flow/issues/103#issuecomment-5969654262)，2026-10-03）；見 [KD-56](03-decisions-and-stack.md#kd-56)）。 | 與「派出」「計畫進行中」連動；未派出的草稿**得**直接刪除，派出後只能取消；計畫底下仍有草稿時，計畫不算完成（依據：負責人補充裁定（[#103 留言](https://github.com/speko-tw/inspect-flow/issues/103#issuecomment-5970063986)，2026-10-03））；草稿還沒有結果與照片，不涉及 [KD-55](03-decisions-and-stack.md#kd-55) 的作廢。 |
| 派出（任務） | 具體資料表／欄位由 `domain-model` 規格制定 | 內業按「派出」，任務離開草稿、現場才看得到；第一個任務派出時，計畫自動變為「進行中」（依據：架構基準 §18、負責人裁定（[#103 留言](https://github.com/speko-tw/inspect-flow/issues/103#issuecomment-5969654262)，2026-10-03）；見 [KD-56](03-decisions-and-stack.md#kd-56)）。 | 逐個任務派出，不是整個計畫一起派出；派出後只能取消、不能刪除；派出後任務的狀態名稱由 `state-machines` 規格確認。 |
| 任務需求快照 | `Task Requirement Snapshot`（資料表：`task_requirements`） | `Inspection Task` 建立當下，把當時生效的 `Evidence Requirement` 複製、固定下來的紀錄，含 `source_requirement_id` 回指原始需求（依據：架構基準 §2.5、§12.9）。 | 是 [PR-04](02-principles.md#pr-04)（歷史不可變）原則的核心資料結構，建立後不改寫；例外只有內業修改專案查核項目時的兩種選擇：選重新查核則只作廢被修改的查核項目並補查（作廢項目的舊快照保留），選「不要」則一併更正文字、不動結果與照片（見 [KD-55](03-decisions-and-stack.md#kd-55)）；`Inspection Task` 的完成度檢查與報告，都應讀這張快照，而非目前版本的 `Evidence Requirement`。 |
| 作廢（標準變更） | 具體資料表／欄位由 `domain-model` 規格制定 | 內業修改專案查核項目並選「要重新查核」時，只作廢任務裡被修改的那個查核項目；作廢的照片、結果與當時標準不刪除，標示「標準變更作廢」存檔，內業人員必須找得到，報告不使用作廢資料；同一任務其他項目的結果與照片保留，任務退回「進行中」，補查後再完成（依據：負責人裁定（[#78 留言](https://github.com/speko-tw/inspect-flow/issues/78#issuecomment-5966290670)，2026-10-03；範圍改為項目層級見[補充裁定](https://github.com/speko-tw/inspect-flow/issues/103#issuecomment-5970063986)，同日），見 [KD-55](03-decisions-and-stack.md#kd-55)）。 | 作廢項目的紀錄整份保留、只標示作廢，不改寫，符合 [PR-04](02-principles.md#pr-04)；選「不要重新查核」不作廢，用到該項次的已建立任務一併更正文字內容（不動結果與照片、狀態不變，見 KD-55）；草稿任務還沒有結果與照片，不涉及作廢。作廢資料不刪除與 [G-05](05-open-questions.md#g-05) 有關，但 G-05 仍未裁定。 |
| 已取消（任務） | 具體資料表／欄位由 `domain-model` 規格制定 | 內業取消的任務狀態；未完成的任務（未開始、進行中）都**得**取消，**必須**填原因，已記錄的照片與結果保留，任務顯示「已取消」，不計入計畫完成判斷；已完成的任務**不得**取消；與「作廢（標準變更）」不同，後者是標準變更重查造成的（依據：架構基準 §18、負責人裁定（[#78 留言](https://github.com/speko-tw/inspect-flow/issues/78#issuecomment-5967467998)，2026-10-03；[#103 留言](https://github.com/speko-tw/inspect-flow/issues/103#issuecomment-5969654262)，2026-10-03）；見 [KD-56](03-decisions-and-stack.md#kd-56)）。 | 屬於某個 `Inspection Task`；已完成的任務不開放重開也不得取消，不能用取消取代 [KD-55](03-decisions-and-stack.md#kd-55) 的重查；取消的任務**得**恢復（見「恢復（任務）」）。 |
| 恢復（任務） | 具體資料表／欄位由 `domain-model` 規格制定 | 取消的任務**得**恢復，回到取消前的狀態繼續查核，已記錄的照片與結果仍在；取消期間標準被修改時，恢復後改用目前標準，被修改的項目待重查（[#103 留言](https://github.com/speko-tw/inspect-flow/issues/103#issuecomment-5970733042)）（依據：架構基準 §18、負責人裁定（[#103 留言](https://github.com/speko-tw/inspect-flow/issues/103#issuecomment-5969654262)，2026-10-03）；見 [KD-56](03-decisions-and-stack.md#kd-56)）。 | 恢復是否須填原因、恢復後計畫狀態如何變，裁定沒有說明，待規格；恢復本身不是作廢；但取消期間標準被修改時，恢復後被修改的項目依「作廢（標準變更）」處理。 |
| 已取消（計畫） | 具體資料表／欄位由 `domain-model` 規格制定 | 計畫底下的任務全部取消時，系統自動設的計畫狀態；若有任務已完成、其餘取消，計畫是「已完成」而不是「已取消」（依據：架構基準 §18、負責人裁定（[#103 留言](https://github.com/speko-tw/inspect-flow/issues/103#issuecomment-5969654262)，2026-10-03）；見 [KD-56](03-decisions-and-stack.md#kd-56)）。 | 與「已取消（任務）」是不同實體的狀態；已取消的計畫仍得封存。 |
| 封存（計畫） | 具體資料表／欄位由 `domain-model` 規格制定 | 內業手動把計畫封存（與取消封存），任何狀態（進行中、已完成、已取消）的計畫都得封存；「進行中」「已完成」「已取消」由系統自動變更，第一個任務派出前的狀態（暫定草稿、就緒）與取消封存後回到哪個狀態未定，待規格；已封存的計畫，底下任務唯讀，須先取消封存才能修改標準、查核、取消或恢復任務（唯讀依業界慣例提出，負責人同意；依據：架構基準 §18、負責人裁定（[#78 留言](https://github.com/speko-tw/inspect-flow/issues/78#issuecomment-5967467998)，2026-10-03；[#103 留言](https://github.com/speko-tw/inspect-flow/issues/103#issuecomment-5969654262)，2026-10-03；補充裁定 [#103 留言](https://github.com/speko-tw/inspect-flow/issues/103#issuecomment-5970063986)，同日）；見 [KD-56](03-decisions-and-stack.md#kd-56)）。 | 計畫的「進行中」「已完成」「已取消」由系統自動變更，見 [KD-42](03-decisions-and-stack.md#kd-42)、[KD-56](03-decisions-and-stack.md#kd-56)。 |
| 有缺失 | 具體資料表／欄位由 `domain-model` 規格制定 | 任務有「不符合」的項次但資料齊全、已完成時，清單與報告上明顯標示的記號；不擋任務完成與計畫自動完成；是否為獨立狀態值，裁定沒有說明（依據：負責人裁定（[#78 留言](https://github.com/speko-tw/inspect-flow/issues/78#issuecomment-5967467998)，2026-10-03）；見 [KD-56](03-decisions-and-stack.md#kd-56)、[KD-54](03-decisions-and-stack.md#kd-54)）。 | 不符合後的改善追蹤與限期複查屬 0.7.x。 |
| 已被新版取代 | 具體資料表／欄位由 `report` 相關規格制定 | 已核發的報告有錯、出新版取代後，舊版的標示；舊版保留、不覆蓋、不刪除；與原 §20.6 列舉的 `SUPERSEDED` 是否為同一狀態，裁定沒有說明（依據：負責人裁定（[#94 留言](https://github.com/speko-tw/inspect-flow/issues/94#issuecomment-5967468330)，2026-10-03）；見 [KD-57](03-decisions-and-stack.md#kd-57)）。 | 與「版次」（`revision`）、[PR-06](02-principles.md#pr-06) 對應；核發不需送審。 |
| 證據 | `Evidence` | 現場工程師針對某個 `Task Requirement Snapshot` 提交的一筆記錄（依據：架構基準 §12.10）；MVP 佐證只收照片，原 `TEXT` 類型是否保留待規格確認（見 [KD-53](03-decisions-and-stack.md#kd-53)）。 | 屬於某個 `Inspection Task` 與某個 `Task Requirement Snapshot`；照片類型依「現場版」「內業版」兩階段保存（見下方條目，依負責人決定 #90～#92，2026-09-28），TEXT 等其他類型不適用此兩階段模型。 |
| 現場版 | 具體資料表／欄位由 `domain-model` 規格制定 | 現場人員拍照、編修並確認後保存的照片版本，是每筆證據照片的第一個保存版本（依據：負責人決定，#90～#92，2026-09-28，見 [KD-32](03-decisions-and-stack.md#kd-32)、[KD-33](03-decisions-and-stack.md#kd-33)）；不另外保存拍攝原圖或編輯中間版本。 | 由現場人員產生並傳送至內業；內業系統據此加工產生內業版。 |
| 內業版 | 具體資料表／欄位由 `domain-model` 規格制定 | 內業系統取得現場版、加入現場與查核相關資訊後保存的照片版本；內業人員之後得再編修；正式報表一律使用內業版（依據：負責人決定，#90～#92，2026-09-28，見 [KD-32](03-decisions-and-stack.md#kd-32)、[KD-34](03-decisions-and-stack.md#kd-34)、[KD-35](03-decisions-and-stack.md#kd-35)）。 | 由現場版加工衍生；是報表產製的唯一圖片來源（見 [PR-07](02-principles.md#pr-07) 端到端可追溯性）；圖片上呈現的資訊欄位待後續規格定義。 |
| 照片註記 | 具體資料表／欄位由 `domain-model` 規格制定 | 現場工程師為每一張照片（總覽照片與佐證項次的照片）加的文字註記；有填寫就呈現在報告中，留白則不顯示，註記一律保留；也用來說明拍照留存的額外文件（例如「出廠證明」）（依據：負責人裁定（[#75 留言](https://github.com/speko-tw/inspect-flow/issues/75#issuecomment-5956039268)，2026-10-02），見 [KD-50](03-decisions-and-stack.md#kd-50)、[KD-53](03-decisions-and-stack.md#kd-53)）。 | 與 [OQ-12](05-open-questions.md#oq-12)（#81）「在照片上畫標註」是兩件事；註記是文字，不改動照片本身。 |

| 檢查標準 | 具體資料表／欄位由 `domain-model` 規格制定 | 每個查核項次可選「文字標準」（按計畫書原文記錄、系統不解析）或「數值標準」（標準值、條件 `≤`／`≥`／`＝`／範圍、單位、容許誤差；條件為範圍時有兩種形式，內業擇一：下限與上限的區間形式，或標準值 ± 容許誤差的形式）；0.3.x 範本先定義這兩種欄位，實測值輸入與自動判定屬 0.7.x（依據：負責人決定（#76，2026-09-28）、負責人裁定（[#313](https://github.com/speko-tw/inspect-flow/issues/313) 追加裁定，2026-10-02；範圍條件的兩種形式見[#313 留言](https://github.com/speko-tw/inspect-flow/issues/313#issuecomment-5974836112)，2026-10-04），見 [KD-37](03-decisions-and-stack.md#kd-37)、[KD-52](03-decisions-and-stack.md#kd-52)）。 | 屬範本結構的一部分（[KD-48](03-decisions-and-stack.md#kd-48)）；與現場填的實測值、符合／不符合／不適用的結果是不同東西。 |
| 查核結果 | 具體資料表／欄位由 `domain-model` 規格制定 | 現場人員對每個查核項次選的結果，三種：符合、不符合、不適用（N/A）；不得只替整個查核項目組選一個，也不得預設符合；系統不自動判定。選「不符合」必須選嚴重度並填註解；項次設有實測欄位時，必須全部填寫才能選符合或不符合（依據：負責人決定（#76，2026-09-28）、負責人裁定（[#76 留言](https://github.com/speko-tw/inspect-flow/issues/76#issuecomment-5965076758)，2026-10-03），見 [KD-37](03-decisions-and-stack.md#kd-37)、[KD-54](03-decisions-and-stack.md#kd-54)）。 | 對應來源文件的 `Result`、PASS／FAIL／N/A 措辭；介面與文件用中文「符合／不符合／不適用」。不符合後的改善追蹤與限期複查屬 0.7.x，尚未裁定。 |
| 不適用 | 具體資料表／欄位由 `domain-model` 規格制定 | 查核項次的第三種結果（N/A）：這個項次不適用，或設有實測欄位但量不到；必須填原因，照片選填（依據：負責人裁定（[#76 留言](https://github.com/speko-tw/inspect-flow/issues/76#issuecomment-5965076758)，2026-10-03），見 [KD-54](03-decisions-and-stack.md#kd-54)）。 | 量不到實測欄位時，不能選符合或不符合，改選本結果並寫原因。 |
| 嚴重度 | 具體資料表／欄位由 `domain-model` 規格制定 | 查核項次選「不符合」時**必須**選的等級：輕微、一般、嚴重；同時必須填註解說明問題（依據：負責人裁定（[#76 留言](https://github.com/speko-tw/inspect-flow/issues/76#issuecomment-5965076758)，2026-10-03），見 [KD-54](03-decisions-and-stack.md#kd-54)）。 | 嚴重度對任務完成與報告呈現的影響裁定沒有說明；不符合後的改善追蹤與限期複查屬 0.7.x。 |
| 實測欄位 | 具體資料表／欄位由 `domain-model` 規格制定 | 查核項次上要現場填寫的實際量測或記錄欄位（例如長、寬、高）；欄位與型別由內業事先設定，型別有兩種：數字（必須設單位，只接受數字）、文字（自由填寫）；設有實測欄位時必須全部填寫才能選符合或不符合（依據：負責人決定（#76，2026-09-28）、負責人裁定（[#76 留言](https://github.com/speko-tw/inspect-flow/issues/76#issuecomment-5965076758)，2026-10-03），見 [KD-37](03-decisions-and-stack.md#kd-37)、[KD-54](03-decisions-and-stack.md#kd-54)）。 | 與「檢查標準」（內業設定的要求）是不同東西；標準值與實測欄位單位的對應待規格對齊（[KD-54](03-decisions-and-stack.md#kd-54)）。 |
| 儲存鍵 | `storage_key` | 後端以 Evidence／檔案的 UUID 產生、指向實際檔案儲存位置的物件定位符（依據：架構基準 §13.1–13.2）；現場版與內業版各自有自己的 `storage_key`（見「現場版」「內業版」條目）；具體路徑格式尚未定案。 | 只是「檔案在哪」的內部定位符，**不是**授權憑證，也不是原始檔名或業務編號；原圖與衍生版並存的舊疑義已由 [G-02](05-open-questions.md#g-02)（已裁定：不存原圖，只存現場版與內業版）解決，路徑格式本身仍待技術規格定案。 |

| SHA-256 | `sha256` / `content_sha256` | 檔案或文件內容的雜湊值，用於完整性檢查、重複檔案偵測、備份驗證與歷史追蹤，**不用於**授權判斷（依據：架構基準 §13.3、§20.14）。 | 出現在 `Evidence`（現場版、內業版）、`Report` 等多處實體上。 |

| 權限 | 權限代碼，例如 `report.read`、`report.approve` | 「資料 × 動作」的組合：讀取、新增、修改、刪除，再加上簽核、匯出列印等特殊動作（依據：負責人決定（#63，2026-09-26）；架構基準無對應章節，見 [KD-25](03-decisions-and-stack.md#kd-25)）。 | 是「專案角色」的組成內容；系統存的是權限代碼，不是寫死的功能表。 |
| 專案成員 | `ProjectMember` | 人員與專案的關聯實體，承載這個人在這個專案掛的角色；同一人在同一專案可同時擁有多個角色，權限加總（依據：負責人決定（#63，2026-09-26）；取代架構基準 §17 的範例矩陣（§17 未區分專案範圍），見 [KD-27](03-decisions-and-stack.md#kd-27)）。 | 是 `User`、`Project`、`Role` 三者的關聯點；角色由有權限的人設定，之後可再修改。 |
| 全系統角色 | 具體資料表／欄位由 `domain-model`、`authentication` 規格制定 | 權限不屬於任何專案、由 Admin 直接指派給人員的角色；與專案角色、Admin 開關並存、不互相混用（依據：負責人裁定（[#313](https://github.com/speko-tw/inspect-flow/issues/313)，2026-10-02），見 [KD-49](03-decisions-and-stack.md#kd-49)）。 | 第一個全系統角色是「範本管理員」；全系統角色清單是否可自訂、還有哪些角色，待規格確認。 |
| 範本管理員 | 全系統角色之一 | 可新增、修改、刪除範本庫的範本，可查看所有專案並把任何專案的查核項目存成範本；範本建議加入與審核流程留待之後版本（依據：負責人裁定（[#313](https://github.com/speko-tw/inspect-flow/issues/313)，2026-10-02），見 [KD-49](03-decisions-and-stack.md#kd-49)）。 | 不負責把範本套用到專案：套用由有權限編輯該專案查核項目的人（專案角色）進行。 |
| 一級自主檢查、二級抽查 | 資料結構預留「自主檢查／抽查」區分與「由誰檢查」，具體欄位由規格制定 | 一級：廠商自己做的自主檢查；二級：甲方的監造／PCM 抽查。長期兩者都用本系統並串起來，MVP 以抽查紀錄表為核心（依據：負責人裁定（[#313](https://github.com/speko-tw/inspect-flow/issues/313) 追加裁定，2026-10-02），見 [KD-51](03-decisions-and-stack.md#kd-51)）。 | 檢查時機與停留點 MVP 不做；缺失改善追蹤屬 #76（0.7.x）、簽認屬 #77（0.8.x）。 |
| 外部身分來源 | `User.auth_source`（`local`／`external`）、`external_source`、`external_id`、`external_synced_at` | 人員帳號是本系統建立還是由外部身分來源（例如 ldap、ad、entra、erp）匯入的標記欄位與同步比對鍵；外部來源怎麼串接屬另開的規格，現階段由開發人員手動建立帳號（依據：負責人決定（#63，2026-09-26）；架構基準無對應章節，見 [KD-20](03-decisions-and-stack.md#kd-20)）。 | 同步時先用「來源＋`external_id`」比對，找不到再用 email 比對本系統建立的帳號並轉換身分來源，保留原本 UUID；外部值覆蓋基本欄位時寫稽核紀錄。 |
